# 087 - 실기기 검증을 Stop Hook으로 강제 — "파일 존재"와 "명령 실행"은 다른 신뢰도의 증거다

**073일차와 같은 패턴을 재사용한 줄 알았는데, 두 훅의 판정 근거를 뜯어보니 하나는 "확실한 증거"고 다른 하나는 "필요하지만 충분하지 않은 증거"였다**

---

## 목적

081(KOFIC 크래시 2건), 082(캐시 검증), 083(재사용성), 084(TalkBack), 086(위젯 배치)까지 5일 동안 **"실기기로 직접 확인"이 매번 반복**됐는데, 이건 사람이 매번 기억해서 하는 수동 습관이었다. 073일차의 Stop Hook 원칙("결정론적 사실 확인은 차단해도 안전")을 그대로 적용해서, 이 반복을 시스템으로 강제한다.

---

## 작업 1 — 판정 로직 설계

`.claude/hooks/lib/check_device_verification.py` — 073일차의 `check_test_pairing.py`와 같은 구조로, 세션 transcript를 훑어 판정한다.

```
이번 세션 transcript에서:
  presentation/**/*.xml, *Fragment.kt, *Widget.kt 등
  UI 관련 파일을 Edit/Write한 적이 있는데,

  adb 관련 bash 명령(install, shell am start, shell screencap 등)이
  같은 세션에서 한 번도 실행되지 않았다면
  → 차단
```

073일차의 무한 루프 방지 로직(`stop_hook_active` 플래그 — 한 번 막힌 뒤 재시도부터는 통과)도 그대로 재사용했다.

---

## 작업 2 — Stop Hook 등록

`stop-device-verification-guard.sh`를 만들고 `.claude/settings.json`의 `Stop` 훅 목록에 등록.

---

## 작업 3 — 시뮬레이션으로 즉시 검증 (071일차 방식 재사용)

070/071/073일차에서 반복 확인된 제약 — **새로 등록한 훅은 현재 세션에 자동 반영되지 않고, 세션 재시작 후에만 로드된다.** 071일차 때처럼 실제 세션이 받을 JSON 페이로드를 직접 구성해서 스크립트에 파이프로 흘려보내는 방식으로, 오늘 안에 동작을 검증했다.

**결과: UI 파일 수정 + adb 명령 없음을 가정한 가짜 transcript를 흘려보내자, 훅이 정확히 차단(exit 2)했다.**

## 작업 4 — 073일차 vs 087일차, 정말 같은 원칙이었나

### 겉모습은 동일

| | 073일차 | 087일차 |
|---|---|---|
| 훅 타입 | Stop | Stop |
| 판정 방식 | transcript를 grep하듯 스캔 | transcript를 grep하듯 스캔 |
| 무한 루프 방지 | `stop_hook_active` | `stop_hook_active` (동일 재사용) |

### 근거의 성격은 다르다 — "존재"와 "실행"은 다른 종류의 증거

| | 073일차: 테스트 파일 존재 여부 | 087일차: adb 명령 실행 여부 |
|---|---|---|
| 확인하는 것 | **정적 사실** — 파일이 있는가 없는가 | **세션 내 이벤트** — 명령이 실행됐는가 안 됐는가 |
| 우회 가능성 | 파일이 존재하기만 하면 통과 (내용이 부실해도 통과는 함 — 073일차 자체도 인정한 한계) | **adb 명령을 실행했다고 해서, 사람이 실제로 화면을 보고 확인했다는 보장은 없다** |
| 예: 거짓 안심 사례 | 테스트 파일은 있지만 assert가 허술함 | `adb install`만 실행하고 화면은 한 번도 안 봄 — 그래도 훅은 통과시킴 |

**핵심 통찰:** "명령이 실행됐다"는 "검증이 실제로 일어났다"의 **필요조건이지 충분조건이 아니다.** 073일차의 "테스트 파일 존재"는 최소한 "누군가 검증 코드를 작성하려는 시도는 했다"는 걸 보장하지만, 087일차의 "adb 명령 실행"은 **명령을 돌렸다는 사실만 보장할 뿐, 그 결과를 사람이 실제로 확인했는지는 전혀 보장하지 못한다.**

> 이건 정직하게 밝혀야 할 한계다: 이 훅은 "아예 검증을 건너뛰는 것"은 막아주지만, "형식적으로만 adb를 돌리고 결과를 안 본 것"까지는 막지 못한다.

## 아직 확인 못 한 것 — 다음 세션의 몫

시뮬레이션으로 판정 로직 자체는 검증했지만, **진짜 세션이 자연스럽게 끝나는 순간에 이 훅이 자동으로 트리거되는지**는 이번 세션 안에서 확인할 수 없다. 070/071일차와 같은 구조적 제약 — 새로 등록한 확장 요소는 다음 세션부터 유효하다.

## 070~087을 관통하는 패턴 — 재사용이 "겉모습 복붙"이 아니라는 것을 다시 확인

083일차(KOFIC 재사용성), 085일차(judge 재사용성)에 이어, 오늘도 같은 구조의 결론이 나왔다: **스캐폴딩(훅 등록 방식, 무한루프 방지, 판정 스크립트 구조)은 그대로 재사용됐지만, "무엇을 판정 근거로 삼을 것인가"는 도메인마다 다시 설계해야 하고, 그 근거의 신뢰도 수준도 다를 수 있다.**

073일차는 "존재"라는 강한 증거를, 087일차는 "실행"이라는 약한 증거를 썼다는 걸 명확히 인지하고 있는 것 자체가, 이 훅을 맹신하지 않고 계속 개선할 지점을 아는 것이다.

## 오늘 배운 것 — 한 줄 정리

1. Stop Hook을 재사용할 때 **"판정 스크립트 구조"와 "판정 근거의 신뢰도"는 분리해서 평가**해야 한다.
2. **"명령을 실행했다"는 "검증이 실제로 일어났다"의 필요조건일 뿐 충분조건이 아니다** — 형식적 실행과 실질적 확인은 다르다.
3. 새로 등록한 훅은 **현재 세션에서 자동 발동하지 않는다** — 071일차 방식(가짜 페이로드 시뮬레이션)으로 당일 안에 미리 검증할 수 있다.
4. 좋은 문서화는 "이 안전장치가 무엇을 막고, 무엇은 못 막는지"를 정직하게 함께 적어두는 것이다.
