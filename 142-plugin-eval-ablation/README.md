## 목적

사용자가 "142일차는 뭘 하면 좋을지, Claude 기능 중 남은 것이 뭔지" 물었고, 후보를 낸 뒤 A를 골랐다.

1. **A를 고른 이유**: 새 기능을 처음 써 보는 것이 목적이었고, 평가 대상(스킬)과 정답(과거 판정)이 이미 저장소에 있어 "새로 만들 것"이 케이스와 채점기뿐이라 하루 안에 끝낼 수 있다고 봤다. 이 판단은 일부만 맞았다. 정답을 과거 README에서 옮기는 과정에서 과거 기록과 어긋난 곳 5건(N2~N6)을 만났고, 정답이 "우리가 예전에 적은 판정"이라는 한계가 생겼다.
2. **무엇을 평가하나**: `material3-design-validator`(Material 3 디자인 검증 스킬)가 있는 팔과 없는 팔이 같은 프롬프트에서 같은 코드를 읽고 같은 형식의 답(`LINES=<줄 번호들|none>`)을 낼 때 점수가 다른가.

**알고 싶었던 것**
- `claude plugin eval`을 어떻게 구성하고 돌리는가(문서 확인, 시범 1회).
- 같은 프롬프트에서 스킬 있음·없음의 점수 차이(Δ)가 얼마인가.
- 스킬이 실제로 호출되는가(발동률), 무관한 케이스에서 호출되지 않는가.
- 비용과 시간(예측: $1.0~$8.0, 15~60분)이 맞는가.

**하지 않은 것**: 스킬 본문 수정, 모델 비교, 케이스 추가 반복, 앱 코드 수정, 결과를 근거로 한 스킬 개선. 대상 스킬 1개·케이스 7개·본 실행 1회라 결과는 "이 스킬이 좋다/나쁘다"가 아니라 "이 조건에서 한 번 잰 값과 이 평가 방식의 한계"다.

## 개념 정리 (나중에 다시 볼 것)

**1. `claude plugin eval`이 하는 일**: 플러그인 안의 `evals/<케이스>/prompt.md`와 `graders/*.md`를 읽어 케이스마다 격리된 새 비대화형 세션에서 프롬프트를 돌리고 채점기로 점수를 낸다. 격리 세션에는 사용자 스킬·`CLAUDE.md`·훅·메모리가 없고 작업 공간이 비어 있으며 도구는 기본 읽기 전용이다(`--allow-tools`로 열 수 있다). 기본 반복은 케이스당 3회다.

**2. ablation(`--ablation none|with-without`)**: `with-without`는 같은 프롬프트를 스킬 있음(WITH)과 없음(W/OUT) 두 팔로 돌리고 Δ(= WITH − W/OUT)를 표로 보여 준다. 스킬 호출을 보는 `tool_used`(Skill) 채점기는 두 팔 비교에서 `scored:false`로 점수에서 제외하고 보고만 한다.

**3. 채점기 종류**: `regex`·`tool_used`·`tool_order`·`file_exists`는 호출 비용이 0이고 `llm`·`baseline`은 판정 모델을 호출한다. `target: trace`를 쓰면 도구 호출 기록에 정규식을 걸 수 있다. `tool_used`의 `tool`은 이름 하나만 받아 "Read 또는 Grep"을 쓸 수 없다.

**4. 비용·종료 코드**: `--max-cost-usd`는 목록 가격 기준 추정이고 run을 시작하기 전에 확인한다(넘으면 종료 코드 2로 부분 결과). `--threshold`(기본 1.0) 아래 케이스가 하나라도 있으면 종료 코드 1이다. `--json`은 조용한 실행이라 표가 나오지 않는다(N1). 결과는 `<evals 폴더>/results/<타임스탬프>/aggregate-result.json`과 `report.html`이다.

**5. 도구 쪽 메모**: 비 TTY(스크립트·파이프)에서는 `--trust-plugin`이 필요하다. `--disallow-tools`는 `--help`에는 있지만 문서에 없다. 도구는 run마다 시스템 임시 폴더(`/tmp`)에 작업 디렉터리를 만들었다가 지운다(`--keep-temp`가 있으면 남는다).

**6. 천장 효과**: 케이스가 너무 쉬우면 두 팔이 모두 만점이라 Δ가 0이 되고, 이것이 "스킬이 쓸모없다"를 뜻하지 않는다. 차이를 보려면 스킬 없는 팔이 틀릴 만한 어려운 케이스가 필요하다. 이번에는 B2 한 케이스에서만 스킬 없는 팔이 0.50이 나왔다.

**7. 스킬은 모델이 스스로 부르는 도구다**: with 팔이라도 스킬이 호출되지 않으면 그 run은 사실상 "스킬 없음"과 같다. 그래서 Δ를 해석하려면 발동률(여기서는 3/15)을 같이 봐야 한다. 이 결과는 스킬 설명(`description`) 쪽 문제일 수도, 질문이 스킬을 부를 만큼 어렵지 않았던 것일 수도 있다(구분되지 않음).

**8. 작은 표본의 구간·검정**: 3/15의 95% Clopper-Pearson은 4.3~48.1%다. 3 run 대 3 run의 Fisher 정확검정은 가능한 p값이 거칠어(3/3 대 1/3이면 양측 0.4) 어떤 결과도 "유의"하기 어렵다.

**9. 사전 고정(pre-registration)**: 예측 파일을 해시로 고정하고 읽기 전용으로 만든 뒤 실행하면 사후 합리화를 막을 수 있다. 고정 뒤 바꾸는 것은 재정의로 기록한다. 이번에는 고정 뒤 변경이 없었지만 P5의 근거 숫자가 파일이 아니라 채팅에 있었다는 점이 빈틈이었다(C4).

**10. 스쿼시 병합과 `-D`**: 스쿼시로 병합한 PR의 브랜치는 `git branch -d`가 "not fully merged"로 실패하고 `-D`가 필요하다. 안전 확인은 "브랜치 트리 == `main` 트리"로 한다. `--match-head-commit`은 머리 커밋이 바뀌었으면 병합을 거부하는 안전장치다.
