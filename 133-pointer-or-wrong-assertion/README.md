## 목적

132일차에 문서가 틀리면 에이전트가 틀리는지를 쟀더니, 도구를 쓰는 에이전트는 낡은 숫자를 grep으로 스스로 바로잡았고(포화 12/12), 틀린 곳은 문서에 "OS 층(`network_security_config.xml`)을 봐야 한다"는 포인터가 없던 질문(Q2·Q3)뿐이었다. 그런데 132일차의 FIX는 숫자 정정과 포인터 추가를 한 번에 했기 때문에 **무엇이 원인인지** 가르지 못했다. 그래서 오늘은 하나만 묻는다.

> **오도의 원인은 "숫자가 낡음"인가, "포인터가 빠짐"인가?**

원칙은 이전과 같다.
- **읽기 → 설계 → 롤백 조건 합의 → 실행** 순서. 숫자·날짜 기준이나 롤백 조건이 걸리면 해석하지 않고 멈추고 묻는다. 재정의는 이유를 적고 승인 후에만 한다.
- 질문·정답·채점기·하네스·조건·예측은 **해시로 사전 등록**하고 이후 바꾸지 않는다. 파일럿이 포화이면 본 실행 전에 멈추고 보고한다. 파일럿 데이터는 본 통계에서 뺀다.
- 평가는 `claude -p`에서 `--setting-sources project,local`로 전역 훅·전역 지침을 격리한다.
- 저장소 변경(push·PR·merge)은 diff를 보여 주고 승인을 받는다. 일차 요약은 `CLAUDE.md`가 아니라 `DEVLOG.md`에만 쓴다.
- 핀 값은 앞 8자만, 요청 URL·키는 출력하지 않고, 기기 설정은 건드리지 않고, 시스템 `/tmp`는 쓰지 않고, 삭제는 리터럴 경로로 허락 후에만 한다.

### 포인터의 정의와 줄 단위 분리
**정의**: 포인터는 "확인하러 열어야 할 파일·문서 절·설정 요소·그것에 묶인 층 이름을 가리키는 구절"이고, 개수·버전·상태·동작은 **단언하지 않는다**. 단언이 들어가면 포인터가 아니라 사실이다. 그래서 줄을 **P(포인터) / N(숫자·이름) / S(상태·동작 단언)**로 나눴다.

OLD → FIX에서 새로 생긴 백틱 토큰을 기계적으로 뽑으면 파일형 토큰은 `network_security_config.xml`(`:308`, `:314`), `NETWORK_SECURITY_REPORT.md`(`:309`, `:315`), 테스트 글롭 4개(`:163`), 번들 이름(`:333`)이고 NSC 요소명은 `pin-set`·`debug-overrides`(`:308`)다. **OLD에는 `network_security_config`가 0번 나온다.**

| 줄 | P(포인터) | N(숫자·이름) | S(상태·동작 단언) |
|---|---|---|---|
| :62 :80 :111 :255 :256 :265 :394 | 없음 | 개수·버전·나열 | 없음(`:255`는 "2.4.x 미시험") |
| :94 | `@ImageOkHttpClient`(`:75`에 이미 있음) | 채널 3개 | "핀 적용" |
| :142 | "아래 Certificate Pinning 참고" | api 2·image 5 | "리프 핀 없음" |
| :163 | 글롭 4개 | 9/21/27/3 | 없음 |
| :307 | 상수 이름 나열 | 7개 | 없음 |
| **:308** | `network_security_config.xml`·`pin-set`·`debug-overrides`·"OS 층" | 없음 | "디버그에도 적용", "앱 층은 만료 없음" |
| **:309** | `NETWORK_SECURITY_REPORT.md` 절 | 없음 | "image는 체인 전체를 핀" |
| **:314** | NSC·`NetworkModule.kt`·"OS/앱 층" | 없음 | "핀 집합이 같아야 정상", "리프는 핀하지 않음" |

| :333 | 번들 이름 | 9개 | 없음 |

- 실질적인 OS 층 포인터는 **`:308`·`:309`·`:314`·`:315` 네 줄**에 몰려 있다. 문제는 **한 문장에 P와 S가 섞여 있다**는 점이다. 특히 `:308`은 "디버그에도 적용"(S)과 파일명(P)이 같이 있다. 그래서 FIX-P를 만들면 S를 파일 이름 없이 남기게 되는데(예: "디버그에서도 핀이 적용되는 층이 있다"), 이때 "다른 층이 있다"는 **존재 암시**가 누수로 남는다.
- OLD+P는 OLD의 낡은 `:308`("디버그에서는 핀 비활성화")을 그대로 둔 채 포인터만 넣게 되므로 포인터와 모순이 생긴다. 포인터를 따라 NSC XML을 열어도 `:44` 주석이 같은 오해를 주기 때문에 **Q3는 오히려 오답이 유지될 수 있다**는 예측을 미리 적어 두었다(P1).

## 확인한 것 / 확인하지 못한 것 / 한계

**확인한 것**: 위 등급 표 참조.

**확인하지 못한 것**
- **2×2의 포인터 효과·숫자 효과**(H1·H2·H3): 본 실행이 없어 측정하지 못했다.
- "틀린 단언이 오도의 원인"의 **인과**: 오답이 단언 질문에서만 났다는 관찰뿐이고, 같은 사실을 틀린 단언(W)·문장 없음(S)·맞는 단언(R)으로 비교한 적은 없다.
- 일반화 팔(위젯·proguard·stdlib)의 포인터 효과: OLD가 이미 전부 맞혀 측정 불가.
- FIX-P2(존재 암시 제거)가 필요한지.
- 실제 문서에서 틀린 단언이 얼마나 자주 생기는가.
- **`cert-pin-check` 첫 정기 실행 결과**(아직 안 돌았음).
- 파일럿 단가가 설계 가정보다 높았던 정확한 원인(캐시 적중 차이 추정).

**한계**
- 파일럿 표본이 질문당 n=1~2라 오답 분포는 어떤 통계 비교도 못 한다(방향성 증거 이하).
- 앵커 Q2·Q3은 132일차에 OLD 오답을 본 뒤 민감 질문으로 골라서 **선정 효과**가 있고, 질문 자체가 낡은 줄을 겨냥해 만들어졌다.
- 새 질문 N1~N8은 내가 설계했고, 포인터가 없는 층의 질문이라 grep으로 쉽게 찾아져 **양성 대조 구실을 못 했다**.
- 설계상 FIX-P에는 존재 암시가 남아 있고 OLD+P는 "선언 위치"라는 구조 사실을 포함해 순수 포인터 효과가 아니다.
- 결과는 **Sonnet 5.5 + 읽기 전용 도구 + 1회 질문**에 한정되고, 도구 없음(M0)은 이번에 하지 않았다.
- 채점기는 정규식이라 의미가 맞아도 형식이 다르면 오답으로 센다.

## 오늘 배운 것 — 한 줄 정리

1. **포화는 "필요 없다"와 "질문이 너무 쉬웠다"를 구분해 주지 않는다.** 에이전트가 grep으로 층을 찾아내면 포인터 유무가 정답률에 드러나지 않는다. 양성 대조(R5)가 이 설계를 지킨 안전장치였다.
2. **오도는 침묵이 아니라 정반대 단언에서 나왔다(가설).** 같은 층을 가리키지 않는 문서라도 에이전트는 grep으로 찾아가고, 문서가 정반대로 단언할 때만 거기에 끌려 갔다. 포인터가 있어도 틀린 단언이 남으면 오답이 유지됐다(OLD+P Q3 0/1).
3. **문서 점검의 우선순위는 "빠진 곳 채우기"가 아니라 "틀린 단언 찾기"일 수 있다.** 132일차의 숫자 정정(포화)은 큰 이득이 없었고, 이득은 오도하는 단언 한 줄(`:308`)에서 나왔다. 다만 단언이 실제 문서에서 얼마나 자주 생기는지는 모른다.
4. **새 질문을 설계할 때는 "이 질문이 OLD를 틀리게 만들 수 있는가"를 승인 전에 점검한다.** 132일차 오답 질문의 공통점(문서가 단언한다)을 가져야 양성 대조가 성립한다.
5. **롤백 규칙(R12·R14)이 실제로 쓸모가 있었다.** 포화를 보고 본 실행을 멈춰 약 $7~10(본 실행 예상)을 쓰지 않았고, 비용 중단선이 걸렸을 때도 해석하지 않고 멈추고 물었다.
6. **비용 어림은 직전 실험의 캐시 유리한 단가가 아니라 같은 구조의 실측으로 한다.** 접두가 다른 조건을 섞으면 캐시 적중이 줄어든다.
7. **"삭제 금지"만으로는 자료가 보존되지 않는다.** `scratchpad` 128~130이 일일 정리로 보이는 동작에 사라졌다. 요약은 저장소(DEVLOG)에 두고 원자료는 저장소 밖 보존 폴더에 따로 복사해야 한다.
8. **사전 등록 예측은 빗나간 것까지 같은 표에 둔다.** 12개 중 6개가 적중이고, 빗나간 P12(새 질문에서 OLD 오답)가 이번 결론 자체를 정했다.
