# 122 - 최근 검색어 목록이 비어 보이는 현상 — DB가 아니라 UI 어댑터가 오래된 목록을 들고 있었다

**121일차에 원인 미조사로 남겨둔 "최근 검색어가 잠깐 비어 보이는 현상"을 실기기에서 재현해 원인을 찾았다. DB와 Flow는 모든 측정에서 정확했고, 문제는 Fragment가 어댑터와 영역 상태를 동기화하는 방식이었다. 수정 중 롤백 조건에 걸렸을 때 조건을 완화하지 않고 보완 후 재검증했다**

---

## 목적

121일차 실기기 검증 중 최근 검색어 목록이 잠깐 비어 보이는 현상을 봤는데, 원인을 조사하지 않고 넘어갔다. 같은 세션의 "OkHttp 로그 0줄" 현상도 원인 미조사 상태였다. 두 현상이 관련 있는지는 모르는 상태였기 때문에, 관련 있다고 가정하지 않고 각각 조사하기로 했다.

처음부터 정한 원칙은 세 가지였다.
- 수정 전에 먼저 재현하고, 증상과 원인을 분리해서 본다.
- "재현 안 됨 / 코드 변경 없음"도 정직한 결론이다.
- 확인하지 못한 것은 확인하지 않았다고 쓴다.

## 작업 2 — 실기기 재현 (SM-S926N)

시도한 조건은 콜드 스타트 후 검색 탭, 탭 전환 후 복귀(1초·7초), 프로세스 복원(`am kill`), 화면 회전, 검색어 추가 직후, X로 지우기(제출 후/제출 없이), 항목 삭제(검색어가 빈 상태/필터된 목록), 포함 검색어, 장르 선택이다.

### 수정 전 재현 수치

조건이 충족되면 매번 나오는 결정적 버그였다.

| 시나리오 | 결과 |
|---|---|
| 제출 → X | **5/5 오류**. 탭 왕복 후 5/5 복구 |
| 포함 검색어 제출 → X | **3/3** 부분 목록 |
| 필터 목록 마지막 행 삭제 | **5/5** 제목만 남음 |
| 정상: 제출 없이 X(키보드 숨김), 빈 검색어에서 삭제, 콜드 스타트 5, 탭 왕복 10, 프로세스 복원 5 | 전부 정상 |

핵심은 **DB 행 수와 Flow가 모든 측정에서 정확했다**는 점이다. "목록이 비어 보이는" 증상이었지만 데이터가 비어 있던 게 아니라, 화면 쪽이 오래된 상태를 들고 있었다.

### 가로 모드는 같은 버그가 아니었다

세로→가로→세로 회전을 5회 해봤고, 가로 모드는 5/5로 제목만 보였다. 이건 어댑터 문제가 아니라 레이아웃 문제였다. `recent_searches_section` 높이가 173px에 제목 줄만 들어가고 `rv_recent_searches` 높이가 0이었다. 이번 수정 범위에서 제외하고 별도 건으로 남겼다.

### 두 현상은 서로 다른 원인이었다

OkHttp 로그가 0줄이었던 현상의 원인은 `monkey -c LAUNCHER`가 LeakCanary의 `LeakLauncherActivity`를 무작위로 띄운 것이었다. 이 액티비티는 설치된 패키지에서 MAIN+LAUNCHER 필터를 가져서 monkey가 앱 대신 이걸 실행할 수 있다.

- monkey 16회 중 4회가 0줄이었다.
- 직접 실행한 10회 중 LeakCanary가 열린 2회가 정확히 0줄이었고, 나머지 8회는 129~143줄이었다.
- 위 4건 중 1건은 로그 줄 수로만 추정했다.
- `am start -n`은 6/6 정상이었다.

최근 검색어 버그는 `am start` 실행에서도 재현됐다. 그래서 둘은 서로 다른 원인이다. 121일차에 "원인 미조사"로 남겼을 때 둘이 같을 수도 있다고 가정하지 않은 게 맞았다.

## 작업 3 — 판정

**(다) 실제 버그.** 층위는 UI(Fragment의 어댑터와 영역 동기화)다. 이 판정을 보고받은 뒤 수정하기로 확인하고, A안(순수 함수 + 두 호출부 공유)으로 진행했다.

다른 안은 이랬다.
- B안: 필터링을 ViewModel의 `combine(recentSearches, searchQuery)`로 옮기기. 구조는 깔끔하지만 Fragment의 `searchQueryState` 의존을 건드려서 범위가 커진다.
- C안: 검색어 기반 필터 기능을 제거하기. 제품 동작이 바뀌어서 비추천.

설계 승인 단계의 결정 3개는 모두 권장안으로 확정했다.

| 결정 | 선택 | 이유 |
|---|---|---|
| 반환 타입 | sealed interface (Recent/Initial/KeepVisibility/Filtered/Hidden 5개 변형) | `when`에서 빠진 분기를 컴파일러가 잡아준다 |
| 장르 선택 중 검색어가 blank | 어댑터를 전체 목록으로 다시 채운다 | "blank면 어댑터는 전체 목록"이라는 불변식이 모든 경로에서 성립한다 |
| 배우 모드 가드 | 이번 PR에 넣지 않는다 | 재현되지 않았고 요청 범위가 현재 동작 보존이다 |

가로 모드 레이아웃은 같이 넣으면 원인이 섞여서 롤백 판단이 어려워지므로 별도 건으로 분리했다.

## 작업 5 — 롤백 조건에 걸렸을 때

구현 전에 합의한 롤백 조건 4개가 있었다. 첫 수정 빌드를 실기기에서 돌렸더니 조건 1("재현 시나리오가 한 번이라도 오류면 실패")에 문자 그대로 걸렸다.

| 시나리오 | 수정 전 | 중간 빌드 |
|---|---|---|
| E1 제출 → X | 0/5 | 5/5 |
| E4b 필터 목록 마지막 행 삭제 | 0/5 | 5/5 |
| E3 포함 검색어 제출 → X | 0/3 | **1/3** |
| E5 실제 검색어 5개 | 0/5 | **3/5** |

원래 증상(목록이 비어 보임)은 해소됐지만, 다른 증상이 남았다. 목록 내용은 완전한데, 방금 제출한 최신 검색어가 위쪽에 가려져서 위로 한 번 스와이프해야 나타났다. 원인은 필터본에서 전체본으로 바뀔 때 RecyclerView가 기존 첫 항목에 스크롤을 고정하는 것으로 **추정**했다(코드 수준으로 확인하지 않은 추정이다).

여기서 Claude Code는 조건을 임의로 완화하지 않았다. 선택지(스크롤 복귀 추가 후 재검증 / 한계로 기록하고 PR / 전부 롤백)를 사용자에게 보여줬고, 조건을 그대로 둔 채 보완 후 전체 스위트를 다시 도는 쪽을 골랐다.

### 보완하다가 만든 새 결함 2건

스크롤 리셋을 "호출 경로"에서 결정했더니 기기에서 새 결함이 두 개 나왔다.
- 스크롤해 둔 채 백그라운드로 갔다 복귀할 때마다 리셋됐다 (0/3).
- 이미 blank인 상태에서 공백을 입력해도 리셋됐다 (0/3).

둘 다 **non-blank → blank 전이에서만 플래그를 세우고, 모든 제출의 콜백이 그 플래그를 소비하는** 방식으로 고쳤다. 이 두 결함은 Fragment 연결부의 동작이라 단위 테스트로는 잡히지 않았고, 개발 중 기기에서만 드러났다.

## 오늘 배운 것 — 한 줄 정리

1. "목록이 비어 보인다"고 해서 데이터가 비어 있는 건 아니었다 — DB 행 수와 Flow를 먼저 재면 원인 층위가 갈린다.
2. 겉으로 비슷한 두 현상(검색어 버그와 로그 0줄)은 서로 다른 원인이었다 — 같은 원인이라고 가정하지 않고 실행 방식(`am start` vs `monkey`)으로 분리해서 확인했다.
3. 롤백 조건이 문자 그대로 걸리면 완화하지 않는다 — 선택지를 드리고, 보완한 뒤 같은 스위트를 처음부터 다시 돈다.
4. 고치는 과정에서 새 결함이 나올 수 있다 — 스크롤 보완이 만든 회귀 2건은 단위 테스트가 아니라 개발 중 실기기에서만 드러났다.
5. 단위 테스트로 RED를 못 만드는 부분은 기기 수치로 대신하되, 그 한계를 문서에 쓴다.
6. "0건"이라는 검사 결과는 양성 대조 없이는 믿지 않는다 — zsh 변수 분리 버그가 가짜 0건을 만들었고, 121일차의 "마스킹된 줄 ≥1 + 안 된 줄 0"과 같은 원리다.
7. 변이 테스트의 높은 검출률은 변이 목록을 미리 알고 설계했다는 점을 같이 적어야 정직하다.
