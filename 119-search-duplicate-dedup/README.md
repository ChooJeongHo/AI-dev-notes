# 119 - 즉시 검색/debounce 중복 호출 제거 — 095~118 사이클을 닫는 마지막 조각

**118일차에서 "이번 변경 이전부터 있던 동작"으로 미뤄둔 중복 검색 문제를 고쳤다. 원인은 merge 두 경로 중 한쪽에만 distinctUntilChanged가 걸려 있던 것이었고, 변이 테스트 결과가 예측과 정확히 일치했다**

---

## 목적

118일차에서 미수정으로 남긴 두 가지 중 하나, **"즉시 검색과 debounce가 같은 검색을 두 번 내는" 문제**를 수정한다.

---

## 작업 1~2 — 원인과 설계

### 원인

`merge(debounce 경로.distinctUntilChanged(), _immediateSearch)`에서 **`distinctUntilChanged`가 한쪽 가지에만** 있었다. 두 경로가 같은 조건을 내보내면 새 Pager가 두 번 만들어졌다.

### 겹치는 경우 (전부 확인)

칩 클릭, 300ms 안의 엔터, 자동 검색이 뜬 뒤 엔터, 장르 다이얼로그 확인(검색어 없음), 끝 공백 쿼리.

### 추가 발견

타이핑 경로는 trim하지 않아서 **`dune%20` 같은 쿼리가 그대로 TMDB로 나가고 있었다** — 중복 문제를 조사하다가 우연히 발견한 별개의 버그였다.

### 설계: distinctUntilChanged를 merge 뒤로 이동 + trim 추가

같은 조건으로 검색한 뒤의 엔터는 **무시**하도록 했다. 대안이었던 "대기 중 debounce 취소"는 **자동 검색이 이미 뜬 뒤의 엔터를 못 막아서** 제외했다.

## 작업 5 — 실기기 검증 (SM-S926N)

| 시나리오 | 전 | 후 |
|---|---|---|
| 자동 검색 후 엔터 | 2 (4.0초 간격) | 1 |
| 최근 검색어 칩 클릭 | 2 (301ms) | 1 |
| 타이핑 직후 엔터 | 2 (266ms) | 1 |
| 끝 공백 + 엔터 | 2 (`dune%20`, `dune`) | **1 (`dune`)** |
| 장르 확인(검색어 없음) | 2 (308ms) | 1 |
| 타이핑만 | 1 | 1 |

수정 후에도 자동 검색, 타이핑 직후 엔터, 자동 검색 뒤 엔터 모두 결과가 정상으로 표시됨을 스크린샷으로 확인했다. 이 측정은 등급 필터를 "전체"로 둔 상태이며, KMRB 필터를 켰을 때 호출이 줄어든다는 건 구조상의 추론이고 직접 재지는 않았다.

### 검증 중 발생한 잔여물

마지막 정리 중 adb 연결이 끊겨서, 테스트용 최근 검색어 4개(avatar, dune, titanic, gladiator)가 기기에 남았다. `joker`는 삭제했고 장르 칩도 되돌렸다.

### 별개 관찰 (원인 미조사)

입력창 X로 지운 직후나 최근 검색어를 삭제한 직후에 "최근 검색어" 목록이 비어 보이다가, 탭을 갔다 오면 복구된다. **수정 전 빌드에서도 나왔던 현상**이라 이번 수정과 무관하며, 원인은 조사하지 않았다.

## 작업 6 — 095~118일차 사이클에서의 의미

### 같은 주제의 네 번째 변주

- **082일차**: N+1을 스냅샷 1회 조회로 해결
- **115일차**: 필터 안의 항목당 추가 호출을 지연 조회로 해결
- **117일차**: 필터 위치를 `cachedIn` 앞으로 옮겨 해결
- **119일차**: 파이프라인 **입구**에서 같은 검색이 두 번 들어오는 것 자체를 막음

### 117일차 구조와 직접 연결됨

117일차에서 "등급이 바뀌면 재검색(새 Pager)"을 택했기 때문에, 재검색 하나가 **KMRB 필터 재시작까지 끌고 와서 비싸졌다.** 그만큼 **불필요한 Pager 생성을 막는 오늘의 가치가 더 커진 셈**이다 — 117일차의 설계 선택이 119일차 수정의 중요도를 높인 사례다.

### 풀지 못한 것

KMRB 장애나 429 중에 등급 칩을 고르면 전 페이지를 연쇄 조회하는 문제와, 연쇄 상한 부재는 **이번 수정과 무관하게 그대로 남아있다.**

### 방법론 — 095~118일차 전체를 관통한 원칙의 재확인

추정으로 끝내지 않고 **수정 전 코드에서 먼저 재현한 뒤 고쳤고**, 변이 테스트와 실기기 전후 비교로 닫았다. 이건 095~118일차 내내(082, 099, 110, 111, 113, 116, 117, 118일차 등) 반복된 "짐작하지 말고 직접 확인한다"는 원칙이 사이클 마지막 날까지 일관되게 적용된 사례다.

## 오늘 배운 것 — 한 줄 정리

1. `merge()`로 합친 여러 경로 중 **한쪽에만 중복 제거를 걸면 의미가 없다** — 합류 지점 이후에 걸어야 모든 경로가 커버된다.
2. 원인을 조사하다가 **별개의 버그(trim 누락)를 우연히 발견**할 수 있다 — 발견하면 같은 작업 범위에서 같이 처리하는 게 자연스럽다.
3. 변이 테스트에서 "제거했을 때 실패하는 테스트 집합"이 **예측과 정확히 일치**하면, 그 테스트가 정말로 해당 제약을 검증하고 있다는 확실한 증거가 된다.
4. 이전 날의 설계 선택(117일차의 "재검색" 방식)이 **다른 날 수정의 가치를 더 키울 수 있다** — 날짜별 작업은 서로 독립적이지 않고 연쇄적으로 영향을 준다.
5. 검증 중 발견한 무관한 현상(최근 검색어 깜빡임)은 **원인 조사 없이 그대로 기록만 남기고 범위를 지키는 것**이 맞는 판단이다.
