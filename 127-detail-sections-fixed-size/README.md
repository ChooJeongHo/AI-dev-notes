## 목적

126일차는 상세 화면의 메모 목록(`rvMemos`) 하나가 `setHasFixedSize(true)` + `wrap_content` 때문에 저장 직후 안 그려지는 문제를 한 줄 삭제로 고쳤다. 그때 같은 패턴이 상세 화면에 두 곳 더 있다는 것을 알았지만 "문제가 되는지 확인 안 함"으로 남겼다. 오늘은 그 두 곳을 **읽기 → 재현 → 방안 비교 → 롤백 조건 합의 → 구현 → 기기 검증** 순서로 다뤘다.

원칙은 이전과 같다.
- 수정 전에 먼저 읽고 재현한다. 증상과 원인을 분리한다.
- "확정"과 "강하게 시사"를 구분해서 쓴다. 직접 보지 못한 것은 보지 못했다고 쓴다.
- 오늘은 상세 화면 목록 4개만 고친다. 다른 문제는 발견해도 기록만 한다.
- 롤백 조건은 구현 전에 합의하고, 걸리면 완화하지 않고 멈춰서 선택지를 받는다.
- 입력(탭·키)은 보내지 않고 딥링크와 읽기만 사용했다(사용자 폰 조작이 표본을 무효로 만든 126일차 교훈).

## 작업 2 — 재현 측정 (코드 수정 0, 실기기 SM-S926N, 같은 26편)

수정 전 기준선은 main `8c329aa`와 같은 소스, 설치 APK의 sha256 일치를 확인하고 쟀다. **수정 APK를 설치하기 전에 수정 전 값을 먼저 찍는다**는 순서를 R7·R9 때문에 지켰다.

| 조건 | 표본 | 수정 전 BUGSIG | 수정 후 SHOWN | t_content 중앙(범위) 전 → 후 |
|---|---|---|---|---|
| G1 콜드·캐시 미스 | 10 | 40/40 | 40/40 | 2.3초(2.2–2.5) → 2.4초(2.2–3.1) |
| G2 웜·캐시 미스 | 10 | 40/40 | 40/40 | 1.0초(0.9–1.0) → 1.0초(0.9–1.6) |
| G3 웜·캐시 적중 | 6 | 23/24 | 24/24 | 0.9초(0.9–1.0) → 1.0초(1.0–1.1) |
| **합계** | **26** | **103/104** | **104/104** | |

- **SHOWN의 정의**: 보임 · 높이 > 0 · 자식 ≥ 1. **BUGSIG**: 라벨이 VISIBLE인데 목록이 그려지지 않은 상태(높이 0).
- 라벨이 VISIBLE이라는 것은 `bindOptionalSection(hasItems=true)`가 실행됐다는 뜻이라, 모든 표본에서 4개 목록 모두 1개 이상의 항목이 있었다. 리뷰 개수는 높이가 0이라 자식이 안 만들어져 **수정 전에는 셀 수 없었고**, 수정 후 행 수는 2~20이었다.
- **수정 전 SHOWN 1건**은 G3의 영화 299534 `rv_recommendations`(891px, 자식 3개)였다. 같은 화면의 나머지 3개는 높이 0이었다. 타이밍이 우연히 맞은 경우로 본다.
- 처음 기준선(보고서 표기 "첫 장소 기준선")도 26건 VALID에 103/104로 같았다.
- **유효성**: 두 측정(수정 전/후) 모두 26건 전부 VALID(무효·미수행 0). 무효 표본 기준은 측정 전에 정했다(전면 앱이 우리 앱이 아님, `mRotation≠0`, 상세 미표시 25초, 오류 화면, 마지막 두 읽기 불일치).
- **불확실성**: 표본 기준으로 수정 전 26/26이면 발생률 95% 하한은 약 89%(rule of three), 수정 후 0/26이면 상한은 약 12%다.
- t_content는 콜드(G1)에서 수정 후 범위가 넓어졌지만(2.2–3.1초) 중앙은 2.3 → 2.4초로 비슷했다.

## 작업 3 — 원인 판정: 무엇이 "확정"이고 무엇이 "강하게 시사"인가

기준선 측정 때는 "강하게 시사"였고, 수정 후 측정과 소스 확인을 거쳐 "확정"으로 올렸다.

| 구분 | 내용 |
|---|---|
| **확정 (소스)** | `RecyclerView`(1.4.0)의 `triggerUpdateProcessor`는 `mHasFixedSize && mIsAttached`이면 `requestLayout` 없이 `postOnAnimation`만 한다. `AsyncListDiffer`는 `mList == null`일 때만 동기로 삽입하므로, 첫 `submitList(emptyList)` 뒤의 제출은 비동기로 처리된다. 그래서 `wrap_content` 목록의 높이가 0인 채로 남는다 |
| **확정 (전/후 격리)** | 같은 폰, 같은 26편에서 BUGSIG 103/104 → 0/104. 두 APK는 `classes17.dex`(−48B) 하나만 다르고 나머지 2,342개 항목의 CRC가 같다. 소스 diff는 호출 2줄과 주석뿐이다 |
| **확정 (라이브러리 회귀 아님)** | `RecyclerView` 1.4.0은 최초 커밋부터 쓰였다 |
| **강하게 시사 / 추정 (확정 아님)** | 점진적 로딩(4/4)과 고정 크기(4/25~26)가 **함께 들어간 뒤부터** 존재했다는 시점. 이분 탐색은 하지 않았다 |
| **미확인** | `classes17.dex` 내부 변경이 호출 2줄 삭제뿐인지는 디컴파일 비교를 하지 않았다 |

## 오늘 배운 것 — 한 줄 정리

1. **126일차에 "미검증"으로 남긴 같은 패턴이 이튿날 실제 결함으로 확인됐다.** 한 곳을 고칠 때 같은 조합이 어디에 더 있는지 목록에 적어 두면, 다음 날 바로 닫을 수 있다.
2. **증거는 이미 스크린샷에 있었다.** 125·126일차 스크린샷에 빈 섹션이 찍혀 있었는데 알아채지 못했다. 스크린샷은 "찍었다"가 아니라 "그 안에 보이는 것을 다 읽었다"까지 해야 증거다.
3. **양성 대조를 세 종류로 겹쳤다.** `rv_memos` 0px 상태 검출(26/26), 정상 목록 891px 자연 대조, 육안 스크린샷 4장. 그래서 수정 후 0건이 "도구가 못 봐서"가 아니라는 것을 말할 수 있다.
4. **성능 지표의 비율 하락은 분모를 먼저 본다.** R9의 Janky 9.5% → 3.0%는 프레임 수가 590 → 1,614로 늘어난 영향이라 "악화 없음"까지만 말했다.
5. **대조군(기대값)도 틀릴 수 있다.** 변형 철자 대조의 기대값 8이 실제로는 9였다(`setHasFixedSize(false)` 1줄). 기대값이 어긋나면 도구가 아니라 기대값부터 의심한다.
6. **고치면 이전에 못 가던 길이 열린다.** 높이 0이라 못 눌렀던 출연진→인물 이동이 이제 눌리는데, 오늘은 측정하지 않았다고 정직하게 적었다.
7. **문서 사실에는 시점이 있다.** #167이 10:13에 쓴 "7곳/6개 파일"은 그때 사실이었고, 수정이 머지된 뒤 낡아졌다. 코드 수정 뒤에는 그 수정으로 틀려지는 문서 문구를 grep으로 찾는 것까지가 작업이다.
8. **여유 값은 시점을 붙여야 한다.** `CLAUDE.md` 여유가 161B였던 시점과 22B였던 시점이 달랐다(사이의 +139B가 오전 문서 PR). "여유"만 말하면 틀린 정보가 된다.
9. **삭제하기 전에 필요한 숫자를 확보한다.** 측정 원자료를 지운 뒤에는 grep으로 다시 셀 수 없어서 문서에 수치를 못 쓰고 PR을 가리켰다. 이번엔 보고서에 값이 있어서 문제없었지만 순서의 문제다.
10. **원래 있던 문제와 내가 만든 회귀를 구분한다.** 회색 포스터는 YR1 핀 불일치로 수정 전 APK에서도 2,866줄이었고, #168은 `di/`를 0줄 바꿨다. 이 근거 세 가지가 "오늘 멈추지 않고 후속 후보로 기록"이라는 결정을 지탱했다.
11. **롤백 조건은 이틀 연속 걸린 것이 없었다.** 126일차 R1~R8, 127일차 R1~R9가 모두 통과했다. 변경이 작았기 때문일 수 있고, 두 번의 무사통과를 방식의 성공으로 단정하지 않는다.
