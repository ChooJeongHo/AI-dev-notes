**141일차 `/code-review` 지적 중 F1(복원이 `watch_history_genre` 행을 만들지 않는다)을 이번에는 실제로 고쳤고, F3·F5는 145일차 방식으로 실행해 확인했다.** F1은 `BackupRepositoryImpl.kt` 한 곳(+13/−1)에서 `insertAll`이 돌려주는 rowId로 장르 행을 만들게 했다(평소 저장 경로 `saveWatchHistoryWithGenres`와 같은 쉼표 분리·공백 제거 규칙, rowId가 −1인 행은 건너뜀). 새 회귀 테스트 `BackupRestoreGenreTest`(`androidTest`, 메서드 2개, N=3, 장르 토큰 6개)는 에뮬레이터에서 **수정 전 1개 실패(`expected:<6> but was:<0>`), 수정 후 2개 모두 통과**했고, 복원 1회 후 장르 행은 0→6, 장르별 개수는 `Action:3;Adventure:2;Drama:1`이 됐다. ## 한계

1. 설정 화면에서 파일을 골라 가져오는 UI 경로는 실행하지 않았다(테스트는 `importUserData`를 직접 호출). PR 코멘트에는 있고 DEVLOG에는 없다.
2. `rowId == -1`을 건너뛰는 분기는 어떤 테스트도 지나가지 않았다(rowId가 0으로 들어가고 유니크 제약이 없어 코드상 충돌 조건이 없다).
3. CI는 `androidTest`를 실행하지 않는다. 로컬 `lintDebug`·`testDebugUnitTest`는 `androidTest`를 컴파일하지 않았고, CI의 다른 빌드 태스크 목록은 확인하지 않았다. 회귀 테스트 결과는 에뮬레이터 1대의 로컬 실행(A·B 각 1회)이다.
4. `detekt`는 `src/main`과 `src/test`만 검사한다(새 테스트 파일은 검사 대상 밖).
5. 같은 백업을 빈 DB에 2회 가져오면 장르 행이 수정 전 0, 수정 후 12다.
6. **기존 기록 위에 자기 백업을 가져오는 경우는 측정하지 않았다.** 수정 후 장르 통계도 늘어난다는 것은 코드를 읽은 추론이다.
7. 에뮬레이터 1대(API 36), N=3, 실행 A·B 각 1회다.
8. F5a의 원본 연-월은 평소 저장 경로로 만든 값이 아니라 테스트가 직접 넣은 값이다. F3는 INSERT 실행 횟수만 봤고 성능은 재지 않았다. F4의 실행 시간은 재지 않았다.
9. 예측은 코드를 읽은 뒤에 세웠고 4개는 비독립이다. P8·P9가 불성립한 원인은 재지 않았다.
10. pre-push 훅은 `--quiet`라 태스크가 실제로 다시 실행됐는지는 알 수 없다.
11. 자동 리뷰 코멘트 본문이 `null`인 원인과 이전 PR에서도 그랬는지는 확인하지 않았다.
12. DEVLOG의 이탈 건수는 커밋 시점 값이다.
13. 첫 adb 명령 전에 서버 데몬이 이미 있었는지, 컴퓨터가 얼마나 잠자기였는지는 재지 않았다.
14. "재현됨"은 고정 기준의 적용 결과이며 결함 판정이 아니다.

## 오늘 배운 것

- **수정 전 실패·수정 후 통과로 테스트가 변경을 구분했다.** 같은 N=3 데이터에서 A는 `expected:<6> but was:<0>`로 실패하고 B는 통과했다. 145일차의 측정이 정식 회귀 테스트로 이어졌다.
- **한 곳을 고치면 인접 동작의 영향 범위가 바뀐다.** F1 수정으로 복원 장르 행이 생기자 F2(중복 가져오기)의 영향이 장르 통계까지 번졌다(2회 후 장르 행 0→12). F2 값을 단언 없이 출력만 하도록 둔 덕에 이 변화가 같은 실행에서 잡혔다. 단언을 걸었다면 오히려 미수정 동작을 고정했을 것이다.
- **연결 확인 단언은 개수만 보는 테스트의 구멍을 막는다.** 행 6개와 개수만 단언하면 rowId와 기록의 짝이 뒤바뀌어도 통과하므로 `movieId:장르` 목록을 단언했다. 이번 실행에서 짝 오류가 실제로 일어났다는 뜻은 아니다.
- **통과한 리뷰 검사는 리뷰를 받았다는 뜻이 아니다.** `claude-review`·`review` 두 검사가 통과했지만 자동 리뷰 코멘트 본문은 `null`이었고 정식 리뷰와 인라인 코멘트는 0건이었다.
- **시간 예측은 세 번 모두 실측이 범위 아래였다.** 145일차 P5, 146일차 P8·P9가 그랬다. 이유를 재지 않았으니 이유를 단정하지 않는 것이 맞다.
- **중단 뒤에는 상태를 먼저 읽고 이어서 한다.** API 오류 뒤 이미 끝난 커밋·푸시·PR 생성을 다시 실행하지 않았다.
- 총 시간의 대부분이 대기와 작업이었고, 결정 화면 대기는 26분 19초로 145일차(74분 31초)보다 줄었지만 CI 대기와 중단 구간이 겹쳐 총 시간은 늘었다.
