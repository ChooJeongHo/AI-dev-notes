# 104 - movie/stats 딥링크 온보딩 재등장 버그 — "새 버그"가 아니라 103일차 화이트리스트의 커버리지 누락이었다

**101/103일차와 같은 popBackStack류 API 오용이 또 나온 게 아니라, 103일차에 새로 만든 함수가 애초에 movie/stats를 빠뜨린 채 만들어진 것이었다**

---

## 목적

103일차에서 "범위 밖"으로 미뤄뒀던 선재 결함(movie/stats 딥링크 진입 후 뒤로가기 시 온보딩 재등장)을 처리한다.

---

## 구현 세부사항

| 항목 | 내용 |
|---|---|
| 커밋 | `8f5df4b` — `fix(nav): movie/stats 딥링크 진입 후 뒤로가기 시 온보딩 재등장 방지` |
| 원인 함수 | `normalizeShortcutEntryBackStack()` (103일차에 신규 작성) |
| 수정 전 화이트리스트 | `search`, `favorite` |
| 수정 후 화이트리스트 | `search`, `favorite`, **`detail`(movie)**, **`stats`** 추가 |
| 신규 테스트 파일 | `MainActivityDeepLinkBackStackTest` |

---

## 원인 — 새 버그가 아니라 103일차 함수의 커버리지 누락

103일차에 만든 normalizeShortcutEntryBackStack()이 search/favorite만 화이트리스트에 넣고 movie/stats는 빠뜨린 채 만들어졌던 것이 원인이었다. 101/103일차의 popBackStack API 오용과는 다른 종류의 문제 — 로직이 잘못된 게 아니라, 애초에 다뤄야 할 대상 목록이 불완전했던 것.

103일차 당시엔 정적/동적 단축키(검색, 즐겨찾기, 최근 본 영화)만 검증 범위였고, movie/stats 딥링크는 그 함수가 처리해야 할 대상인 줄 모르고 넘어갔던 셈이다.

---

## 수정

detailFragment(movie)/statsFragment(stats)를 화이트리스트 대상 목록에 추가했다. 추가로, detailFragment는 필수 argument(movieId)가 유실되지 않도록 하는 처리도 함께 반영했다 — 단순히 목록에 추가하는 것만으로는 부족하고, 그 목적지가 요구하는 파라미터까지 챙겨야 했다.

---

## 테스트 — 이 로직 자체에 자동화 테스트가 전혀 없었다

MainActivityDeepLinkBackStackTest를 신규 추가했다. 103일차에 이 로직을 처음 만들 때도 이 부분을 커버하는 자동화 테스트가 없었다는 게 이번에 드러났다 — 화이트리스트에 항목이 빠져도 테스트가 잡아주지 못하는 구조였던 것.

---

## 실기기 검증 (SM-S926N)

movie/stats/search/favorite 전부 뒤로가기 1회 → 앱 정상 종료, 온보딩 재등장 없음 확인. 103일차에 이미 검증했던 검색/즐겨찾기 단축키도 회귀 없이 재확인됐다.

---

## 부가 발견 (별도 이슈, 이번엔 수정 안 함)

WatchGoalNotificationHelper의 stats 알림 딥링크가 implicit intent + path 불일치로 실기기에서 아예 안 열리는 별개의 버그를 발견했다. 오늘 작업 범위(백스택 정규화)와는 다른 문제라 수정하지 않고, 다음에 알림 관련 작업을 할 때 참고할 수 있도록 메모리에 기록해뒀다.

---

## 배포 과정에서 있었던 일

원격에 Dependabot 커밋(AGP 9.3.2→9.4.0, Coil 업데이트) 2개가 먼저 들어와 있어서 rebase 후 push했다. push 시 관리자 권한으로 required status checks가 우회됐는데, 이건 저장소 설정상 정상 동작이었다 — 예외적인 실패가 아니라 관리자 계정의 의도된 동작이라는 점도 확인됐다.

---

## 101/103/104일차 비교 — 겉보기엔 비슷해도 원인은 다 다르다

| | 원인의 성격 |
|---|---|
| 101일차 | 코드가 아니라 XML 리소스 타입(res/anim vs res/animator) |
| 103일차 | popBackStack API를 의미를 오해하고 오용 |
| 104일차 | 로직 자체는 맞았지만, 처리 대상 목록이 애초에 불완전(커버리지 누락) — API 오용이 아니라 화이트리스트 설계 시점의 누락 |

세 일차 모두 "실기기 UI 흐름 검증에서만 발견된 문제"라는 공통점은 있지만, 매번 실제 원인의 층위가 다르다는 게 확인됐다. 101일차가 배웠던 것처럼, 겉보기 증상(온보딩 재등장)이 같아도 원인을 매번 직접 확인해야 한다는 원칙이 여기서도 그대로 적용됐다.

---

## 오늘 배운 것 — 한 줄 정리

1. "선재 결함"이라고 미뤄둔 문제도 원인을 파보면 완전히 새로운 버그가 아니라, 어제 만든 코드의 커버리지 누락일 수 있다.
2. 화이트리스트 방식(특정 대상만 명시적으로 처리)의 코드는, 새로운 진입 경로가 생길 때마다 그 목록에 빠짐없이 추가됐는지 확인이 필요하다.
3. 목적지를 목록에 추가하는 것만으로 부족할 수 있다 — 그 목적지가 요구하는 필수 파라미터까지 함께 챙겨야 완전한 수정이다.
4. 새로 만든 로직에 자동화 테스트가 없으면, 화이트리스트 누락 같은 실수를 테스트가 못 잡아준다 — 이번에 처음으로 이 로직 전용 테스트가 생겼다.
5. 작업 중 우연히 발견한 무관한 버그(알림 딥링크)는, 범위를 지키고 기록만 남기는 것이 맞는 판단이다.
