# 081 - KOFIC 박스오피스 API 연동 — 빌드는 통과했지만 실기기에서만 보이는 버그 2개

**070~080이 11일 내내 "AI 내부(에이전트/훅/검증)"만 다뤘다면, 081일차는 처음으로 외부 실제 데이터를 연동했다 — 그리고 컴파일·테스트·detekt를 전부 통과한 코드가 실기기에서 두 번이나 크래시했다**

---

## 목적

070~080은 11일 내내 "AI가 AI를 설계/검증"하는 내부 지향적 실험이었다. 081일차는 완전히 다른 결의 실험 — **한국 영화진흥위원회(KOFIC) 오픈API를 MovieFinder에 실제로 연동**해서, 외부 실 데이터를 Clean Architecture로 통합하는 실무 감각을 채운다.

---

## 에피소드 — API 키를 이미 갖고 있었다

KOFIC은 업계 종사자용 사이트(`kobis.or.kr`)와 오픈API 전용 사이트(`kobis.or.kr/kobisopenapi`)가 **서로 다른 회원 체계**로 분리되어 있어서 처음엔 가입이 막힌 줄 알았다. 알고 보니 **2021년 12월에 이미 발급받은 키**가 있었고 (본인도 잊고 있었다), 4년 넘게 미사용이었는데도 실제로 테스트해보니 **여전히 살아있었다.**

---

## 작업 1 — Clean Architecture 레이어별 구현

기존 TMDB 연동 패턴을 그대로 재사용:

```
data/remote/api/KoficApiService.kt        ← Retrofit 인터페이스
data/remote/dto/KoficBoxOfficeResponse.kt ← DTO
domain/model/BoxOffice.kt                 ← 순수 도메인 모델
domain/repository/BoxOfficeRepository.kt  ← 인터페이스
domain/usecase/GetDailyBoxOfficeUseCase.kt
data/repository/BoxOfficeRepositoryImpl.kt ← safeApiCall/DomainException 재사용
```

`local.properties`의 `KOFIC_API_KEY`를 TMDB와 **동일한 `buildConfigField` 패턴**으로 관리 — 기존 관례를 그대로 따라서 새로운 걸 배우지 않고도 일관성 유지.

## 작업 2 — TMDB × KOFIC 데이터 매칭 설계

### 핵심 설계 결정 — "안 보이는 것"이 "틀린 것을 보여주는 것"보다 낫다

```kotlin
// 매칭 로직: 공백/구두점 제거 후 완전 일치만 채택
// (Levenshtein 거리 등 더 정교한 방법도 가능하지만, 오탐 위험이 커짐)
```

> 두 API는 영화 식별자 체계가 다르다(KOFIC `movieCd` vs TMDB `id`) — 유일한 접점은 영화명 문자열뿐이라 근본적으로 퍼지 매칭 문제다. "매칭 실패로 안 보이는 것"보다 "다른 영화를 잘못 매칭해서 틀린 정보를 보여주는 것"이 사용자 신뢰에 더 나쁘다고 판단해, **다소 보수적인 규칙**을 택했다.

### 데이터 신선도 불일치 처리

```kotlin
// KOFIC 일별 박스오피스는 전일 자정 이후 집계되는 배치성 데이터
// "오늘"을 그대로 조회하면 빈 응답이 온다
fun koficDefaultTargetDate(...) = /* KST 기준 전일 계산 */
```

TMDB는 사실상 실시간인데 KOFIC은 하루 지연 — 이 시점 불일치가 사용자에게 안 드러나는 건 향후 개선점으로 남겨둠(정직하게 인정).

### 의도적으로 안 고친 것들 (스코프 관리)

| 이슈 | 판단 |
|---|---|
| TOP 10마다 TMDB 검색 1회씩 = N+1 호출 | 근본 해결(로컬 캐시 우선 조회)은 범위 밖으로 남김 |
| KOFIC 클라이언트에 인증서 피닝/재시도 없음 | TMDB와 비대칭이지만 "핀을 잘못 박아 기능이 죽는 것"을 피하려는 의도적 선택 |
| 매칭 실패 원인(네트워크 실패 vs 진짜 없음)을 구분 안 함 | 실패 사유 필드 추가는 지금 스코프에서 과설계로 판단 |

> **하나하나 다 고치려 하지 않고, 뭘 지금 고치고 뭘 다음으로 미룰지 명시적으로 판단한 것 자체가 실무 감각이다.**

---

## 부분 실패 격리 — 기존 패턴 재사용

KOFIC 섹션 로드가 실패해도 **홈 화면의 나머지 섹션(탭, 최근 본 영화, 그리드)은 전혀 안 깨지게** 설계했다. 이건 `DetailViewModel`의 "선택적 로드(loadOptional)" 패턴을 그대로 재사용한 것 — 새로 발명하지 않고 기존 프로젝트 관례를 따랐다.

## 핵심 발견 — 컴파일·테스트·detekt를 다 통과해도 못 잡는 버그 2개

`assembleDebug` 성공, `testDebugUnitTest` 638+개 전체 통과, `detekt` 클린 — **여기까지는 다 정상이었다.** 그런데 실기기에 설치하자마자 문제가 드러났다.

### 버그 1 — KOFIC의 특이한 에러 응답 형식

```
KOFIC은 인증/파라미터 오류를 HTTP 401 같은 상태 코드가 아니라,
HTTP 200 OK + {"faultInfo": {...}} 형태의 JSON envelope로 반환한다.
```

원래 코드는 `boxOfficeResult`를 필수 필드로 가정했는데, fault 응답이 오면 `kotlinx.serialization`이 `MissingFieldException`을 던졌고, 이게 `DomainException.ParseError`로 뭉뚱그려져서 **"서버 응답을 처리할 수 없습니다. 앱을 업데이트해 주세요"**라는 완전히 엉뚱한 메시지가 떴다.

```kotlin
// 두 필드 모두 nullable로 두고 응답 형태로 성공/실패를 구분
data class KoficBoxOfficeResponse(
    val boxOfficeResult: KoficBoxOfficeResult? = null,
    val faultInfo: KoficFaultInfo? = null
)
```

> **왜 목업 테스트로는 못 잡았나:** KOFIC 공식 문서상 스펙과 실제 응답의 차이는 문서만 보고 목업을 만들면 재현이 안 된다 — **실제 키(만료/오류 상태)로 진짜 호출**해야만 드러나는 문제였다.

### 버그 2 — Material3 전용 속성을 Material2 프로젝트에서 사용

```
item_box_office.xml의 tv_audience에 ?attr/colorOnSurfaceVariant 사용
    ↓
이 프로젝트 테마는 Theme.MaterialComponents.DayNight.NoActionBar (Material2 계열)
    ↓
해당 속성이 정의되어 있지 않음
    ↓
그 아이템이 실제로 화면에 레이아웃되는 순간 UnsupportedOperationException으로 앱 전체 크래시
```

**왜 컴파일/테스트/detekt로 절대 못 잡는가:** XML 레이아웃의 테마 속성 참조는 **런타임에 실제로 인플레이트(inflate)될 때만 검증**된다. 정적 분석 도구는 이 속성이 "존재하는 이름인가"는 확인해도 "현재 테마에 실제로 정의되어 있는가"는 확인하지 못한다.

## 실기기 전면 검증 — 4개 탭 + 네비게이션 전부 확인

수정 후 재설치해서 홈/검색/즐겨찾기/설정 4개 탭과 박스오피스 아이템 → 상세 화면 이동까지 전부 스크린샷으로 확인했다.

| 화면 | 상태 |
|---|---|
| 홈 (박스오피스 TOP 10 + 기존 섹션) | 정상, 1~6위 전부 TMDB 매칭 성공 |
| 박스오피스 아이템 → 상세 화면 | 정상 (평점/장르/예고편/줄거리) |
| 검색/즐겨찾기/설정 탭 | 정상 |

### 정직하게 남긴 미검증 항목

> 오늘 실제 KOFIC 데이터가 마침 전부 "순위 변동 없음(-)"이라, ▲(상승)/▼(하락)/NEW 배지 로직은 **유닛테스트로만 검증**됐고 실기기 화면으로는 못 봤다 — 순위가 바뀌는 날 다시 확인이 필요하다고 남겨둠.

## 오늘 배운 것 — 한 줄 정리

1. 외부 API 연동 시 **공식 문서와 실제 응답이 다를 수 있다** — 특히 에러 처리는 진짜 실패 케이스로 테스트해야 한다.
2. 두 개의 서로 다른 데이터 소스를 결합할 때는 **"틀린 정보를 보여주는 것"이 "안 보여주는 것"보다 나쁠 수 있다** — 보수적인 매칭 규칙이 정답일 때가 있다.
3. **모든 이슈를 한 번에 다 고치려 하지 말고, 지금 고칠 것과 다음으로 미룰 것을 명시적으로 구분**하는 것도 실력이다.
4. 테마 속성처럼 **런타임에만 검증되는 요소는 컴파일/테스트/정적분석으로 절대 못 잡는다** — 반드시 실제 렌더링이 필요하다.
5. 4년 넘은 API 키도 무조건 재발급하지 말고 **먼저 테스트해서 유효성을 확인**하면 시간을 아낄 수 있다.
6. "실기기가 아니면 안 보이는 문제가 있다"는 원칙은 성능(056/079)뿐 아니라 **기능 정확성(081)에도 그대로 적용**된다.
