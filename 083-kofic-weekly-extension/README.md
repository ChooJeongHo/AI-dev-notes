# 083 - KOFIC 주간 박스오피스 확장 — 081/082 설계가 진짜 재사용 가능했는지 실증

**082일차에서 배운 "명시적 스텁" 원칙 덕분에, 테스트를 짜다가 실제 버그 하나(우연히 날짜가 일치해서 생기는 또 다른 "우연한 통과")를 미리 잡아냈다**

---

## 목적

081일차(KOFIC 일별 연동)와 082일차(N+1 최적화)에서 만든 설계가 **정말로 재사용 가능한 구조였는지**, 주간 박스오피스로 확장하면서 실증한다. "재사용 가능하게 설계했다"는 주장은 실제로 다른 데이터에 적용해봐야 검증된다 — 077일차("1줄 교체 설계"를 실제로 검증)와 같은 정신.

---

## 작업 1 — 설계 전에 실제 API부터 검증

`feature-planner`가 계획을 세우기 전에 **먼저 실제 KOFIC 주간 API를 직접 호출**해서 확인했다.

| 확인 항목 | 결과 |
|---|---|
| 응답 배열 키 | `weeklyBoxOfficeList` (일별은 `dailyBoxOfficeList`) — 이름만 다름 |
| 개별 영화 필드 | `rank`/`movieCd`/`movieNm`/`audiCnt` 등 — **일별과 100% 동일** |
| `weekGb` 파라미터 값 | 실제로 잘못된 값을 보내서 **에러 응답으로 역추적**해 `0=주간/1=주말/2=주중`을 확정 |

**결론:** `BoxOffice` 도메인 모델은 **확장 없이 그대로 재사용 가능** — 이게 오늘 실증하려던 것의 첫 번째 증거였다.

> **왜 문서만 보지 않고 직접 호출했나:** 081일차에서 "공식 문서와 실제 응답이 다를 수 있다"는 교훈을 얻었으니, 이번엔 설계 전에 미리 실제로 확인하는 습관으로 이어졌다.

---

## 작업 2 — UI: ChipGroup 토글 + 상태 보존

홈 화면 박스오피스 섹션 헤더에 일별/주간 `ChipGroup` 추가, 선택 상태는 `SavedStateHandle`에 저장해서 화면 회전/프로세스 재생성에도 유지되도록 했다.

---

## 작업 3 — 테스트: 082일차 원칙이 또 다른 버그를 잡다

765개 테스트 전부 통과, detekt 이슈 0건. **"우연히 통과 방지" 원칙대로 전부 명시적 스텁으로 작성**했는데, 그 원칙 덕분에 구현 중 **실제 버그 하나를 미리 발견**했다.

### 발견한 버그

```
오늘 날짜(2026-07-28)의 koficDefaultWeeklyTargetDate() 기본값이
테스트에 쓴 명시적 날짜와 우연히 같아짐
    ↓
MockK가 이걸 "의도한 스텁"으로 잘못 매칭
    ↓
로직이 실제로 맞는지와 무관하게 테스트가 통과할 뻔함
```

**082일차와 정확히 같은 종류의 함정**(우연히 통과하는 테스트)이 형태만 바꿔서 다시 나타났다. 이번엔 "예외가 삼켜진 것"이 아니라 "날짜 값이 우연히 일치한 것"이 원인이었지만, **본질은 같다 — 테스트 조건이 실제 검증 대상과 우연히 겹쳐서 가짜 통과가 만들어질 수 있다.**

**조치:** 캡처 슬롯(captured slot) 방식으로 바꿔서, 우연한 값 일치에 의존하지 않고 **"어떤 값이 실제로 전달됐는지"를 명시적으로 확인**하도록 고쳤다.

> **일반화된 교훈:** "우연히 통과하는 테스트"는 한 가지 원인(082일차의 예외 삼킴)에서만 생기는 게 아니라, **테스트 데이터와 실제 로직의 우연한 일치**처럼 여러 형태로 나타날 수 있다. 매번 "왜 이 값이 이렇게 나왔는가"를 의심하는 습관이 필요하다.

## 작업 4 — 실기기 검증: 캐시 로직이 진짜로 공유되는지 확인

Galaxy S24+에 설치해서 직접 확인:

| 확인 항목 | 결과 |
|---|---|
| 일별↔주간↔일별 전환 | 정상 동작 (스크린샷 확인) |
| 주간 TOP1 "호프" 관객수 | `1,286,065명` — curl로 받은 실제 API 응답과 **정확히 일치** |
| 캐시 히트율 (로그캣) | 10개 중 5개 로컬 캐시 즉시 매칭, 나머지 5개 네트워크 폴백 |
| **캐시 미스 5개 제목** | **일별/주간 두 경로에서 정확히 동일** |
| 크래시 | 없음 |

**가장 중요한 확인:** "일별/주간 두 경로에서 캐시 미스 제목이 정확히 동일하다"는 건, **매칭 로직이 진짜로 공유되고 있다**는 증거다. 만약 일별/주간 코드가 겉만 비슷하고 실제로는 따로 짜여 있었다면, 같은 영화라도 두 경로의 캐시 히트/미스 결과가 미묘하게 달랐을 것이다.

## 작업 5 — 정직한 재사용성 평가

| 구성요소 | 재사용 여부 |
|---|---|
| `BoxOffice` 도메인 모델 | 완전 재사용 — 확장 없이 그대로 |
| 캐시 스냅샷 조회(`getCachedMoviesSnapshot`) | 완전 재사용 — 실기기 로그로 공유 확인 |
| 제목 매칭 로직(`findMatch`) | 완전 재사용 |
| `weekGb` 파라미터 처리 | 새로 추가 필요 — 일별 API엔 없는 개념 |
| 목표 날짜 계산(`koficDefaultWeeklyTargetDate`) | 새로 추가 필요 — 주간 집계 주기가 일별과 다름 |

**정직한 결론:** 핵심 도메인 로직(모델·매칭·캐시)은 **100% 순수 재사용**됐지만, API 파라미터 처리와 날짜 계산처럼 **각 엔드포인트 고유의 부분은 당연히 새로 필요**했다. "전부 복붙됐다"는 과장도 아니고 "억지로 끼워 맞췄다"는 실패도 아닌, **설계가 의도한 경계(공용 로직 vs 엔드포인트별 로직)가 실제로 정확히 지켜졌다**는 게 실증됐다.

## 081 → 082 → 083 3부작 요약

```
081: KOFIC 일별 박스오피스 연동 (첫 외부 API)
     ↓
082: N+1 문제 해결 — 캐시 우선 조회 설계, "우연한 테스트 통과" 최초 발견
     ↓
083: 주간으로 확장 — 082의 설계가 진짜 재사용 가능한지 실증
     → 082와 같은 함정(우연한 통과)이 다른 형태로 재발, 같은 원칙으로 예방
     → 실기기 로그로 "공유 로직이 진짜 공유되고 있음"을 직접 증명
```

## 오늘 배운 것 — 한 줄 정리

1. 설계 전에 **문서만 믿지 않고 실제 API를 먼저 호출**해서 확인하는 습관이 081일차 교훈에서 자연스럽게 이어졌다.
2. "우연히 통과하는 테스트"는 **예외 삼킴(082)뿐 아니라 테스트 데이터와 실제 값의 우연한 일치(083)**처럼 다른 형태로도 나타난다.
3. 캡처 슬롯(captured slot) 방식은 **"어떤 값이 실제로 쓰였는가"를 명시적으로 확인**해서 우연한 일치에 기대지 않게 해준다.
4. 두 기능(일별/주간)의 **캐시 미스 결과가 실기기에서 정확히 같다는 것**은, 코드가 겉모습만 비슷한 게 아니라 실제로 로직을 공유한다는 강력한 증거가 된다.
5. 재사용성 평가는 "전부 됐다/안 됐다"의 이분법이 아니라, **"설계가 의도한 경계가 실제로 지켜졌는가"**로 판단해야 정직하다.
6. 좋은 서브에이전트(kotlin-architecture-reviewer)는 신규 기능마다 계속 새로운 가치를 낸다 — 한 번 검증됐다고 다음엔 안 써도 되는 게 아니다.
