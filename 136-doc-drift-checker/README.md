## 목적

132일차에 `CLAUDE.md`의 낡은 문구 19건을 사람이 하나씩 증거로 찾아 고쳤다. 134일차는 "빈 곳 채우기보다 틀린 곳 지우기가 먼저일 수 있다"는 방향성 증거를 남겼다(침묵은 해롭지 않았고 틀린 단언이 해로웠다). 오늘은 그 앞 단계, **틀린 줄을 사람이 찾지 않고 규칙으로 찾을 수 있는가**를 묻는다.

> **저장소의 사실(식별자·경로·개수·버전)과 문서의 문장이 어긋난 줄을, 결정론적 규칙 점검기가 얼마나 정확하게 찾아내는가?**

- 점검기는 Python 표준 라이브러리·git·grep만 쓴다. 네트워크·adb·`claude -p`는 쓰지 않는다(R9). 비용은 $0이다.
- 재현율은 gold(132일차에 사람이 찾은 줄)로, 정밀도는 정답을 모르는 실문서(시험 B)로 잰다. **재현율만으로는 쓸모를 판단할 수 없어서 정밀도 시험을 처음부터 따로 사전 등록했다.**
- 변이 시험(A)은 정답을 아는 합성 오류이고, 실문서 시험(B)은 정답을 모르는 진짜 문서다.

원칙은 이전과 같다.
- **읽기 → 설계 → 롤백 조건 합의 → 실행**. 숫자·날짜 기준이나 롤백 조건이 걸리면 해석하지 않고 멈추고 묻는다. 기준 재정의는 이유를 적고 승인 후에만 한다.
- gold·예측·설계·점검기·생성기는 해시로 사전 등록하고, **시험 세트를 연 뒤 규칙 수정은 금지**(R7)한다.
- 저장소 변경(push·PR·merge)은 diff를 보여 주고 승인을 받는다. 일차 요약은 `CLAUDE.md`가 아니라 `DEVLOG.md`에만 쓴다.
- 핀 값은 앞 8자만, 요청 URL·키는 출력하지 않고, 기기 설정은 건드리지 않고, 시스템 `/tmp`는 쓰지 않고, 삭제는 리터럴 경로로 허락 후에만 한다.

## 오늘 배운 것 — 한 줄 정리

1. **재현율만 보면 점검기가 쓸 만해 보인다.** 개발 세트 7/15는 나쁘지 않았지만 정답을 모르는 문서에서의 정밀도가 7.3%였다. 결론을 정한 것은 시험 B였다.
2. **같은 규칙도 문서 성격에 따라 정밀도가 다르다.** `README`는 실제 4/8이었고 `PROJECT_HEALTH`는 0/54였다. 보고서·스냅샷 문서는 과거 시점 값을 담고 있어서 "현재 저장소와 다르다"가 곧 "틀렸다"가 아니다.
3. **존재 검사(K1·K2·K4·K5)는 외부·로컬 참조에서 거의 항상 오탐이었고 버전 비교(K6)만 쓸 만했다**(6/13). 값을 직접 비교할 수 있는 주장이 규칙으로 점검하기 쉽다.
4. **정확도가 낮아도 부산물은 있었다.** 실제로 낡은 줄 9건을 찾았다. Dependabot이 래퍼를 올리고 문서를 안 고친 3곳이 대표적이다.
5. **"잡았다"의 정의는 우연을 센다.** 범위 안 어느 한 줄 정의로 7건이지만 사유 일치는 5건이었다. 이유를 따로 등록한 덕에 숫자가 부풀지 않았다.
6. **합성 변이는 순환한다.** A1은 설계상 100%, 무작위 A2는 55%였다. 점검기 실력은 A2 쪽에 가깝다.
7. **멈춤 규칙이 작동했다.** R4 발동 뒤 규칙을 한 줄도 고치지 않고 멈췄고, 이 덕에 "시험 세트를 보고 규칙을 맞춰 점수를 올리는" 일이 없었다. 다만 30%라는 기준 자체는 근거가 약했다.
8. **"사용자 확인"은 절차를 정하지 않으면 승인으로 바뀐다.** 증거 원문을 보여 주고 대조하게 만드는 단계가 따로 있어야 확인이 된다.
9. **마스킹 함수는 정의 직후 합성 대조값으로 과잉·과소를 둘 다 시험해야 한다.** 이번에는 과잉 1·과소 1이 출력에서 발견됐다.
