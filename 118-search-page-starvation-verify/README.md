# 118 - 117일차 재개 — "멈추지 않는다"는 확인됐지만 "빨라졌다"는 아니다

**117일차에서 미커밋 상태로 남겨둔 수정이 이미 main에 병합되어 있었다 — 오늘은 KMRB 한도가 풀린 실기기에서 그 수정을 검증했고, 동작(오판·정지)은 고쳐졌지만 지연 자체는 전혀 달라지지 않았다는 걸 정확히 구분했다**

---

## 목적

117일차에서 결론이 흔들려 코드를 커밋하지 않고 정지했던 검색 페이지 기아 문제를, KMRB API 한도가 풀린 뒤 실기기로 재검증한다.

---

## 시작 전 확인 — 이미 (A)안이 병합되어 있었다

오늘 작업을 시작하기 전 저장소를 확인해보니, 117일차에서 "결정 대기"로 남겨뒀던 두 방향(A: cachedIn 앞으로 필터 이동, B: PagingSource 레벨 이동) 중 (A)가 이미 main에 병합·커밋되어 있었다. 미커밋 변경이나 대기 중 결정은 남아있지 않았다.

처리 방향: 원래 프롬프트대로 진행하면 끝난 작업을 반복하게 되므로, "KMRB 429 해결 후 실기기 재확인"과 "(B) 후속 작업" 중 어느 쪽을 원하는지 먼저 확인했다. KMRB 429 확인 후 실기기 재검증을 선택했다 — 117일차가 정확히 원했던 그 검증이었다.

---

## 결과 — 실기기 검증 완료

### KMRB 429 해소 확인

홈에서 박스오피스를 주간으로 전환하자 KMRB가 200 OK(985ms)로 응답했다. 새 날이 되면서 한도가 초기화된 것으로 보인다.

### 원래 결함 시나리오 재현 — 정상 동작

zombie를 검색하고 스크롤로 2페이지를 선로드한 뒤 15세이상을 골랐다.

- TMDB를 1페이지부터 다시 받고 6페이지까지 이어 로드했다.
- 약 10초 시점에는 shimmer, 48초 시점에는 필터를 통과한 결과(미스 좀비, 아메리칸 좀비 등)가 표시됐다.
- shimmer에 멈추거나 "검색 결과 없음"이 뜨지 않았다.

KMRB 호출은 118건이고 전부 200, 건당 약 0.4~0.5초, 429는 0건이었다.

### 이번 가드가 실제로 작동했다

45초가 되자 칩을 전체로 되돌렸고, KMRB 요청이 118건에서 즉시 멈췄다. 117일차의 가드는 관찰만 멈춰서 요청이 약 320건 더 나갔던 것과 대조된다 — 오늘 가드는 앱 자체를 멈췄다.

---

## 측정하지 못한 것

- 첫 결과가 뜬 정확한 시점 — 45초 관찰 상한에 걸려 모른다. 10초 시점은 shimmer, 48초 시점은 결과였다는 것만 안다.
- night + 전체관람가 같은 "통과 항목이 뒤 페이지에만 있는 조합" — KMRB 호출이 200건 이상이라 시도하지 않았다. 어제 본 연쇄 로드 동작과 오늘 본 결과 표시를 합치면 문제없을 가능성이 크지만, 그 조합 자체를 직접 본 것은 아니다.

---

## "48초"를 지연 지표로 쓰면 안 되는 이유 — 중요한 정정

처음엔 "48초 시점에 결과가 표시됐다"를 개선 수치처럼 오해할 뻔했지만, 정확히는 정상 동작 확인이었지 지연 측정이 아니었다.

48초는 관찰 상한(45초) 직후 찍은 마지막 스크린샷 시점일 뿐이다. 실제로 아는 건 "약 10초 시점에는 shimmer, 48초 시점에는 결과가 표시됨"뿐이고, 첫 결과가 뜬 정확한 시점은 10~48초 사이 어딘가이며 측정되지 않았다.

이번 검증이 보여준 것은 "멈추지 않고 결과가 나온다"이지 "빨라졌다"가 아니다.

### 68초(115일차)와 비교할 수 없는 이유

115일차의 68초(60건 ≈ 1.13초/건)는 필터 안에서 항목마다 한국어 제목을 추가 조회하던 방식의 수치였고, 이미 롤백됐다. 116~118일차에서 다룬 문제는 지연이 아니라 "로딩 중 검색 결과 없음 오판"과 "2페이지 선로드 후 정지"였다. 이번 변경은 필터의 KMRB 조회 방식 자체를 건드리지 않아서 같은 잣대로 비교할 수 없다. 오히려 등급을 바꿀 때마다 재검색이 추가된다(KMRB 결과는 Room 캐시라 큰 비용은 아니다).

## 정리 — 범위를 나눠서 적어야 한다

| 구분 | 내용 |
|---|---|
| 해결 | 로딩 중 "검색 결과 없음" 오판, 2페이지 이상 로드 후 등급 칩 선택 시 이어 로드 정지 |
| 미해결 | 필터 지연(페이지당 약 10초, 통과 항목이 드물면 1분 이상), 연쇄 상한 없음, KMRB 장애 중 연쇄 호출 |

기록된 수치는 night + 전체관람가 약 86~94초, knight + 15세이상 138초이며, 연쇄에 상한이 없다는 문제는 그대로 남아있다. 오늘 본 118건/48초(건당 약 0.4초)도 같은 속도라서, 지연 쪽은 달라진 게 없다고 봐야 한다.

"해결됨"만 쓰지 않고 범위를 나눠 적는다 — 이게 오늘 정리의 핵심 원칙이었다.

---

## 남은 것 — 이번 변경 이전부터 있던 동작 두 가지 (미수정)

1. KMRB 장애 중 등급 칩을 고르면 전 페이지를 연쇄 호출하는 것
2. 즉시 검색과 debounce가 같은 검색을 두 번 내는 것

## 부수 확인 — 스스로의 판단을 재점검함

앞서 "치이카와에는 등급 배지가 없다"고 읽었는데, 다시 보니 "전체" 배지가 있었다. 그 상세 화면은 캐시 적중이었던 것으로 판단이 바뀌어, KMRB 호출 여부 판단에는 쓰지 않았다.

## 116 → 117 → 118일차 발전 요약

```
116: "통과 0건이면 다음 페이지가 안 불린다" (페이지 기아 최초 발견)
    ↓
117: 1차 재현 실패 → "기아 아니라 오판" → 재검증 중 KMRB 429 잡음 →
     "1페이지는 오판, 2페이지 선로드는 조건부로 진짜 기아" (세 번째 결론)
     → 확실하지 않아 미커밋 상태로 정지
    ↓
118: 다른 세션에서 (A)안이 이미 병합된 걸 확인 →
     KMRB 한도 풀린 실기기로 재검증 →
     "멈추지 않는다"는 확인, "빨라졌다"는 아님을 명확히 구분
```

## 오늘 배운 것 — 한 줄 정리

1. 이전에 "미커밋, 결정 대기"로 남겨둔 작업이 다른 세션에서 이미 진행됐을 수 있다 — 새 작업을 시작하기 전에 저장소 현재 상태부터 확인해야 중복 작업을 피한다.
2. "동작이 정상으로 바뀌었다"와 "성능이 개선됐다"는 서로 다른 주장이다 — 관찰 상한에 걸려 찍힌 마지막 시점을 성능 수치처럼 쓰면 안 된다.
3. 서로 다른 날, 서로 다른 원인(115일차 데이터 조회 방식 vs 116~118일차 페이지네이션 로직)에서 나온 수치는 직접 비교할 수 없다 — 무엇을 측정한 수치인지 항상 구분해야 한다.
4. "해결됨" 한 단어로 뭉뚱그리지 말고, 해결된 범위와 미해결로 남은 범위를 나눠서 기록해야 다음 세션이 오해하지 않는다.
5. 과거에 내린 판단(치이카와 등급 배지 없음)도 다시 보면 틀렸을 수 있다 — 스스로의 관찰을 재확인하는 태도가 정확성을 지킨다.
