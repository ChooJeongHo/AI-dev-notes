# 114 - Compose 동적 색상 배선 마무리 — XML만 진짜 디버깅이 필요했다

**113일차에서 스코프 밖으로 남겨둔 Compose 화면 배선을, 새벽 세션이 예상대로 "한 줄 API 수준"으로 깔끔하게 끝내놨다 — Compose의 동적 색상 API는 구조적으로 XML의 함정 2가지가 애초에 적용될 수 없는 설계였다**

---

## 목적

113일차에서 남겨둔 SearchFragment/OnboardingFragment의 dynamicColorScheme() 미배선을 마무리한다.

---

## 시작 전 확인 — 이미 새벽 세션에서 해결되어 있었다

오늘 세션을 시작하기 전, 별도의 새벽 세션(커밋 5c7a332, 2026-09-23 01:00)이 이미 이 문제를 발견·수정·검증까지 끝내놓은 상태였다. 오늘 세션이 실제로 이어받은 건 그 커밋이 못 채운 조각(테스트)뿐이었다.

---

## 새벽 세션(5c7a332)에서 있었던 일 — 113일차 예상대로였다

결론부터: 113일차 예상대로였고, 새로운 함정은 없었다.

- 발견한 문제: SearchFragment의 ComposeView 2곳, OnboardingFragment가 MaterialTheme { }을 옵션(colorScheme 파라미터) 없이 써서, XML 쪽에 이미 적용된 DynamicColors와 무관하게 M3 기본 보라색 팔레트로 남아있었다.
- 고친 방법: 공용 컴포저블 MovieFinderTheme.kt를 새로 만들어 Build.VERSION.SDK_INT >= 31 체크 후 dynamicLightColorScheme()/dynamicDarkColorScheme(context)를 쓰고, 미만이면 기존 lightColorScheme()/darkColorScheme()로 폴백 — 정확히 예상했던 "한 줄 API 수준"의 수정이었고, 113일차 XML 쪽처럼 디컴파일까지 가야 했던 숨은 함정은 없었다.
- 검증까지 한 번에 끝냄: 실기기(SM-S926N)에서 수정 전/후 스크린샷을 PIL로 픽셀 샘플링해서 #C3CAD0(수정 전, 기본 폴백) → #D0DCFC(수정 후, 실제 동적 팔레트)로 바뀐 걸 직접 확인했다.

### 유일하게 짚고 넘어간 판단 포인트 — "타이밍 함정도 있지 않을까?"

"XML 쪽 DynamicColors는 Activity 타이밍이 중요했는데(113일차 함정 2), Compose 쪽도 그런 타이밍 문제가 있지 않을까?" — 확인해보니 없었다. Compose의 dynamic color scheme은 XML의 DynamicColors 오버레이 적용 여부와 완전히 무관하게 android:color/system_accent1_* 시스템 리소스를 직접 읽는 구조라, 애초에 그 함정이 적용될 수 없는 API였다.

이건 디버깅이라기보다 "왜 문제가 안 생기는지"를 확인한 것에 가까웠다.

## 오늘 세션에서 한 일 — 테스트 인프라 구축

작업 1(조사)에서 커밋 5c7a332 diff와 현재 코드(MovieFinderTheme.kt, SearchFragment.kt, OnboardingFragment.kt)를 직접 읽어, MaterialTheme { } 미배선 문제가 더 이상 존재하지 않음을 코드로 재확인했다.

작업 2(구현)는 신규 구현이 불필요했다 — 이미 요청한 그대로가 구현되어 있었다. 대신 테스트 가능하도록 분기 로직만 resolveColorScheme() 순수 함수로 리팩터링했다 (동작 변경 없음).

작업 3(테스트)이 이번 세션에서 실제로 새로 한 유일한 작업이었다:
- MovieFinderThemeTest.kt 신규 작성, 4케이스(API31+ 다크/라이트, API31 미만 다크/라이트 폴백) 전부 통과
- presentation/common/ 디렉터리의 첫 유닛 테스트

작업 4(실기기 검증)는 리팩터링한 빌드를 같은 SM-S926N에 재설치 → force-stop → 재실행 → 검색 탭 스크린샷 재캡처로, 동적 팔레트(연한 블루 계열)가 리팩터링 후에도 동일하게 유지됨을 재확인했다.

## 작업 5 — 정리: "세 겹의 함정"이 Compose에서는 재현되지 않았다

| 113일차 XML 함정 | Compose에서 재현됐나 | 이유 |
|---|---|---|
| 함정 1 (인자 없는 편의 메서드 no-op) | 재현 안 됨 | Compose dynamic API엔 애초에 그 조회 경로가 없음 |
| 함정 2 (Activity 타이밍/AppCompat 덮어쓰기) | 재현 안 됨 | 오버레이 적용 방식이 아니라 컴포지션 시점에 값으로 넘기는 구조라 "덮어쓸 대상" 자체가 없음 |
| 함정 3 (삼성 수동 팔레트 선택) | 동일하게 재현됨 | OS 레벨 이슈라 XML/Compose 무관 |

결론: Compose 쪽은 XML과 달리 숨은 함정이 없는 API 설계였다. 113일차 XML 쪽만 진짜 디버깅이 필요했고, Compose 쪽은 예상대로 단순 배선으로 해결됐다.

## 070~114를 관통하는 패턴 — 같은 기능이라도 구현 방식에 따라 위험도가 다르다

101~113일차 내내 "실기기에서만 드러나는 함정"이 반복됐는데, 114일차는 같은 기능(동적 색상)을 다른 API 계층(XML View vs Compose)으로 구현했을 때 위험도가 완전히 다를 수 있다는 걸 보여준 사례다. XML의 DynamicColors는 오버레이 적용이라는 간접적 메커니즘 때문에 타이밍/조건 함정이 있었지만, Compose는 값을 직접 넘기는 구조라 그런 함정 자체가 성립하지 않았다.

---

## 오늘 배운 것 — 한 줄 정리

1. 같은 기능이라도 View 시스템(오버레이 적용)과 Compose(값 직접 전달)는 구현 메커니즘이 근본적으로 달라서, 위험 요소도 다르다.
2. "문제가 재현되지 않는 이유"를 확인하는 것도 디버깅만큼 가치 있는 작업이다 — 왜 안전한지를 구조적으로 설명할 수 있으면 다음에 비슷한 상황에서 확신을 가질 수 있다.
3. 새로운 컴포저블을 만들 때 분기 로직을 순수 함수로 분리해두면, 나중에 유닛 테스트를 붙이기 쉬워진다.
4. 다른 세션(새벽 작업)이 먼저 처리해놓은 부분을 이어받을 땐, 무엇을 재확인했고 무엇을 새로 했는지 명확히 구분해서 기록하는 게 정직한 문서화다.
5. "예상대로 단순하게 끝났다"는 결과도 113일차와 대조되는 의미 있는 발견이다 — 모든 실기기 검증이 복잡한 버그로 이어지는 건 아니다.
