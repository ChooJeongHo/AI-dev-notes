# 107 - RAG 재인덱싱 — 인프라 사고 5연발을 뚫고, 079/085일차의 함정이 세 번째로 재현되다

**076~079일차 설계 당시엔 없던 core/ 폴더가 095~106일차를 거치며 App Shortcuts·알림·딥링크의 핵심 거처가 됐는데, 인덱스 범위엔 계속 빠져 있었다 — 이걸 고치는 과정에서만 인프라 사고가 다섯 번 연달아 터졌다**

---

## 목적

076~079일차에 설계한 코드베이스 RAG를 095~106일차 신규 코드(KMRB 등급 연동, App Shortcuts, 딥링크 백스택 수정)로 최신화한다.

## 작업 1 — 인덱싱 범위 확장, 그리고 다섯 번의 실패

### 범위 공백 발견

기본 스캔 범위(domain/presentation/data)에 095~106일차 핵심 기능이 빠져 있었다.

| 항목 | Before | After |
|---|---|---|
| 스캔 대상 | domain/, presentation/, data/ | 위 3개 + core/(AppShortcutManager, 알림, 딥링크) + MainActivity.kt/MovieFinderApp.kt(최상위 파일) |

core/와 최상위 파일이 빠져 있던 이유는, 딥링크 백스택 수정(101/103/104/106일차)과 App Shortcuts 전체가 애초부터 인덱스 사각지대에 있었기 때문이다.

### 다섯 번의 시도

| 시도 | 결과 | 원인 |
|---|---|---|
| 1 | FAILED (50분 12초) | 네트워크 순단(ConnectException) — 당시엔 임베딩이 전부 끝나야 DB에 쓰는 구조라, 50분치 Voyage API 비용이 전부 소실 |
| 2 | FAILED (즉시) | 시스템 여유 메모리 121MB(16GB 중 15GB 사용 중)에서 JVM 기동 직후 강제 종료 |
| 3 | FAILED | 배치 단위 저장 첫 적용, 그러나 다른 문제로 중단 |
| 4 | FAILED | --no-daemon으로 재시도했지만 Gradle이 JVM 설정을 맞추려 내부적으로 "single-use daemon"을 또 띄워 --stop에 안 걸림. resume 로직이 아직 없어 0부터 재시작 → 이미 처리한 120개가 다시 임베딩되는 낭비 발생 |
| 5 | SUCCESS | Gradle을 완전히 우회 — 컴파일만 Gradle로 하고 실제 임베딩은 시스템 java(OpenJDK 25, ~/.gradle 밖)로 nohup 분리 실행. 새로 추가한 dao.count() 기반 resume 로직이 이미 처리된 820개를 스킵하고 나머지 860개(86배치)만 이어서 완주 |

### 경로 위에서 발견한 환경 문제

1. 시스템 메모리 고갈(여유 121MB) — Chrome/Slack/Notion/Channel Works 동시 구동
2. Wi-Fi/DNS 순단으로 Voyage API 연결 실패, 기존 코드는 429만 재시도하고 일반 네트워크 예외는 그대로 죽었음
3. ~/.gradle/jdks의 JetBrains JDK 압축 해제 디렉터리가 실행 도중 통째로 사라짐
4. androidx.sqlite:sqlite-bundled-jvm 네이티브 캐시가 빈 채로 남아 "Cannot find a suitable SQLite binary"로 마지막 DB 쓰기 단계에서 실패

### 코드 수정

| 파일 | 수정 내용 |
|---|---|
| VoyageEmbeddingProvider.kt | 429뿐 아니라 IOException(네트워크 순단)도 재시도하도록 확장 |
| Query.kt | ANTHROPIC_API_KEY를 System.getenv() 대신 ProjectConfig(local.properties 포함)에서 읽도록 수정 — 이 버그 때문에 처음 세 질의응답이 전부 오프라인 모드로 나왔었다 |
| Indexer.kt 계열 | 인덱싱 범위 확장 + resume 로직(dao.count() 기반) 추가 |

최종 결과: 1,680개 청크 저장, 297개 .kt 파일 스캔.

## 작업 2 — 질의응답 테스트 3건 (전체 청크 top-5 코사인 유사도 검색 → Claude Sonnet 5가 근거 합성)

### Q1. "KMRB 등급 정보는 어떤 파일들을 거쳐서 처리돼?"

data/remote/dto/KmrbRatingDto.kt(0.4312) 등 top-5 검색. "API → DTO → 도메인 모델" 3단계 흐름으로 정확히 답변 — KmrbApiService.kt가 XML 응답을 받고 KmrbRatingDto.kt가 SAX 파서로 채운 뒤 toDomain()으로 변환, KoreanRatingGrade.kt enum과 매칭한다고 서술. max_tokens 한도에 걸려 답변이 중간에 잘림.

### Q2. "딥링크 관련 버그가 가장 많이 발생했던 화면이나 기능은 뭐야?"

core/notification/WatchGoalNotificationHelper.kt(0.4851)가 검색 1위. 동적 단축키(AppShortcutManager) 구조를 클래스 시그니처·refreshRecentMovieShortcuts()·buildMovieShortcut() 코드까지 인용하며 정확히 설명. Mutex/Dispatchers.IO 사용 이유도 코드 주석 그대로 재현. 단, max_tokens=1024 한도에 걸려 답변이 끊김.

### Q3. "App Shortcuts는 어떻게 구현되어 있어?"

89/100점, "신뢰 가능" 판정.

## 작업 4 — 정리: 076~079일차 설계가 095~106일차의 다른 종류 코드에도 확장 가능했나

### 부족했던 지점

1. DEFAULT_INDEXED_PATHS가 domain/presentation/data만 가정해서, App Shortcuts의 실질 거처인 core/와 최상위 파일이 완전히 사각지대에 있었다. 기능 종류가 다양해질수록(외부 API, 유틸리티성 코드) 이 갭이 더 크게 드러난다.
2. .kt 전용 청커라 XML을 아예 못 본다. App Shortcuts는 절반이 shortcuts.xml(정적 단축키)인데, KotlinChunker 밖에 있어 이 리소스는 top-K를 아무리 올려도 검색 결과에 나올 수 없다. Q3 채점(89점)이 감점된 이유의 절반이 여기서 나왔다.
3. top-K=5 고정이 재현율 병목이 됐다. Q1(KMRB 파일 흐름)의 정답 파일 2개, Q2(딥링크 버그)의 정답 청크 1개가 전부 6~7위에서 잘렸다. 076~079일차 설계 당시엔 청크 총량이 적어 k=5로 충분했지만, core 추가로 1,680개까지 늘어난 지금은 상대적으로 더 좁은 창이 됐다.
4. "유사도≠랭킹" 함정은 근본적으로 미해결이다. 079/085일차에 발견된 함정이 이번엔 정면으로 재발하진 않았다(모델이 표현을 스스로 다운그레이드). 하지만 judge는 "정답이 우연히 나왔을 뿐, 인덱스에 커밋/이슈 이력이 없어 빈도 질문에 답할 데이터 자체가 없다"는 구조적 원인은 076~079일차 설계 때부터 그대로라고 지적했다.

### 반대로, 이번에 실제로 튼튼해진 부분

- 배치 단위 즉시 저장 + resume: 다섯 번의 실패 중 세 번째부터는 진행분이 보존됐고, 마지막 시도는 820개를 스킵하고 860개만 이어서 완주했다. 076~079일차 설계엔 이 안전장치가 아예 없어서 첫 두 번의 실패로 API 비용을 순수하게 날렸다.
- 네트워크 예외 재시도: 기존엔 429(rate limit)만 재시도했는데, 실제로 발목을 잡은 건 일반 네트워크 순단이었다. 지금은 둘 다 처리.

## 오늘 배운 것 — 한 줄 정리

1. 좋은 설계도 시간이 지나면 범위 공백이 생긴다 — 새 기능이 추가될 때마다 인덱싱/검증 도구의 스캔 범위 자체를 재확인해야 한다.
2. 인프라 사고(메모리, 네트워크, JDK 캐시, 네이티브 바이너리)는 한 번에 하나씩이 아니라 연달아 겹쳐서 터질 수 있다 — 매번 근본 원인을 정확히 분리해서 처리해야 한다.
3. 오래 걸리는 배치 작업은 중간 저장 + resume 로직이 없으면, 실패할 때마다 이미 쓴 비용을 전부 날린다.
4. "유사도≠랭킹" 함정(079/085일차)은 겉보기엔 안 걸린 것처럼 보여도, judge가 근거를 파고들면 "우연히 맞은 것"과 "구조적으로 답할 수 없는 질문"이라는 실체가 드러난다.
5. .kt 전용 청커처럼 한 가지 파일 형식만 다루는 도구는, 프로젝트에 다른 형식(XML 등)의 핵심 리소스가 늘어날수록 커버리지가 벌어진다.
