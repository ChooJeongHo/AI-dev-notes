# 124 - 다른 탭의 가로 모드 점검 — 막힌 곳은 홈의 메인 목록 하나뿐이었고, 그 목록은 "시청기록이 있으면" 0px이었다

**123일차에서 검색 탭을 고친 뒤, 나머지 탭도 가로 모드에서 쓸 수 있는지 실기기로 점검했다. 사용 불가였던 건 홈의 "현재 상영작" 목록(`rv_movies`) 하나뿐이었고, 시청기록이 하나라도 있으면 세로·가로 모두 높이가 0px이었다. 박스오피스·시청기록 섹션을 접히는 앱바로 옮겨 목록에 닿을 수 있게 했다. 다만 첫 화면에서는 여전히 목록이 보이지 않는다 — "닿을 수 있음"과 "처음부터 보임"을 구분해서 기록했다. 롤백 조건 R1이 문자 그대로 걸렸을 때는 몰래 풀지 않고 멈춰서 물었고, "재정의"로 명시했다**

## 목적

123일차는 검색 탭만 다뤘다. 같은 종류의 문제(가로에서 높이 예산 부족)가 다른 탭에도 있는지 확인하는 게 오늘의 출발점이었다.

원칙은 이전과 같다.
- 먼저 재현하고 측정한다. 증상과 원인을 분리한다.
- "문제 없음"도 정직한 결론이다.
- 확인하지 못한 것은 확인하지 않았다고 쓴다.
- 롤백 조건은 구현 전에 합의하고, 걸리면 완화하지 않고 멈춰서 묻는다.

## 작업 1 — 다른 탭 가로 모드 점검

실기기 SM-S926N으로 탭별 가로 모드를 측정했다.

- 사용 불가였던 건 **홈의 메인 목록(`rv_movies`)뿐**이었다.
- 홈에서 시청기록이 있으면 세로·가로 모두 `rv_movies` 높이가 **0px**이었다.
- 그 외 탭(상세, 인물, 즐겨찾기, 컬렉션 등)은 "쓸 수는 있지만 불편한" 수준이라 오늘 고치지 않고 후보로만 기록했다(아래 "남은 한계").

### 홈이 0px인 이유 (측정 + 계산)

홈의 루트는 `LinearLayout`이고 세로로 쌓인다.

| 영역 | 높이(px) |
|---|---|
| 툴바 / 탭 / 앱바 영역 | 491 |
| 박스오피스 섹션 (가로 레이아웃매니저 + wrap_content) | 1328 |
| 시청기록 섹션 (기록이 있을 때만 표시) | 937 (잘린 값, 아래 참고) |
| `rv_movies` ("현재 상영작" 그리드) | **남은 높이 = 0** |

- 박스오피스는 2026-07-24(KOFIC 연동), 시청기록은 3월에 추가됐다. 즉 섹션이 추가될 때마다 목록이 밀려나, 기록이 있으면 항상 0이 됐다 — **데이터에 따라 나타나는 결함**이라 기록이 없는 기기에서는 안 보인다.
- `uiautomator`는 높이 0인 노드를 덤프에서 빼버린다. 그래서 `dumpsys`와 스크린샷으로 교차 확인했다.

## 작업 2 — 수정 방안과 결정

선택한 방안은 **○-c**였다.

- 툴바·탭은 고정한다.
- 그 아래 영역을 `CoordinatorLayout`으로 바꾼다.
- 박스오피스·시청기록 두 섹션을 접히는 `AppBarLayout` 자식으로 옮긴다.
- 목록에는 `appbar_scrolling_view_behavior`를 건다.
- 컬렉션·상세 화면이 이미 쓰는 패턴이라 새 개념이 아니다.
- "맨 위로"(FAB, 상단 탭·하단 내비 재선택)가 섹션도 함께 펼치도록 `MainActivity.scrollCurrentTabToTop()`을 고쳤다.

Kotlin 변경은 HomeFragment +5(한도 20), MainActivity 함수 안 순증감 +3이다.

### R1이 걸렸다

시청기록 섹션이 **937 → 1024px(+87px)**로 바뀌어 R1이 문자 그대로 걸렸다. Claude Code는 조건을 풀지 않고 멈춰서 A/B/C 선택지를 줬다.

- 원인: 수정 전 937px은 **잘린 값(AT_MOST)**이었다. 남은 공간에 눌려 측정된 값이다. 1024px은 **자연 높이(UNSPECIFIED)**다. 섹션이 커진 게 아니라 잘리지 않게 된 것이다.
- 수정 전에 있던 제목 겹침·카드 잘림이 이 +87px과 함께 사라졌다.

| 선택 | 내용 | 결과 |
|---|---|---|
| **A** | 불변 대상을 "툴바/탭 491, 세로 박스오피스 1328은 1px까지 동일"로 좁히고, 이력 섹션의 풀림은 의도된 변화로 인정 | **채택** |
| B | 이력 섹션을 일부러 다시 잘라 937에 맞춤 | 기각 (고친 결과를 망가뜨림) |
| C | 수정 철회 | 기각 (0px 결함이 남음) |

이 재정의는 README와 PR 본문에 **"R1 재정의"**로 명시했다. 숨기지 않는 게 핵심이다.

### R4도 해석이 갈렸다

MainActivity 변경이 함수 안 순증감 **+3**이지만, import 한 줄을 포함한 파일 전체로는 **+5/−1**이다. 함수 안 순증감 +3을 통과로 처리하고, 두 해석을 모두 기록했다.

## 작업 3 — 앱 데이터 복원 (DB 파일 수술)

시청기록이 있는 상태를 재현하려면 기기 데이터를 건드려야 했다. 그래서 **DB 파일을 백업하고, 호스트 복사본에서 행을 지운 뒤 되돌리는** 방식을 썼다.

1. 앱 중지 → DB 3개 파일 복사.
2. 호스트 복사본에서 행 삭제.
3. 기기로 push → 각 단계 해시로 검증.

- 첫 시도는 `adb shell` 인용 문제로 4단계에서 중단됐다. 해시가 수술 전 복사본과 일치함을 확인한 뒤 다시 했다.
- 즐겨찾기는 로컬 전용(Room `favorite_movies`)이다. TMDB 동기화는 읽기 전용이고 GET 엔드포인트가 2개뿐이라, 지워도 서버에 영향이 없음을 먼저 확인했다.
- 작업이 끝난 뒤 DB 복사본과 임시 덤프를 지웠다.

## 오늘 배운 것 — 한 줄 정리

1. "탭마다 점검해 보니 막힌 건 하나뿐"이라는 결과도 정직한 결론이다. 범위를 넓게 보고 좁게 고쳤다.
2. 결함이 **데이터에 따라** 나타났다 — 시청기록이 있을 때만 0px. 데이터 없는 환경의 테스트로는 영영 못 본다.
3. **"닿을 수 있음"과 "처음부터 보임"은 다르다.** 앱바로 목록에 도달할 수 있게 만들었지만 첫 화면은 그대로이고, 이를 성공으로 포장하지 않았다.
4. 측정값에도 조건이 있다. 937px은 잘린 값이었고, 롤백 조건 R1이 걸린 이유가 거기 있었다. 걸렸을 때 조용히 풀지 않고 멈춰서 물은 뒤 "재정의"로 기록했다.
5. 0 계열 판정은 도구가 쉽게 속인다 — `uiautomator`는 높이 0 노드를 빼고, 스크립트는 실패를 조용히 삼킨다. 교차 확인이 필요했다.
6. 집계도 틀린다(lint 83 → 85, "9개 red" → 6개). 틀린 걸 숨기지 않고 정정 절에 적었다.
7. 행동 변화(당겨서 새로고침)와 확인하지 못한 항목을 결과와 같은 비중으로 적었다.
