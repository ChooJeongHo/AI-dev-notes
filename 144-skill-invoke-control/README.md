# 144 - 143일차의 "스킬을 호출하지 않은 run도 만점" 의문을 b2 변형 2종(프롬프트 맨 앞에 스킬 호출 강제·금지 문장 한 줄)을 팔당 10 run(40 run, $4.3094, 862초)으로 쟀더니 호출 강제 with 10/10(fired 10/10) 대 금지 with 4/10(fired 0/10)이 나왔고 금지 변형에서도 with 0.70 대 without 0.45로 갈렸지만 구간이 넓어 원인은 구분하지 못한다(예측 5개 중 4개 성립, 작업 1시간 24분, DEVLOG PR #207)

**143일차는 b2에서 with 10/10 대 without 2/10을 얻었지만, with 팔의 스킬 비호출 3 run도 모두 만점이라 "스킬 호출의 효과"로 읽을 수 없다는 점이 남았다. 144일차는 b2 프롬프트 앞에 한 문장만 붙인 변형 2개(`b2-force-skill`: 호출 강제, `b2-forbid-skill`: 호출 금지)를 `--runs 10`으로 다시 쟀다.** 변형 외 b2의 채점기·resources 14개 파일은 바이트 동일하고 원본 66개 케이스 digest도 같다(`case.yaml`의 name과 `prompt.md`의 경로 1줄은 달라졌다). 예측 5개와 분석 계획은 실행 전에 고정했다(09:49:02). 본 실행은 1회(09:57:45~10:12:08, 862초, $4.3094, 오류 run 0)이고, 만점 run 수는 force with 10/10·without 3/10, forbid with 4/10·without 0/10이다. 스킬 호출은 force with 10/10, forbid with 0/10이라 금지 통제는 작동했다(프롬프트 수준). 금지 변형의 with 4/10은 143일차 비호출 3 run의 3/3과 다르지만 CLI(2.1.330→2.1.331)와 프롬프트가 달라 합치지 않았고, with 대 without도 p=0.0867·구간 겹침이라 원인은 구분하지 못한다. 예측은 5개 중 4개 성립(P3 불성립)이다. 총 1시간 24분 22초, 결정 화면 3개, 저장소 변경은 DEVLOG 한 절(+8/−0, PR #207 병합 `c7a27e0a`)뿐이다.

## 오늘 배운 것

- **호출 여부를 통제하면 수치가 갈렸다(관찰).** force with는 fired 10/10에 만점 10/10, forbid with는 fired 0/10에 만점 4/10이었다. 143일차 비호출 3 run의 3/3이 forbid에서는 재현되지 않았지만, CLI·프롬프트·집단(자발 비호출 대 지시 비호출)이 달라 같은 현상의 반증으로도 확증으로도 쓰지 않는다.
- **with의 우위는 forbid에서도 숫자상 남지만 뚜렷하지 않다.** forbid with 0.70 대 without 0.45(만점 4/10 대 0/10, p=0.0867, 구간 12.2~73.8% 대 0.0~30.8%)는 구간이 겹쳐 이 표본으로는 구분하기 어렵다. 143일차 가설("등록만으로 높을 수 있다")은 지지도 기각도 되지 않았다.
- **문장 한 줄이 without 팔 점수에도 걸릴 수 있다.** without 만점이 force 3/10, 143일차 2/10, forbid 0/10이었지만 3/10 대 0/10의 p=0.2105라 말할 수 없다. 처치 변수를 분리할 때 "통제 문장 자체"가 새 변수가 된다는 점이 설계상의 교훈이다.
- **검증 스크립트도 실패 경로를 시험해야 한다.** 병합 때 원격 브랜치가 자동 삭제되는 경우를 가정하지 않아 `verify_merge144.sh`의 1회차가 무효가 됐다. 1회차를 무효로 표시하고 같은 스크립트로 2회차를 돌린 처리는 맞았다.
- **DEVLOG 인용을 자동 검증하는 절차는 효과가 있었다.** 백틱 구간 51개를 도구 출력 파일과 글자 단위로 대조해 143일차 같은 오기를 사전에 막았고, 본문 수정 라운드 없이 결정 화면 3개로 끝났다.
- **작업 시간은 줄었지만 사용자 대기 시간은 그대로였다.** 총 시간은 10분 16초 줄었고 사용자 대기는 43분대로 같았다(시간표의 시작 기준 차이에 주의).
