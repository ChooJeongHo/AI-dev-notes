# 116 - 검색 화면 언어 재검토 — "60개"는 고정값이 아니라 연쇄 로드의 결과였다

**115일차의 68초 문제를 "표시 제목만 지연 조회"하는 방식으로 해소했다 — 그 과정에서 "60개 항목을 조회한다"는 전제 자체가 틀렸다는 게 드러났다. 실제로는 필터 통과율에 따라 페이지가 연쇄로 로드되는 구조였다**

---

## 목적

115일차에서 부분 해소로 남긴 검색 화면 KMRB 필터의 언어 문제(영어 모드에서 68초)를 마저 처리한다.

---

## 작업 1~2 — 조사와 설계: 처음 제안한 방향이 두 번 기각됐다

### 기각 1 — "화면에 보이는 항목만 필터 조회"는 불가능했다

필터를 통과해야 목록에 들어가는데, 목록에 있어야 화면에 보이는 순환 구조였다. 억지로 하면 "전체 표시 후 탈락 항목 제거" 방식이 되는데, 목록이 튀고 필터의 의미 자체가 깨진다.

### 기각 2 — "배치 조회로 우회"도 실측으로 기각됐다

ko-KR 검색 1회로 영어 페이지의 한국어 제목을 얻으려면 두 응답의 ID 집합이 같아야 하는데, 30개 페이지 중 28개에서 달랐다 (TMDB가 언어별로 재정렬한다). 깊은 페이지일수록 더 어긋났다.

### 최종 설계 — 방향을 뒤집었다: 필터는 그대로, 표시 제목만 지연 조회

- 필터 경로(검색/discover)는 변경하지 않고 ko-KR 유지 — KMRB 매칭도 그대로라, 영어 모드에서도 필터에 추가 호출이 0건.
- 영어 모드에서는 화면에 컴포즈된 카드만 /movie/{id}?language=en-US로 제목을 조회.
  - 150ms 디바운스로 빠른 스크롤 구간 스킵
  - 동시 요청 4개로 제한
  - 화면을 벗어나면 조회 취소
- 카드는 제목과 평점만 표시(줄거리 없음)이라 제목만 바꾸면 충분.
- 캐시는 메모리 LRU + OkHttp HTTP 캐시로 처리. TMDB 응답의 cache-control: max-age≈10,217초(약 2.8시간)를 확인해서 새 Room 테이블/마이그레이션은 불필요했다.
- 기존 movie_korean_title_cache는 ko 방향이라 검색에는 못 쓰고, 상세 화면 KMRB 매칭용으로 그대로 유지.

### 이 안으로도 남는 한계 (사전에 정직하게 짚음)

- KMRB 순차 지연(20개당 약 11초)은 그대로
- 페이지 기아 현상도 그대로 (뒤에서 원인이 드러남)
- 영어 모드에서 제목이 약 0.5초 뒤 한국어→영어로 전환
- 포스터는 ko-KR 기준으로 유지

대안(2번: 필터를 PagingSource 레벨로 이동)은 근본 해결이지만 SearchViewModel/Paging 구조를 크게 바꾸는 리팩터라 범위 초과로 기각하고, 1번(표시 제목 지연 조회)으로 승인했다.

## 작업 3 — 구현

GetLocalizedTitleUseCase, LocalizedTitleRepositoryImpl, SearchComposables의 rememberDisplayTitle로 조회 경로를 구성했다. 과호출 방지 장치(디바운스/동시성 제한/이탈 취소)를 전부 반영했다.

## 작업 4 — 테스트

새 테스트 21개 추가, SearchViewModelTest 갱신. 동시 4개 제한과 디바운스를 일부러 망가뜨려서(4→6, 150ms→0) 해당 테스트가 정확히 실패하는 것까지 확인했다 — 테스트가 실제로 그 제약을 검증하고 있다는 방증이다.

### Stop 훅이 잡아낸 테스트 커버리지 공백

세션 종료 시 stop-test-coverage-guard.sh가 걸렸다 — domain/repository/LocalizedTitleRepository.kt, domain/usecase/FilterMoviesByKoreanRatingUseCase.kt, domain/usecase/GetKoreanTitleUseCase.kt에 대응 테스트가 없다는 경고였다.

말로만 "필요 없다"고 넘기지 않고, diff로 직접 확인했다:

| 파일 | 변경 내용 | 근거 |
|---|---|---|
| FilterMoviesByKoreanRatingUseCase.kt | 주석만 수정 | 주석 아닌 변경 라인 0건, 실행 코드 그대로, 기존 테스트 이미 존재 |
| GetKoreanTitleUseCase.kt | 주석만 수정 | 위와 동일 |
| LocalizedTitleRepository.kt | 새 인터페이스 | 시그니처 3개만 있고 구현 코드가 없어 테스트 대상 자체가 없음 |

인터페이스의 실제 동작은 이미 다른 테스트가 검증하고 있었다 — 구현체 LocalizedTitleRepositoryImplTest(11개: 캐시, 언어별 키, LRU, 동시 4개 제한)와 소비자 GetLocalizedTitleUseCaseTest(10개: 디바운스, 취소, 폴백).

## 작업 5 — 실기기 측정

| 항목 | 결과 |
|---|---|
| 영어 모드 첫 화면 | 4개 카드에 조회 4건(평균 247ms), 영어 제목 정상 표시 |
| 62개 항목 플링 | 조회 25건, 스쳐간 구간은 조회 없음, 중복 0건 |
| ko-KR 제목 조회 | 0건 (115일차 방식은 항목마다 발생했음) |
| 한국어 모드 | 표시 제목 조회 0건 (회귀 없음) |
| 필터 경로 항목당 비용 | 약 0.45초(307건/138초). 115일차는 약 1.13초(68초/60건) |

68초와의 직접 비교는 못 했다 — 필터가 몇 페이지를 이어 로드하는지는 필터 선택도에 좌우되어 정확히 60건 상황을 재현할 수 없었다. 대신 항목당 비용으로 비교했고, 같은 60건이면 약 27초로 추정된다(계산치이지 측정치는 아니다).

## 작업 6 — 정리: 완전 해소는 아니다, 그리고 진짜 원인을 찾았다

### 해소된 것

검색 화면이 앱 언어를 따르고, 영어 모드 필터가 한국어 모드와 같은 비용이 됐다(68초 문제 제거).

### 남은 한계 (언어와 무관한 기존 문제)

- KMRB 순차 호출이라 한 페이지(20건)에 약 10초가 걸린다.
- 통과 항목이 적으면 페이지가 연쇄 로드된다 (knight + 15세 이상 필터 → 15페이지·307건·138초).
- 통과가 0건이면 다음 페이지가 로드되지 않아 "검색 결과 없음"이 나온다 (dragon+12세 이상, night+전체관람가에서 재현).
- "60건"은 고정값이 아니라 연쇄 로드의 결과였다. BaseMoviePagingSource가 loadSize를 무시해서 첫 로드는 20건이다.

개선 후보: 필터를 PagingSource 레벨로 옮기는 리팩터가 근본 해결이지만, 이번 범위 밖이라 하지 않았다.

## 요청했던 release 로깅 확인 — 꺼져 있음, 별도 이슈 불필요

logging-interceptor가 debugImplementation이고 release의 addDebugLogging()은 no-op이다. release APK의 dex와 R8 mapping에서 HttpLoggingInterceptor가 0건이었다. 확인에 쓴 APK는 9/20 빌드라 최신 커밋 기준 재빌드는 하지 않았다. 디버그 빌드에서는 KMRB serviceKey가 계속 로그에 남는다 (이번 범위에서 수정하지 않음, 별도 과제로 남김).

## 알아두실 점

- 실기기 측정 중 다른 앱이 갑자기 실행됐다. kr.co.neople.dfon(던파온)이 실행됐는데, 원인은 사용자가 굿락(Good Lock)으로 설정해둔 정오 자동 실행 루틴이었다 — Claude Code의 자동화가 띄운 게 아니었다. 확인 후 이후 스크립트는 입력 전에 포커스를 확인하고, 아니면 중단하도록 바꿨다.
- Stop 훅을 한 번 막을 수 있다. domain/repository/LocalizedTitleRepository.kt는 동작이 없는 인터페이스라 전용 테스트를 만들지 않았다 (동작은 구현체와 UseCase 테스트에서 검증).
- CLAUDE.md(33.9KB)와 코드 주석의 낡은 수치("60개" 등)를 갱신했고, 메모리에도 기록했다.

변경은 아직 커밋하지 않았다.

## 115 → 116일차 발전 요약

```
115: 검색 화면 언어 연동 시도 → 60개 전부 조회로 68초 → 부분 해소(한국어 롤백)

     → 조사 과정에서 "60개"가 고정값이 아니라
       필터 통과율에 따른 연쇄 로드의 결과였다는 걸 발견
```

## 오늘 배운 것 — 한 줄 정리

1. 처음 제안한 설계가 논리적으로 불가능하거나(순환 구조) 실측으로 기각될 수 있다(API가 언어별로 응답을 재정렬함) — 두 번 기각당하고 세 번째 안이 채택됐다.
2. 겉보기 수치("60개")가 사실은 다른 메커니즘(연쇄 로드)의 결과값일 수 있다 — 원인을 제대로 추적하면 전제 자체가 틀렸다는 게 드러나기도 한다.
3. Stop 훅이 테스트 누락을 지적하면, 말로 반박하지 않고 diff로 직접 근거를 확인하는 게 맞는 절차다.
4. 테스트가 실제로 제약을 검증하는지 확인하려면 그 제약을 일부러 깨뜨려서 테스트가 정확히 실패하는지 봐야 한다.
5. 실기기 측정 중 예상 밖의 일(다른 앱 실행)이 생기면, 원인을 자동화 탓으로 단정하지 않고 사용자에게 먼저 확인하는 게 맞는 태도다 — 이번엔 사용자의 자동화 루틴(굿락)이 원인이었다.
