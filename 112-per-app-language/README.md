# 112 - 앱별 언어 설정 검증 — "기능 없음"이 아니라 "이미 있음", 그리고 되돌린 결정이 옳았다

**요청은 "언어 설정 추가"였지만 기능은 이미 있었다. 알려진 공백(API 24~32 영속화 누락)을 메우려다, API 33+ 전체에서 업데이트마다 언어가 초기화되는 더 넓은 회귀를 만들었고, 좁은 문제 대신 넓은 문제를 되돌리는 판단을 내렸다**

---

## 목적

MovieFinder에 앱별 언어 설정(시스템 언어와 무관하게 이 앱만 언어를 바꾸는 기능)을 추가한다.

---

## 전제 정정 — 이미 구현되어 있었다

요청은 "언어 설정 추가"였지만, 조사해보니 기능은 이미 있었다. item_language 행과 showLanguageDialog()(시스템/한국어/English)가 AppCompatDelegate.setApplicationLocales()를 이미 호출하고 있었다. 그래서 신규 구현 대신 검증과 보완으로 목표를 바꿨다.

---

## 작업 1 — 조사

| 항목 | 결과 |
|---|---|
| 설정 화면 언어 UI | 이미 있음 |
| 문자열 완전성 | 유지됨 — values 339개 문자열이 values-en에 전부 있고, plurals 누락/초과 없음 (065일차 검증 상태 유지) |
| API 적용 가능성 | 이미 사용 중 — minSdk 24, targetSdk 36, AppCompat 1.8.0 조합에서 33+는 네이티브, 24~32는 AppCompat 방식 |

발견한 빈틈 3가지:
1. API 24~32 영속화 훅(autoStoreLocales) 없음
2. TMDB language가 ko-KR로 고정
3. 언어 관련 테스트 없음

작업 범위: 1+3(영속화 + 테스트)로 결정 — 2번(TMDB 언어 연동)은 Room 캐시 무효화까지 얽혀 별도 설계가 필요해서 제외.

---

## 작업 2 — 설계 및 구현: 영속화 시도 → 회귀 발견 → 되돌림

새 UI는 만들지 않고 기존 다이얼로그를 그대로 재사용했다. AndroidManifest.xml에 AppLocalesMetadataHolderService(API 24~32 영속화용)를 추가했다.

TMDB 언어 연동은 범위에서 제외 — 인터셉터 방식은 유력하지만 Room 캐시의 한국어 데이터 무효화까지 얽혀 별도 설계가 필요했다.

---

## 작업 3 — 테스트

SettingsFragmentTest에 Espresso 3개를 추가하고 @After에서 로케일을 복원하도록 했다.
- 다이얼로그 선택지 3개 표시
- English 선택 시 로케일 en과 표시값 갱신
- 시스템 기본값 선택 시 로케일 해제

유닛 테스트는 추가하지 않았다 — 언어 로직이 AppCompatDelegate(Android 프레임워크)에 붙어 있고, 이 프로젝트가 Robolectric을 안 써서 계측 테스트가 맞다고 판단했다.

---

## 작업 4 — 실기기 검증에서 드러난 핵심 발견: 회귀

### 확인된 것 / 확인하지 못한 것

| 확인됨 | 확인 못함 |
|---|---|
| SettingsFragmentTest 12개 전부 통과 | Stats/Detail 화면의 즉시 반영 (온보딩 화면만 확인) |
| en 전환 후에도 시스템 로케일 ko-KR 유지 | Detail 제목/줄거리는 TMDB 파라미터 코드로 추정만 함, 실제 확인 안 함 |
| 프로세스 종료 후 재실행해도 en 유지 | API 24~32 동작 (API 36 기기 한 대뿐이라 검증 불가) |

### 실기기에서만 드러난 회귀 — 핵심 발견

추가한 AppLocalesMetadataHolderService가 API 33+에서 언어 선택을 첫 실행 시 []로 초기화했다.

통제 실험으로 원인을 확정했다 — 서비스가 없으면 [en]이 유지되고, 있으면 초기화됨. 실제 사용자 시나리오인 업그레이드 설치에서도 재현됐다: 이미 고른 언어가 업데이트 후 한 번 사라지고, 그 뒤에는 정상 유지된다.

컴파일과 계측 테스트는 이 문제를 잡지 못했다.

## 되돌리기 결정 — "좁은 공백"보다 "넓은 회귀"가 우선

| | 원래 상태 (서비스 없음) | 서비스 추가 |
|---|---|---|
| API 24~32 영속화 | 안 될 수 있음 (좁은 구버전 기기 한정) | 해결됨 |
| API 33+ 업데이트마다 | 문제없음 | 언어가 한 번씩 초기화됨 (넓은 최신 기기 전체) |

"이득보다 리스크가 크면 되돌린다"는 101/103/104/109/110일차 원칙을 그대로 적용해서, 서비스를 되돌리기로 결정했다.

### 되돌리기 + 재검증

AndroidManifest.xml의 AppLocalesMetadataHolderService 추가분을 git checkout으로 원복했다. 재검증(SM-S926N, API 36)에서 아래 네 시점 모두 앱 로케일이 [en]으로 유지됨을 확인했다:

- 신규 설치 후 첫 실행
- 재시작
- 업데이트 설치(install -r)
- 업데이트 후 실행

## 작업 5 — 정리

065일차 i18n 재사용도: 문자열 리소스, locales_config.xml, 설정 다이얼로그가 거의 전부 그대로 재사용됐다. 이번에 새로 추가한 문자열/UI는 없다.

095~111일차 패턴 재현: "실기기에서만 드러나는 문제"가 이번에도 재현됐다 — 101/103/104/106/109/110일차에 이어 일곱 번째. 검증 방식이 겹치는 지점은 통제 실험, 업그레이드 시나리오 확인, 실기기 검증이다.

새로 드러난 한계: 반대 방향의 한계도 있었다 — 최신 API 기기(API 36) 한 대만으로는 구버전(24~32) 경로를 검증할 수 없다.

## 070~112를 관통하는 패턴 — 좁은 공백보다 넓은 회귀가 우선

101(리소스 타입)/103(API 오용)/104(커버리지 누락)/106(Intent 매칭)/109(ViewModel 스코프)/110(WorkManager 정책)에 이어, 112일차도 실기기에서만 드러나는 문제였다는 점에서 같은 계열이다. 다만 오늘은 "발견하고 고쳤다"가 아니라 "고치려다 더 큰 문제를 만들어서 되돌렸다"는 다른 종류의 결말이었다 — 이것도 정직한 엔지니어링의 일부다.

---

## 오늘 배운 것 — 한 줄 정리

1. 요청받은 "기능 추가"가 사실 이미 구현되어 있을 수 있다 — 조사 없이 바로 구현에 들어가지 않고 먼저 확인하는 습관이 필요하다.
2. 좁은 범위의 공백(구버전 기기 한정)을 메우려다, 더 넓은 범위(최신 기기 전체)에 새로운 회귀를 만들 수 있다 — 영향 범위를 비교해서 판단해야 한다.
3. 구조적 영속화 도구(AppLocalesMetadataHolderService)를 추가하는 것도 부작용이 있을 수 있다 — "공식 문서가 권장하는 방법"이라도 실기기에서 재검증해야 한다.
4. 되돌리는 것도 정당한 엔지니어링 결정이다 — "고쳤다"만이 성과가 아니라 "회귀를 만들지 않았다"도 성과다.
5. API 36 한 대만 갖고 있으면 API 24~32 경로는 검증할 수 없다는 테스트 장비의 한계도 정직하게 문서화해야 한다.
