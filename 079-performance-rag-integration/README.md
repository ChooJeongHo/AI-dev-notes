# 079 - RAG에 성능 데이터 통합 — 056일차 "에뮬레이터는 못 믿는다"가 그대로 재현되다

**"어떤 화면이 제일 느려?"를 풀려고 에뮬레이터로 측정했다가 Jank 61~67%라는 말도 안 되는 수치가 나왔고, 실기기로 다시 재니 전부 정상 범위로 뒤집혔다**

---

## 목적

078일차(JaCoCo 커버리지 통합)와 **동일한 패턴**을 성능 데이터에 적용해서 "어떤 화면이 제일 느려?" 질문에 답할 수 있게 만든다. 076~078에서 검증된 방법론(코퍼스 확장)을 다른 데이터에 재사용하는 **실행력 강화** 목적의 실험.

## 사전 조사에서 드러난 뜻밖의 사실

### "이전 작업물"이 git에 없었다

프롬프트에서 "056/062/078일차 결과물을 재사용해달라"고 했는데, 확인해보니:

> `tools/` 디렉토리 전체가 아직 커밋되지 않은 **untracked 상태**였고, "day 단위 작업 로그"는 git·stash·브랜치 어디에도 없었다.

다만 078일차의 `COVERAGE_METRIC` 패턴 자체(`ChunkType.kt`, `JacocoCoverageParser.kt`)는 파일로 실재했다 — **커밋 이력 없이 파일만 존재하는 상태**였던 것.

### `chunkType` 필터는 "다음 개선 지점"이 아니라 이미 완성돼 있었다

078일차 README에서 "다음 개선 지점"으로 남겨뒀던 `chunkType` 필터가, 확인해보니 **`Query.kt`의 `parseTypeFilter()` + `-Ptypes="CLASS,FUNCTION"`으로 이미 동작 중**이었다. 이번 작업은 이걸 새로 만든 게 아니라 그대로 재사용한 것.

> **교훈:** "다음에 할 일"이라고 남겨둔 메모가, 실제로는 이미 어느 세션에선가 처리됐을 수 있다 — 작업 시작 전에 항상 **현재 상태를 먼저 확인**하는 습관이 중요하다는 걸 다시 확인했다.

## 새로 만든 것 — `PERFORMANCE_METRIC` 청크 + 부분 재인덱싱

### 078일차와 동일한 패턴

```kotlin
enum class ChunkType {
    CLASS, FUNCTION, FILE_OVERVIEW,
    COVERAGE_METRIC,
    /** gfxinfo 프레임 성능 측정에서 파생된 화면당 프레임 타이밍 요약 - 소스 코드가 아닌 메트릭 데이터 */
    PERFORMANCE_METRIC,
}
```

### 새로운 기능 — 타입별 부분 재인덱싱

078일차는 매번 전체(또는 샘플 전체) `clearAll() + insert`였는데, 이번엔 한 단계 더 나아갔다:

```kotlin
/** 특정 타입의 청크만 삭제 - 전체 재인덱싱 없이 해당 타입만 부분 갱신할 때 사용 */
@Query("DELETE FROM code_chunks WHERE chunkType = :type")
suspend fun deleteByType(type: ChunkType)
```

`ragIndexPerf`라는 별도 Gradle task로 **성능 청크만 삭제 후 재삽입** — 소스 코드나 커버리지 청크는 안 건드리고, 어제 인덱싱된 463개 청크에 성능 청크 5개만 추가했다.

> **078일차에서 지적했던 "데이터 신선도 문제"의 실제 해법**이다. 매번 전체를 다시 인덱싱하지 않고, 바뀐 데이터 종류만 부분 갱신할 수 있게 됐다.

## 1차 측정 — 에뮬레이터 (Pixel_10 AVD)

| 화면 | p50 | Jank 비율 |
|---|---|---|
| HomeFragment | 34ms | **61.2%** |
| SearchFragment | 40ms | **61.2%** |
| FavoriteFragment | 40ms | **66.9%** |
| SettingsFragment | 42ms | **67.3%** |
| DetailFragment | 38ms | **65.2%** |

전 화면이 목표(16ms)의 2배 이상, Jank 60%대 — **정상적인 앱이라면 나올 수 없는 수치**다.

## "에뮬레이터 말고 실기기로 하는 게 낫지 않아?" — 056일차의 교훈이 재현되다

사용자의 이 질문 하나로 056일차("에뮬레이터 Janky 31% → 실기기 5.41%, 최대 11배 과장")와 정확히 같은 패턴이 다시 나왔다.

> 에뮬레이터는 소프트웨어 렌더링 오버헤드 때문에 프레임 타임이 실제보다 비관적으로 나오고, GPU 프로파일링도 절반이 4950ms sentinel 값으로 깨져서 신뢰도가 떨어진다.

## 2차 측정 — 실기기 (Galaxy S24+, SM-S926N)

| 화면 | 에뮬레이터 (이전) | 실기기 (지금) |
|---|---|---|
| Home | p50 34ms / Jank 61.2% | **p50 10ms / Jank 1.17%** |
| Search | p50 40ms / Jank 61.2% | **p50 5ms / Jank 0.93%** |
| Favorite | p50 40ms / Jank 66.9% | **p50 5ms / Jank 0.23%** |
| Settings | p50 42ms / Jank 67.3% | **p50 5ms / Jank 0.23%** |
| Detail | p50 38ms / Jank 65.2% | **p50 5ms / Jank 0.42%** |

**에뮬레이터 수치는 사실상 못 쓸 정도로 부풀려져 있었다.** 실기기 기준으로는 전 화면이 60fps 기준(16ms)을 충족하거나 근접한 정상 범위.

### 정답: HomeFragment가 실기기 기준 상대적으로 가장 느림

`p99 26ms, Jank 1.17%`로 5개 중 최고치 — 스크롤 시 카드 3열 그리드 + 4개 탭 동시 로딩 때문으로 추정(단, 원인 분석은 이번 작업 범위 밖).

## ★ 가장 중요한 발견 — "유사도 1위"가 "실제 1위"와 일치한 건 우연이었다

검색 결과 1위(HomeFragment)가 실제로 가장 느린 화면과 일치했지만:

> 이건 임베딩이 수치를 비교해서 나온 결과가 **아니라, 텍스트 유사도로 나온 우연의 일치**다. 여전히 "정말 가장 느린 화면"을 수치 기반으로 확정 답하려면 `ANTHROPIC_API_KEY`를 설정해 LLM 합성 답변 경로를 쓰는 게 안전하다.

**왜 중요한가:** RAG의 벡터 검색은 "질문과 의미적으로 비슷한 텍스트"를 찾을 뿐, **"수치를 비교해서 최댓값/최솟값을 계산"하지 않는다.** "가장 느린"이라는 질문이 우연히 맞았다고 해서 이 도구가 진짜로 랭킹 계산을 한다고 착각하면 안 된다 — 076일차 Q3에서 배운 "AI가 원리적으로 할 수 없는 일을 구분하기"가 여기서도 그대로 적용된다.

## 오늘 배운 것 — 한 줄 정리

1. "다음에 할 일"로 남겨둔 메모도 **작업 시작 전 현재 상태부터 확인**해야 한다 — 이미 처리됐을 수 있다.
2. 타입별 부분 재인덱싱(`deleteByType`)으로 **078일차의 데이터 신선도 문제**를 실제로 해결했다.
3. **056일차의 "에뮬레이터는 못 믿는다"는 교훈이 성능 데이터에서도 그대로 재현됐다** — Jank 61%(에뮬레이터) vs 1.17%(실기기).
4. RAG의 벡터 검색은 **"의미적으로 비슷한 텍스트"를 찾을 뿐, 수치를 비교해서 랭킹을 계산하지 않는다** — 우연히 맞아도 원리적으로 다른 것이다.
5. "정말 정확한 순위"가 필요하면 검색(retrieval)만으로는 부족하고 **LLM 답변 합성 단계**까지 거쳐야 한다.
6. 테스트 중 우연히 발견한 버그는 **범위를 넘지 않고 기록만 남기고 넘어가는 것**도 중요한 판단이다.
