## 목적

138·139일차는 "문서 점검기"(규칙 대 LLM)를 비교하는 검증 실험이었다. 오늘은 **AI 인재로서의 역량을 AI 기능을 다루는 쪽에서 쌓는다**는 방향으로 바꿔 다음 질문을 정했다.

> **자연어로 쓴 영화 검색 질의("공포는 빼고 액션 영화 추천해줘")를 앱의 검색이 실제로 쓸 수 있는 조건(JSON)으로 `claude -p` 프롬프트가 안정적으로 바꿀 수 있는가? 그리고 그 정확도를 정답을 미리 정해 두고 재현 가능하게 잴 수 있는가?**

- **왜 오프라인 `claude -p`인가**: Max 구독은 Claude Code 사용량을 덮지만 **앱이 호출하는 API는 별도 과금**이다. 그래서 오늘은 앱에 연결하지 않고 `claude -p`로 프롬프트의 변환 능력만 잰다. 앱에 API 키를 내장하면 안 되므로(키가 앱에서 추출될 수 있음) 실제로 앱에 연결할 때는 서버 프록시가 필요하고, 기기 안에서 도는 모델은 기기 지원 여부가 불확실하다. 이 둘은 이번에 검증하지 않았고 다음 일차 후보로만 적는다.
- **점수는 앱 동작이 아니라 정답표와의 일치**다. 정답표의 품질이 점수의 상한이다(0단계의 Insight).
- 스키마는 **앱이 실제로 지원하는 조건만** 담는다. 앱이 무시하는 조합(검색어 + 장르 등)이 JSON에 나오면 "규칙 위반"으로 따로 센다.
- **정답표를 프롬프트보다 먼저 확정**하고, 개발에서 프롬프트를 고르는 **선택 규칙과 예측을 시험 전에 해시로 사전 등록**하며, **시험은 1회만** 연다.
- 정답표 작성·프롬프트 작성·채점기 작성을 같은 모델이 하므로 편향이 생긴다. 이 한계는 처음부터 적었다.

원칙은 138·139일차와 같다.
- **읽기 → 설계 → 롤백 조건 합의 → 실행**. 숫자·날짜 기준이나 롤백 조건이 걸리면 해석하지 않고 멈추고 묻는다. 기준 재정의는 이유를 적고 승인 후에만 한다.
- 저장소 변경(push·PR·merge)은 diff를 보여 주고 승인을 받는다. 일차 요약은 `CLAUDE.md`가 아니라 `DEVLOG.md`에만 쓴다.
- 핀 값은 앞 8자만, 요청 URL·키는 출력하지 않고, 기기 설정은 건드리지 않고, 임시 파일은 scratchpad에만, 삭제는 리터럴 경로로 허락 후에만 한다. `checkout`·`switch`·`reset`·`stash`는 쓰지 않고 과거 상태는 `git show`·`cat-file`로만 읽는다.
- **확인을 거치지 않은 것을 "확인을 거쳤다"고 쓰지 않는다.** 판정 화면에서 Claude Code는 라벨이나 힌트를 제안하지 않는다.

## 개념 정리 (나중에 다시 볼 때)

1. **자연어 → 구조화 출력(JSON)**: 사람의 말을 앱이 바로 쓸 수 있는 형식으로 바꾸게 하는 방식이다. 핵심은 모델 능력이 아니라 **스키마 설계**다. (a) 앱이 실제로 쓰는 필드만 담는다, (b) 앱의 동작 규칙(텍스트 경로는 장르를 무시)을 스키마에 반영한다(`mode`), (c) "해당 없음"의 표현을 통일한다(단일 값은 null, 목록은 `[]`), (d) 지원하지 않는 요청의 대체 경로를 정한다(`text`).
2. **정답표(gold)와 채점**: 정답을 프롬프트보다 먼저 정해야 프롬프트에 맞춰 정답을 고치는 일이 없다. **완전 일치**(6필드 모두 같음)와 **필드 단위** 정확도는 다르다. 필드별로 보면 mode·query·year·sort가 60/60이고 genres·rating_grade가 57/60이라 어디서 틀리는지 보인다. **엄격**은 정의 그대로, **관대**는 사람이 "허용 가능"으로 인정한 것을 더한다.
3. **정규화**: 채점 전에 공백·대소문자를 같게 만드는 처리다. 정규화가 점수에 영향을 줬는지는 정규화 없는 단순 비교(`json.loads` 후 ==)로 교차 확인했다(60/60, 57/60).
4. **사전 등록**: 결과를 보기 전에 예측과 판정 규칙을 해시로 고정하는 것이다. "깨지는 조건"을 함께 적어 두면 틀릴 수 있는 예측이 된다. 오늘은 8개 중 3개가 실제로 깨졌다.
5. **포화(천장 효과)**: 시험이 너무 쉬워 모두 만점이면 점수로 두 후보를 구분할 수 없다. 개발 10/10이 그 예다. 대책은 더 어려운 질의 세트를 별도로 만드는 것인데, 만들어도 같은 작성자 편향이 남는다.
6. **신뢰구간(Clopper-Pearson)**: 표본이 작으면 "95%"의 오차가 크다. 19/20 → 75.1~99.9%, 10/10 → 69.2~100%이고, 20개를 모두 맞혀도 95% 하한은 약 83.2%다. 그래서 1질의 차이로는 우열을 말하지 않는다.
7. **프롬프트 캐싱**: 같은 앞부분(시스템 프롬프트)을 반복해 보내면 두 번째부터 싸게 읽는다. 첫 호출은 캐시 쓰기, 이후는 캐시 읽기(비율 99.9%). 140의 호출당 비용이 $0.00175인 이유는 출력이 짧고(46~67토큰) 입력이 한 줄 질의라서다.
8. **구독과 API 과금은 별개**: Max 구독은 Claude Code 사용량을 덮고, 앱이 호출하는 API는 별도 과금이다. 앱에 API 키를 내장하면 안 되므로(앱에서 키가 추출될 수 있음) 서버 프록시를 거치는 구조가 필요하다. 기기 안에서 도는 모델은 기기 지원 여부가 불확실하다.
9. **하네스와 점수**: 점수는 모델 능력 + 채점기 + 정답표의 합이다. 만점이 나오면 채점기·정답표부터 의심하고(교차 확인), 하네스를 만든 쪽이 스스로 승인하지 말고(독립 검토), 바꾼 부분은 되돌려 보며 시험이 실패하는지 본다(양성 대조).

## 오늘 배운 것 — 한 줄 정리

1. **포화한 개발 세트는 선택을 증거 없이 규칙의 마지막 단계에 맡긴다.** 개발 질의를 시험보다 어렵거나 식별력 있게 설계하지 않으면 A·B 비교가 비어 버린다(P5·P8의 성립도 거의 정보 없음).
2. **버전 확인을 동결 직전과 호출 직전마다 하는 방식이 실제로 필요했다.** CLI가 하루에 두 번 바뀌었다(2.1.321 → 2.1.322). 호출 0회 시점에 걸려 수정 비용이 없었다.
3. **"안전한 방향"으로 만든 정지가 되돌릴 수 없으면 오히려 실험을 잠근다.** 독립 검토가 굳은 선택 파일 문제(HIGH 1건)와 이것을 잡았다.
4. **만점은 채점기와 무관한 교차 확인이 필요하다.** 단순 비교로 60/60과 57/60을 다시 확인했다.
5. **사용자에게 보이는 값은 기록에서 복사하고 검증한 뒤 쓴다.** 판정 화면의 오타(`all_ames`), 브랜치 오보(낡은 추적 ref), 글롭 실수가 모두 손으로 옮기거나 확인 없이 쓴 값에서 나왔다.
6. **스키마는 앱이 실제로 하는 일에서 출발한다.** 앱의 두 갈래(텍스트·탐색)가 서로의 조건을 버린다는 사실이 `mode`를 만들었다. "JSON으로 표현은 되는데 앱이 무시하는 조합"을 규칙 위반으로 따로 센다.
7. **예측을 "깨질 수 있게" 쓰자 3개가 깨졌고 모두 모델이 예상보다 잘하거나 빠른 쪽이었다.** 내 감각이 보수적이었다는 뜻이다(P1 상한 초과·P4 예상 밖 범주·P6 지연 범위 아래).
8. **유일한 오답 test08은 재현 가능한 실패였다.** 3회 모두 같은 답이라 "흔들림"이 아니라 규칙·정답표 쪽 설계 문제일 가능성이 높다. 분위기 표현이 장르 1개로 정해지는지, 동반 대상(아이들)이 등급으로 이어지는지가 질문이다(n=1이라 방향성).
9. **비용은 출력 토큰과 입력 길이가 정한다.** 한 줄 질의 → JSON 한 줄이면 호출당 $0.00175로 점검기(호출당 $0.0334)의 약 5%다. 앱에 연결해도 호출 단가는 이 수준일 가능성이 높지만 서버 프록시·과금 구조는 별개다.
10. **도우미의 "일반 원칙"도 판정을 기울게 한다.** 라벨만 제안하지 않으면 되는 게 아니라 대응표·원칙의 문장 구성까지 독립성에 영향을 준다(내 쪽 정정 5).
