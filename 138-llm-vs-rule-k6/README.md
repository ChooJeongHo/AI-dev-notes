## 목적

137일차에는 규칙 점검기 v2가 K6(버전 대조)만으로 시험 구간 15/23(65.2%)을 잡았고, 놓친 8사이트는 날짜 줄 건너뜀 4·이름 해석 실패 4였다. 다음 질문은 자연스럽다.

> **규칙 코드 대신 LLM이 문서를 읽고 "이 버전 서술이 카탈로그와 어긋났는가"를 지목하면, 같은 gold에서 재현율과 정밀도가 얼마나 달라지는가? 그리고 그 차이는 믿을 만한가?**

- 137의 gold·경계·분석기를 **바꾸지 않는다.** 바꾸는 것은 탐지기 하나다(규칙 코드 → `claude -p`).
- LLM은 비결정적이라 같은 입력을 **3회** 반복해 과반(2/3)을 주 결과로 삼고, 합집합·교집합은 민감도로만 본다.
- 개발 구간에서 **프롬프트 2개를 비교해 하나를 고르고**, 시험 구간은 그 하나로 **1회만** 연다.
- 정밀도는 137과 같은 F/X/U 구간 정의(사람·Claude 판정 없음)로 계산한다.

원칙은 이전과 같다.
- **읽기 → 설계 → 롤백 조건 합의 → 실행**. 숫자·날짜 기준이나 롤백 조건이 걸리면 해석하지 않고 멈추고 묻는다. 기준 재정의는 이유를 적고 승인 후에만 한다.
- 저장소 변경(push·PR·merge)은 diff를 보여 주고 승인을 받는다. 일차 요약은 `CLAUDE.md`가 아니라 `DEVLOG.md`에만 쓴다.
- 핀 값은 앞 8자만, 요청 URL·키는 출력하지 않고, 기기 설정은 건드리지 않고, 임시 파일은 scratchpad에만, 삭제는 리터럴 경로로 허락 후에만 한다.
- checkout·switch·reset·stash는 쓰지 않고 과거 상태는 `git show`·`cat-file`로만 읽는다.
- **표본 확인은 원문을 보여 주고 사용자가 판단한 뒤에만 "확인"이라고 쓴다.** 확인을 거치지 않은 것은 "확인을 거쳤다"고 쓰지 않는다.

### 3회 반복과 집계

- 같은 호출을 **연속·순차 3회** 실행한다(병렬 금지). **과반(2/3) = 주 결과**, 합집합·교집합 = 민감도.
- 비결정성 자체도 측정한다(Jaccard).

### 선택 규칙 G (개발 구간, 사전 등록)

1. 재현율이 높은 쪽(**차이 ≤1사이트는 동률**) →
2. 동률이면 정밀도 하한이 높은 쪽 →
3. 그래도 같으면 비용이 낮은 쪽.

선택한 프롬프트로 시험 구간을 **1회만** 연다.

### 별칭(alias) 해석 — 파일럿 2에서 발견, 개발 전 결정

- 카탈로그에는 `library`/`plugin` 별칭과 `version.ref`, `[versions]` 키가 있다. LLM이 "카탈로그에 적힌 키 그대로"를 말하면 별칭이 나오는데 어댑터는 처음에 `[versions]` 키만 인정했다(이탈 표 추가7).
- **어댑터 해석 순서**: gradle 예외 → `[versions]` 키 → 별칭 경로(구분자 정규화) → `version.ref` → `[versions]` 키.
- **지원하지 않는 경우**: `ambiguous`·`no_ref`·`ref_missing`·`value_mismatch`·`not_found`. 카운터: `alias_resolved`·`alias_fail_*`·`alias_not_found`.
- 사용자가 결정 1(별칭 해석)을 승인했고 v4 동결에 반영했다.

## 오늘 배운 것 — 한 줄 정리

1. **같은 틀에서 탐지기만 바꿔 비교하면 차이가 작을 때 "차이 없음"이 정직한 결론이다.** 시험 16/23 대 15/23, 구간 대부분이 겹치고 부호 검정 p=1.0이라 LLM이 낫다는 증거가 없다.
2. **독립 단위가 표본 수를 정한다.** 시험 gold 23사이트의 78%가 일괄 갱신 커밋 2개에서 나와 독립 단위는 5개 안팎이다. +1사이트는 우연과 구분되지 않는다.
3. **두 탐지기는 많이 겹치고 일부는 보완한다.** 공통 13, LLM만 3, 규칙만 2, 합집합 18/23. 규칙이 놓친 8사이트 중 3을 LLM이 3회 모두 잡았다.
4. **어댑터가 LLM의 점수를 바꾼다.** 별칭 해석 없이는 개발 재현율이 20/29(P1)·19/29(P2)로 떨어졌다. 평가 점수는 모델만이 아니라 출력을 읽는 규칙에도 달려 있다.
5. **LLM은 같은 입력에도 문장이 다르다.** 판정 집합은 거의 같지만(Jaccard 평균 0.964, 시험 96쌍 중 15쌍이 1 미만), 32단위 중 전체 텍스트가 같은 단위는 1개뿐이다. 과반으로 집계하는 이유다.
6. **정밀도 하한 F는 "방치된 줄"에서 과소평가한다.** 표본 U 5/5가 실제로 낡은 줄이었다. 다만 5건뿐이고 13건은 확인하지 못했다.
7. **평가 도구가 만든 값(교차표)도 틀릴 수 있다.** `event_id` 키 덮어쓰기로 틀린 교차표가 나왔고, 표본 계획의 모집단이 이상해서 발견했다. 틀린 해석 문장을 먼저 말하기 전에 합계를 맞춰 본다.
8. **정지 조건은 포화(100%)에도 필요하다.** J6이 P1 29/29에서 발동해 보고했고, 사전 등록 규칙 G로 선택해 사후 합리화를 막았다.
9. **격리 기준은 "전부 0"보다 "허용 목록과 정확히 일치"가 낫다.** 내장 플러그인 3개는 끌 수 없었다. 호출마다 init을 검사하는 방식이 소급 적용 없이도 재현성을 지킨다.
10. **"읽기 전용" 요청에도 이탈은 생긴다.** 확인 중 `/tmp` 리다이렉트와 `cd /tmp`가 나왔다. 읽기 전용 확인에는 출력 리다이렉트 자체를 쓰지 않는다.
11. **지시문의 숫자·범위는 정의까지 적는다.** "13줄"은 빈 줄을 뺀 값이었고 44단위 가정은 틀렸다. 숫자 기준을 줄 때는 무엇을 세는지 같이 쓴다.
