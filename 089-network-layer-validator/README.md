# 089 - 기존 스킬로 검증하고 즉시 고치기 — `/network-layer-validator`

**088일차까지 19일간 계속 "직접 만들기"만 했는데, 오늘은 이미 있는 검증 스킬로 081~083일차 KOFIC 연동을 재점검하고, 발견된 개선점 하나를 그 자리에서 바로 고쳤다**

---

## 목적

076~088(13일)이 RAG, 외부 API 연동, judge, Stop Hook까지 "직접 설계하고 만드는" 실험으로 밀도 높게 이어졌다. 089일차는 방향을 바꿔서, **oh-my-claudecode에 이미 내장된 검증 스킬**을 그대로 써본다. 081일차에서 실제 크래시 2건이 났던 네트워크 레이어를, KOFIC 연동 이후 처음으로 재검증하는 타이밍이다.

---

## 왜 `/network-layer-validator`를 먼저 골랐나

같은 후보군(`/proguard-validator`, `/material3-design-validator`, `/network-layer-validator`) 중에서, **"지금 시점에 실제로 문제가 있을 확률이 가장 높은 것"** 기준으로 순서를 다시 정했다.

| 스킬 | 급한 정도 | 이유 |
|---|---|---|
| network-layer-validator | 높음 | 081일차에서 이미 실기기 크래시 전례가 있고, KOFIC 연동 이후 재검증 이력이 없음 |
| material3-design-validator | 중간 | 086일차 Glance 위젯이 GlanceTheme을 새로 도입 — 검증 필요하지만 급하진 않음 |
| proguard-validator | 낮음 | 아직 실제 릴리즈 배포 이력이 없어서, 지금 당장 문제가 터질 가능성이 낮음 |

"쓸모"를 그냥 감으로 정하지 않고, **최근 실험 이력과 연결해서 우선순위를 다시 매긴 것** 자체가 오늘의 작은 배움이었다.

---

## 검증 결과 — 4개 축 중 3.5개 통과

### 오프라인 처리 — OK

- `IOException → 도메인 예외 변환`이 data 레이어에서만 일어나고, domain 레이어엔 `IOException` import가 아예 없음을 확인
- 모든 catch 블록에서 `CancellationException`을 먼저 잡아 재던지는 패턴이 일관됨
- 오프라인 시 `MovieRemoteMediator`가 네트워크 호출 자체를 생략하고 Room 캐시를 즉시 노출

### 타임아웃 — 발견 즉시 수정

| 설정 | 값 (검증 전) | 조치 |
|---|---|---|
| connect/read Timeout | 15s(공용) / 30s(v4 인증) | 유지 |
| callTimeout | 미설정 | **추가함** |

`callTimeout`이 없으면 리다이렉트+재시도까지 포함한 "요청 전체" 상한이 없어, 이론상 개별 타임아웃 합보다 오래 걸릴 수 있다는 게 발견됐다.

**즉시 수정:** `NetworkModule.kt`의 `applyCommonConfig()`에 `callTimeout(25.seconds)`를 추가했다. 개별 timeout(connect/read/write)은 그대로 두고, 전체 요청의 상한만 새로 얹은 것.

**검증:**
1. 컴파일 확인 — 정상
2. 관련 유닛 테스트 통과 확인 — 정상
3. 089일차 검증에서 확인했던 캐시/오프라인 동작이 실기기에서도 여전히 정상 — 재확인 완료

### 에러 처리 — OK (부가 조사까지 함)

`safeApiCall`이 15개 Repository 중 4개에서만 쓰이는 걸 발견했지만, **직접 확인해보니 나머지 11개는 네트워크 호출 자체가 없는 순수 Room 저장소**라 문제가 아니었다 — 표면적으로 이상해 보이는 걸 그냥 "이슈"로 보고하지 않고 실제로 원인까지 조사한 것.

### 캐시 전략 — OK

- Room 캐시 TTL 1시간, OkHttp 레벨에서 엔드포인트별 Cache-Control 세분화(장르 1일/트렌딩 1분/검색 no-store/기타 5분)
- 오프라인 시 stale 데이터를 지우지 않고 그대로 유지 — 086일차 Glance 위젯도 같은 원칙("갱신 실패 시 기존 스냅샷 유지") 적용
- callTimeout 추가 후에도 이 동작들이 그대로 유지됨을 재확인

## 검증 도구가 오탐할 뻔한 지점을 스스로 알아챈 사례

체크리스트는 "부분 실패 격리 = supervisorScope 사용"을 정답으로 가정하는데, MovieFinder는 **coroutineScope와 supervisorScope를 상황에 따라 다르게 선택**하는 전략을 쓴다.

```
핵심 필드(상세 정보 없이는 화면이 의미 없음)
    → coroutineScope로 묶음 (형제 실패 시 전체 취소, all-or-nothing)

선택적 필드(출연진처럼 없어도 되는 것)
    → async 람다 안에서 개별 try-catch로 격리 (loadOptional 패턴)
```

**두 코루틴 빌더의 실패 전파 의미론 차이를 이해했기 때문에**, "supervisorScope가 없다"는 표면적 사실을 그대로 결함으로 보고하지 않고, 실제로는 **동등한 효과를 다른 방식으로 달성했다**는 걸 정확히 짚어냈다.

> 070~080일차에서 배운 "AI 검증 도구는 체크리스트를 맹목적으로 적용하면 오탐이 난다"는 교훈이, 오늘은 검증 도구 자신이 그 함정을 스스로 피해간 좋은 사례로 나타났다.

## 부가 인사이트 — addNetworkInterceptor를 쓴 이유

```
addInterceptor()        → 캐시 계층을 거치기 전, 매 요청마다 항상 실행됨
addNetworkInterceptor() → 실제로 네트워크를 탄 시점에만 실행됨
```

Cache-Control 헤더 오버라이드는 **"서버 응답이 실제로 네트워크를 타고 왔을 때만"** 의미가 있으므로, `addNetworkInterceptor`를 쓴 게 정확한 선택이었다는 걸 확인했다 — 잘못된 위치에 넣으면 캐시에서 응답을 그대로 서빙할 때 이 로직이 조용히 안 먹히는 미묘한 버그가 생길 뻔했다.

## 070~089를 관통하는 두 가지 확인

1. **기존 스킬도 체크리스트를 맹목적으로 적용하지 않고 설계 의도를 이해한다** — 직접 만든 게 아닌 도구에서도 070~080일차와 같은 성숙도를 확인했다.
2. **가벼운 검증 실험도 "발견하고 끝"이 아니라 "발견 → 즉시 수정 → 재검증"까지 완결 지어야 한다** — 074/080/088일차의 반복된 패턴이 오늘도 그대로 적용됐다.

## 오늘 배운 것 — 한 줄 정리

1. "어떤 스킬을 먼저 쓸지"도 감이 아니라 **최근 실험 이력(어디서 문제가 났었는지)과 연결해서 우선순위를 정하면** 더 실용적인 순서가 나온다.
2. callTimeout 미설정처럼, **개별 타임아웃은 다 있어도 "전체 요청 상한"이 빠질 수 있다** — 재시도 로직이 있는 경우 특히 챙겨야 한다.
3. 표면적으로 이상해 보이는 패턴(safeApiCall 일부만 사용)도 **실제 원인까지 확인하면 문제가 아닐 수 있다.**
4. coroutineScope와 supervisorScope는 "정답이 하나"가 아니라 **상황(핵심 데이터 vs 선택적 데이터)에 따라 의도적으로 다르게 선택**할 수 있다.
5. addInterceptor와 addNetworkInterceptor는 실행 시점이 다르므로, **캐시 관련 헤더 조작은 반드시 addNetworkInterceptor에 넣어야 한다.**
6. **가벼운 검증 실험이라도 발견한 문제는 그 자리에서 바로 고치고 재검증까지 마치는 게 완결된 하루다.**
