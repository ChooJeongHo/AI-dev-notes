# 108 - RAG 랭킹 함정 가드 — 079/085/107일차 세 번의 반복을 "확신에 찬 오답"에서 "정직한 거부"로 바꾸다

**079/085/107일차에 세 번 나타난 "유사도≠랭킹" 함정을 프롬프트 가드로 해소했고, 우연히 벌어진 서브에이전트 중복 실행 사고 덕분에 Claude Code 자체의 실제 버그까지 발견해서 신고했다**

---

## 목적

107일차 "다음에 손볼 것" 5가지 중 우선순위가 가장 높은 2가지(랭킹형 질문 가드, max_tokens 상향)를 처리한다.

---

## 작업 1 — 랭킹형 질문 가드 (최우선)

079(RAG 근본 한계 발견) → 085(judge로 검증) → 107(재인덱싱 후 세 번째 재현)까지 반복된 "유사도 1위를 실제 랭킹 1위로 착각"하는 함정을, 이번엔 근본적으로 막는 대신 정직하게 거부하도록 가드했다.

ClaudeAnswerProvider.kt에 RANKING_OR_FREQUENCY_KEYWORDS(가장 많이/자주, 최다, 빈도 등) 매칭 로직과 RANKING_GUARD_NOTE를 추가했다. 이 키워드가 매칭되면, 프롬프트에 "이 인덱스는 코드 스냅샷만 포함하며 발생 빈도 집계는 불가능하다"는 문구가 자동으로 주입된다.

107일차 judge가 제안한 근본 해결책(커밋 이력을 별도 chunkType으로 인덱싱)은 이번 범위에서 의도적으로 제외했다 — 오늘은 "정직하게 거부하기"까지만, "실제로 답할 수 있게 만들기"는 다음 과제로 남겼다.

---

## 작업 2 — max_tokens 상향

1024 → 4096으로 올렸다. 107일차에서 Q1(KMRB 흐름)과 Q3(App Shortcuts) 답변이 둘 다 코드 인용 중간에 잘렸던 직접적인 원인이었다.

---

## 작업 3 — 검증: 107일차와 같은 3개 질문 재실행

| 질문 | 결과 |
|---|---|
| KMRB 흐름 | API→Repository→UseCase 계층 흐름을 완결된 답변으로 서술 (잘림 없음) |
| 딥링크 버그 최다 화면 (함정 질문) | 가드 문구가 실제로 답변에 반영됨 — "빈도 집계 불가"를 명시하며 랭킹 답변 자체를 거부하고, 대신 컨텍스트에서 확인 가능한 개별 사례(WatchGoalNotificationHelper, MainActivity)만 정직하게 나열 |
| App Shortcuts | AppShortcutManager 구조/동시성 처리까지 상세 답변 (잘림 없음) |

## 작업 4 — judge 재채점: 16/25 → 25/25

딥링크 함정 질문을 rag-answer-judge로 재채점한 결과 종합 95/100, 랭킹/수치비교 기준 25/25 (107일차 16/25에서 대폭 개선). judge는 "유사도 순위를 빈도로 착각하는 오류가 전혀 없음"이라고 독립적으로 확인했다.

### 우연히 얻은 교차검증 — 서브에이전트 중복 실행

메모리 조회용으로 띄운 fork 서브에이전트가, 요청받지 않았는데도 자기 판단으로 별도의 rag-answer-judge를 하나 더 띄워서 같은 질문을 중복 채점했다. 결과적으로 두 번째 채점(97/100)이 첫 번째 채점과 독립적으로 일치하면서, 오히려 의도치 않은 교차검증 역할을 했다.

---

## 작업 5 — 정리: 함정이 실질적으로 해소됐나

3회 반복된 함정은 이번 가드로 실질적으로 해소됐다 — 핵심 변화는 "확신에 찬 오답"에서 "정직한 거부"로의 전환이다.

다만 judge가 두 채점 모두에서 공통으로 지적한 잔존 한계 2가지가 있다:

1. 청크 관련성의 미세한 오배치 — 버그 이력 없는 "딥링크 사용처" 청크(BoxOfficeWidgetContent.kt)가 실제 버그 주석보다 유사도 순위가 더 높게 나옴. 다만 답변이 그 청크를 근거로 쓰지 않아서 실질적 피해는 없었다.
2. 파일 경로 인용 규칙을 파일명만으로 부분 준수하는 경우가 있음.

근본적으로 "실제 빈도가 몇 번인지" 자체를 답할 능력은 여전히 없다 — 이건 오늘 의도적으로 범위 밖에 남긴 것이다 (107일차 judge가 제안한 커밋 이력 인덱싱이 진짜 해법).

## 부수 사건 — Claude Code 자체의 실제 버그를 발견하고 신고

오늘의 "우연한 교차검증"을 자세히 파보니, Claude Code 자체의 버그였다는 게 드러났다.

> fork 서브에이전트에 "메모리에서 이전 질문 문구를 찾아라"는 읽기 전용, 서브에이전트 생성 요청 없음인 좁은 작업만 줬는데, 이 fork가 부모 세션의 전체 대화 맥락을 그대로 상속받아서 "이미 다른 곳에서 rag-answer-judge로 재채점하기로 계획된 단계"를 스스로 발견하고, 요청받지 않은 자기 판단으로 그 단계를 중복 수행했다.

/feedback으로 버그 리포트를 작성해서 확인 후 Anthropic에 전송했다. 리포트엔 재현 조건, ListAgents 증거, 원인 분석("fork가 맥락을 상속받아 스코프 밖 행동을 자체 결정")까지 포함됐다.

## 079 → 085 → 107 → 108, 4일에 걸친 완결 사이클

```
079: RAG에 성능 데이터 통합 중 "유사도≠랭킹" 함정 최초 발견
    ↓
085: judge를 RAG에 적용해서 이 함정을 정확히 짚어내는 능력 확인
    ↓
107: 재인덱싱 후 같은 함정이 세 번째로 재현 (partial pass)
    ↓
108: 가드 추가로 "확신에 찬 오답"을 "정직한 거부"로 전환,
     judge 재채점(16→25/25)으로 개선을 수치로 확인
```

073→074, 087→088일차와 같은 "발견 → 한계 인정 → 재설계로 해소" 패턴이 이번엔 4일에 걸쳐 완결됐다.

## 오늘 배운 것 — 한 줄 정리

1. 근본 해결이 어려운 문제도, "정직하게 답을 거부하게 만드는" 가드만으로도 실질적인 개선이 된다 — 완벽한 해법과 부분적 개선을 구분해서 오늘 할 수 있는 것만 정확히 하는 게 맞는 판단이다.
2. max_tokens 같은 단순 설정값이, 겉보기와 다르게 답변 품질 저하의 직접적 원인일 수 있다.
3. 서브에이전트가 부모의 전체 맥락을 상속받으면, 명시적으로 요청 안 한 작업까지 스스로 판단해서 수행할 위험이 있다 — 이건 AI 도구 자체의 설계 이슈로 신고할 가치가 있다.
4. 우연한 사고(중복 실행)가 늘 나쁜 것만은 아니다 — 이번엔 의도치 않은 교차검증이라는 부수적 이득으로 이어졌다.
5. AI 도구를 쓰다가 발견한 도구 자체의 결함은, 구체적인 재현 조건과 증거를 갖춰서 신고하면 애매한 피드백보다 훨씬 유용하다.
