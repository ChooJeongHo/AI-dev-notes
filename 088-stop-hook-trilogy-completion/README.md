# 088 - Stop Hook 실전 검증 + "오래된 증거" 함정 — Stop Hook 3부작 완성

**087일차 훅이 진짜 세션 종료에서도 작동하는지 확인하다가, "스크린샷 파일이 존재하기만 하면 통과"라는 허점을 사용자가 직접 짚어냈고, 083일차와 같은 종류의 "우연한 통과" 함정이었다**

---

## 목적

087일차는 시뮬레이션(가짜 JSON 페이로드)으로만 Stop Hook을 검증하고, "진짜 세션 종료 시 자동 발동 여부"는 다음 세션의 몫으로 남겼다. 088일차는 바로 그 다음 세션에서 실전 검증을 완료한다.

---

## 작업 1 — 실전 트리거 확인 (음성 케이스)

UI 파일(`item_box_office.xml`)을 사소하게 수정하고, **adb 명령을 의도적으로 실행하지 않은 채** 세션을 정상 종료 시도했다.

**결과: 087일차 시뮬레이션 때와 동일하게 실제로 차단됐다.** 070/071/073일차에서 반복된 "새 훅은 다음 세션부터 유효"라는 제약이 이번엔 **정확히 예상한 대로** 재현됐다 — 087→088 사이에 세션이 한 번 바뀌었기 때문에 자동으로 로드된 것.

---

## 작업 2 — 정상 케이스 확인 (양성 케이스)

같은 파일을 수정한 뒤 이번엔 `adb shell screencap`을 실제로 실행하고 세션을 종료했다.

**결과: 정상적으로 통과됐다.** 차단(음성)과 통과(양성) 두 경로 모두 의도대로 작동함을 확인.

---

## 작업 3 — 1차 보강: "명령 실행"에서 "파일 생성"으로

087일차 스스로 남긴 한계("adb 명령 실행 ≠ 실제 확인")를 반영해, 단순히 명령이 실행됐는지가 아니라 **screencap 결과 파일이 실제로 디스크에 생성됐는지**까지 확인하도록 판정 로직을 보강했다.

---

## 예상 밖 발견 — "존재"만 확인하면 시점을 놓친다

1차 보강 직후, **"파일이 존재하기만 하면 통과되는" 새로운 허점**을 짚어냈다:

```
어제 찍어둔 오래된 스크린샷 파일이 폴더에 그대로 남아있음
    ↓
오늘 UI 코드를 수정하고 adb 명령을 아예 안 돌림
    ↓
그런데 "예전" 스크린샷 파일이 존재하긴 하므로
    ↓
Stop Hook이 통과시켜버림 (오늘은 실제로 검증 안 했는데도!)
```

**조치:** 파일 존재 여부만이 아니라, **파일 생성 시각이 이번 세션 시작 시각 이후인지(타임스탬프 비교)**까지 확인하도록 재보강했다.

```python
# 존재만 확인 (허점 있음)
screenshot_exists = screenshot_path.exists()

# 세션 시작 이후 생성됐는지까지 확인 (보강 후)
screenshot_exists = (
    screenshot_path.exists() and
    screenshot_path.stat().st_mtime > session_start_timestamp
)
```

> **083일차와 완전히 같은 종류의 함정이다.** 083일차는 "테스트 데이터의 날짜가 우연히 오늘 날짜와 일치해서" 생긴 우연한 통과였고, 088일차는 "오래된 파일이 우연히 존재해서" 생긴 우연한 통과였다 — **둘 다 "정적 사실(존재/일치)"만 확인하고 "시점"을 놓쳐서 생긴 같은 구조의 결함.**

## Stop Hook 3부작 완성 — 073 / 087 / 088

| | 073일차 | 087일차 | 088일차 |
|---|---|---|---|
| 확인 대상 | 테스트 파일 존재 | adb 명령 실행 | screencap 파일 생성 + 시점 |
| 증거의 성격 | 정적 사실 | 세션 내 이벤트 (약한 증거) | 세션 내 이벤트 + 시점 검증 (강화된 증거) |
| 반복된 함정 | "테스트가 있다고 품질이 보장되진 않는다"는 073일차 자체의 한계 | "명령 실행 ≠ 실제 확인"이라는 087일차 자체의 한계 | "파일 존재 ≠ 오늘 생성됨"이라는, 083일차와 같은 종류의 함정 |

**세 훅 모두 073일차의 원칙("결정론적 사실 확인은 차단해도 안전")을 공유하지만, "무엇을 결정론적 사실로 볼 것인가"를 매번 더 정교하게 다듬어야 했다.**

---

## 작업 4 — "세션 재시작 필요" 제약, 오늘은 예상대로 작동

070/071/073일차에서 이 제약 때문에 매번 시뮬레이션으로 우회해야 했는데, 088일차는 **자연스럽게 세션이 한 번 넘어간 덕분에 실전으로 검증됐다.** 이건 제약이 사라진 게 아니라, "087→088 사이에 세션 전환이 있었다"는 우연한 타이밍이 맞아떨어진 것 — 근본 제약 자체는 여전히 유효하다.

---

## 정직하게 남기는 한계

이번 보강("파일이 세션 시작 이후 생성됨")도 완전한 증거는 아니다. **"세션 중에 파일이 생성됐다"와 "사람이 그 파일을 열어서 실제로 확인했다"** 사이엔 여전히 간극이 있다. 이 검증 사슬은 이론적으로 끝없이 강화할 수 있지만(예: 파일을 실제로 열람했다는 로그까지 요구), 지금 단계에서 **의도적으로 멈췄다** — 072일차 이후 반복된 "완벽한 해법은 없고 계층적으로 방어선을 겹친다"는 원칙과 같은 판단이다.

---

## 070~088을 관통하는 하나의 패턴 — 재발견

083일차(테스트 데이터 날짜 우연 일치), 088일차(오래된 파일 우연 존재) — **"정적 사실만 확인하면 시점을 놓친다"**는 같은 함정이 형태를 바꿔 두 번째로 나타났다. 이건 우연이 아니라, **"이 작업이 정말 지금 일어났는가"를 확인하려면 항상 시간 축을 명시적으로 검사해야 한다**는 일반화 가능한 설계 원칙이다.

---

## 오늘 배운 것 — 한 줄 정리

1. Stop Hook의 "다음 세션부터 유효" 제약은 여러 날에 걸쳐 자연스럽게 세션이 전환될 때 **실전으로 확인**될 수 있다.
2. "명령 실행 → 파일 생성 → 시점 확인"으로 증거를 단계적으로 강화하는 건, 완벽을 향한 게 아니라 **실용적으로 충분한 지점을 찾아가는 과정**이다.
3. **"존재 여부"만 확인하는 검증 로직은 항상 "오래된 증거가 우연히 통과하는" 함정을 갖는다** — 083일차와 088일차 모두 같은 유형의 결함이었다.
4. 세 개의 Stop Hook(073/087/088)이 같은 원칙을 공유하면서도, 매번 "무엇을 결정론적 사실로 볼 것인가"를 다르게 설계해야 했다 — 재사용은 항상 "스캐폴딩"과 "판정 근거"를 분리해서 평가해야 한다.
5. 완벽한 검증은 없다는 걸 알면서도, **어디서 멈출지를 의도적으로 판단하고 그 이유를 문서화**하는 게 성숙한 엔지니어링이다.
