# 123 - 가로 모드 검색 탭 레이아웃 — 원인은 한 뷰의 높이 0이 아니라 "높이 예산 부족"이었고, 고치다 만난 크래시는 기기 검증만 잡았다

**122일차에서 별도 건으로 분리해 둔 "가로 모드에서 최근 검색어 목록 높이 0"을 조사했다. 영향받은 건 목록 하나가 아니라 검색 탭 콘텐츠 영역 전체(173px)였고, 최근 검색어도 검색 결과도 가로에서는 사실상 쓸 수 없는 상태였다. 가로 전용 레이아웃(`layout-land`)으로 고쳤고, 수정 후 검증에서 크래시가 나 롤백 조건에 걸렸을 때는 조건을 완화하지 않고 처음부터 다시 재서 통과시켰다**

---

## 목적

122일차에서 세로→가로 회전 5회 중 5회, 최근 검색어 영역에 제목만 보이는 현상을 확인했다. 어댑터 문제가 아니라 레이아웃 문제로 판정하고 같이 고치면 원인이 섞이니 별도 건으로 분리했다. 이번에 그걸 다뤘다.

처음부터 정한 원칙은 이랬다.
- 수정 전에 먼저 재현하고, 증상과 원인을 분리해서 본다.
- "의도된 레이아웃이다 / 재현 안 된다"도 정직한 결론이다.
- 확인하지 못한 것은 확인하지 않았다고 쓴다.
- 높이가 왜 0이 되는지는 122일차에서는 측정만 했고 원인은 확인 안 된 상태였으므로, XML 제약 문제라는 추정을 확정하지 않는다.

## 작업 1~3 — 조사와 판정

### 증상: 122일차보다 범위가 컸다

기기는 SM-S926N(1440×3120, 560dpi, 3버튼 내비, 폰트 1.0)이다. 가로 값은 모두 키보드 내림 상태다.

| 조건 | 가로 결과 | 세로(같은 실행) |
|---|---|---|
| (a) 검색 화면에서 회전, 최근 검색어 1개 | rv=0px, 행 0개: **3/3** | rv=1271px |
| (a) 3개 | **3/3** | 1271px, 행 3개 |
| (a) 10개 | **3/3** | 1271px, 행 6개 (뷰포트 한계) |
| (a) 0개 | 섹션이 GONE이라 rv는 해당 없음, frame_h=173: **3/3** | frame_h=1495 |
| (b) 가로에서 홈→검색 탭 | **5/5** | 해당 없음 |
| (c) 가로 콜드 스타트(`moviefinder://search`) | **5/5** (유효 표본 기준) | 해당 없음 |

- 가로, 키보드 내림, 최근 검색어 1개 이상 조건의 유효 표본 **19건 중 19건이 rv=0**이었고 예외는 0건이다.
- 최근 검색어 개수(1/3/10)와 진입 경로(회전/탭/콜드 스타트)와 무관하게 값이 같았다. 어댑터나 데이터 문제가 아니라는 뜻이다.
- **122일차의 173px은 `recent_searches_section`만의 높이가 아니라 검색 탭 콘텐츠 영역 전체(FrameLayout)의 높이였다.** 검색 결과 영역(`compose_search_results`)도 가로에서 173px, 세로에서 1495px이었다. 즉 가로 모드의 검색 탭은 최근 검색어뿐 아니라 결과 목록도 거의 안 보이는 상태였다.

### 원인: "속성 하나가 틀린 것"이 아니라 높이 예산 부족

측정한 산술은 이렇다(가로, 키보드 내림).

```
nav_host 1244px = 1440 − bottom_nav 196
 ├ 상단 인셋     105  (fitsSystemWindows)
 ├ toolbar       196
 ├ 입력창        224
 ├ 칩 3줄        546
 │  = 1071px (nav_host의 86%)
 └ FrameLayout  173px  ← 남은 공간 전부
     └ 헤더 행: 자연 높이 224px → 173px로 잘림
        └ rv: 173 − 173 = 0
```

- 고정 높이 스택 아래에 `match_parent` FrameLayout이 있고, 스크롤로 높이를 흡수하는 컨테이너가 없다. 가로 높이는 411dp뿐인데 스택이 306dp를 차지해 49dp가 남는다.
- **"XML 제약 오류"가 아니었다.** 잘못 지정된 속성은 없고 높이 예산이 부족한 구조였다. 그래서 `rv`만 고치면 검색 결과 영역(173px)이 그대로 남는다. 영역 전체를 다루는 쪽이 근본에 맞다.
- 예측 검증을 했다. 헤더 자연 높이가 173보다 작았다면 설명이 틀렸을 텐데 224였다. 키보드 상태의 IME 프레임 하단 예측도 세로(1430)·가로(442) 모두 실측과 정확히 맞았다.
- 앱 너비(WindowSizeClass)로만 적응하는 점이 근본 요인이다. 이 기기는 가로 너비가 891dp라 EXPANDED(4열)로 분류되지만 높이는 411dp뿐이라, 너비 기반 적응이 오히려 같은 창에 열을 늘리는 쪽으로 작동한다.
- 의도 신호는 없었다. 가로를 제외하는 장치(방향 고정 코드)는 0건이고 `layout-land`도 없었다. "의도된 동작"이 아니었다.
- 다만 "루트 `fitsSystemWindows`가 IME 인셋을 창 하단 기준으로 패딩에 반영한다"는 **소스 수준의 메커니즘은 확인하지 못했다.** 수치가 일치하는 수준까지만 말할 수 있다.

## 작업 5 — 수정 후 검증에서 크래시가 났다

첫 수정 빌드를 실기기에서 돌렸더니 **가로에서 검색어를 입력하자 크래시**가 났고, 롤백 조건 R2/R3(가로)가 이 빌드에서 충족되지 못했다. 설계 승인과 reviewer 정적 리뷰(APPROVE)는 이걸 못 봤고, 기기 검증이 잡았다.

Claude Code는 조건을 임의로 완화하지 않았다. 선택지를 제시했다.

| 선택지 | 내용 |
|---|---|
| 보완 후 재검증 | 가로 루트에 `baselineAligned="false"` 한 속성을 추가하고(id·클래스 패리티·세로 XML 불변, Kotlin 무변경), 그 속성을 고정하는 JVM 테스트(속성을 빼면 RED)를 붙인 뒤, R1·R2·R3·V1~V3·IME·칩 폭을 처음부터 다시 재측정하고 모든 실행에 크래시 버퍼 0건 검사를 넣는다. 또 걸리면 다시 멈춰서 묻는다 |
| F3 포기 + 한계 기록 | 브랜치를 버리고 `CLAUDE.md`만 갱신한다. 가로 검색 탭은 173px 상태로 남는다 |
| 설계 재논의 | 루트 `LinearLayout` 고정 제약(baseline-prof) 때문에 변경 범위가 커질 수 있어 비추천 |

"보완 후 재검증"을 선택했다. 범위가 여전히 XML 한 속성이고, 롤백 조건을 완화하는 게 아니라 같은 조건으로 처음부터 다시 재는 것이기 때문이다.

### 크래시 원인

가로 루트에 `baselineAligned="false"`가 없으면, `width=0dp` + `weight`인 자식이 UNSPECIFIED 높이로 선측정되어 `LazyVerticalGrid`가 터진다(`LinearLayout.java:1219`로 확인). 속성을 추가한 뒤 크래시가 사라진 것을 "수정 후 사라짐"으로 확인했다. 크래시 원인을 앱 안에서 별도로 계속 추적하지는 않았다.

## 오늘 배운 것 — 한 줄 정리

1. "목록 높이 0"처럼 보인 증상의 진짜 범위는 콘텐츠 영역 전체였다 — 증상을 본 뷰만 보고 판정하면 크기를 놓친다. 122일차에 본 건 일부였다.
2. 원인은 속성 하나가 아니라 "높이 예산 부족"이었다. 고정 높이 스택이 가로 높이의 86%를 차지하고, 스크롤로 흡수하는 컨테이너가 없었다.
3. 설계 승인과 정적 리뷰가 통과해도 레이아웃 크래시는 못 잡는다 — `baselineAligned` 누락은 기기에서 입력해 봐야 드러났다.
4. 롤백 조건이 걸렸을 때 완화하지 않고 같은 조건으로 처음부터 다시 쟀다. 122일차에 이어 두 번째로, 이번에도 최종 빌드가 전부 통과했다.
5. 측정 도구도 틀린다 — lint "0건" 집계 정규식 오류, 무효 표본, 다이얼로그 정규식 오타를 양성 대조가 잡았다. "0건은 양성 대조 없이 믿지 않는다"(121·122일차)가 이번에도 맞았다.
6. 설계가 "확인 못 함"으로 남긴 것을 기기에서 확인하라고 요청한 게 효과가 있었다 — 칩 폭이 1264px로 줄바꿈이 필요했음을 확인했다.
7. 범위를 지키는 결정(그리드 열 수, IME 하단 낭비를 별건으로)이 "프로덕션 Kotlin 변경 0건"을 유지했다.
