# 080 - LLM-as-judge — "AI의 판단을 어떻게 검증하는가"

**070/074일차 리뷰를 재검증했더니 하나는 순수 환각(코드 인용을 정반대로 뒤집음)이었고, 세 번 모두 같은 결함(A5 누락)이 반복돼서 즉시 원 에이전트를 고쳤다**

---

## 목적

070~074일차에서 `kotlin-architecture-reviewer`라는 Subagent를 만들고 계속 개선해왔는데, **그 리뷰 자체가 실제로 정확한지는 한 번도 시스템적으로 검증한 적이 없었다.** 080일차는 별도의 "judge" 에이전트로 과거 리뷰들을 재조사한다.

---

## 작업 1 — review-judge 설계

`kotlin-architecture-reviewer`의 산출물(리뷰 텍스트 + 대상 코드)만 입력받아, **코드를 다시 읽고 리뷰의 주장을 하나하나 재검증**하는 감사관 역할.

### 채점 기준 (100점 만점, 25점씩)

| 기준 | 확인 방법 |
|---|---|
| 1. 심각도 분류 정확성 | Critical/Major/Minor 기준이 정의(크래시·데드락 vs 관례위반 vs 무해)에 맞는가 |
| 2. 근거 코드 라인 정합성 | 인용된 "근거" 코드가 실제 파일에 그대로 있는가 (Read/Grep 직접 대조) |
| 3. 재현율 | 체크리스트 A~D를 judge가 직접 재수행해서 놓친 위반이 있는가 |
| 4. 정밀도 | 지적한 위반이 실제로 문제인가 (experimental API 건은 컴파일 재실행으로 확인) |

**감점 상한 규칙:** 근거 조작/Critical 오탐/Critical 누락/심각도 완전 오분류 중 하나라도 있으면 산술합과 무관하게 **전체 40점 상한.**

## 작업 2 — 과거 리뷰 재검증 결과

### 070일차 (HomeViewModel.kt): 40/100, 재작업 필요

당시 세션에서도 "이건 오탐이었다"고 정정했었는데, **그 정정의 근거조차 완전히 정확하진 않았다.**

> 070일차 당시 결론: "coroutines 1.7.0부터 `flatMapLatest`가 experimental 딱지를 뗐다"
> **judge의 재조사 (javap로 바이트코드 직접 확인):** 1.11.0에서도 `@ExperimentalCoroutinesApi` 어노테이션은 여전히 붙어있음. 진짜 이유는 "딱지가 없어져서"가 아니라 **"이 프로젝트가 `-Werror`(경고를 에러로 승격)를 안 켜놔서 경고만 뜨고 빌드는 통과한다"**는 것.

**같은 결론(오탐 맞음)에 도달했지만 근거는 두 번 다 살짝 부정확했다** — LLM이 "그럴듯한 설명"을 만들어내는 게 얼마나 쉬운지 보여주는 사례다.

### 074일차 (DetailViewModel.kt): 33/100, 재작업 필요 — 순수 환각 발견

> Critical 지적: `ratingMutex.tryLock()`이 `launch` 밖에서 호출됨
> **judge의 재조사:** 인용문이 실제 코드와 **구조가 정반대**임을 확인. 실제 코드는 `launchWithErrorHandler { if (tryLock()) {...} }`(안전한 패턴)인데, 리뷰는 `if (tryLock()) { launchWithErrorHandler {...} }`(위험한 패턴)로 **뒤집어서 인용**했다.

이건 근거를 잘못 읽은 게 아니라 **순수 환각(hallucination)**이었다. 만약 사람이 "리뷰가 그럴듯하니 믿고 코드를 고쳤다"면, **이미 안전한 코드를 오히려 위험한 패턴으로 "수정"할 뻔한 사례**다.

## 작업 3 — 의도적 저품질 리뷰로 judge 신뢰성 테스트

`FavoriteViewModel.kt`를 대상으로 Critical 2건을 조작해서 judge에게 줬다:

1. **완전 허구:** `favoriteMutex.tryLock()` — 이 파일엔 Mutex 관련 코드가 아예 없음 (grep 0건)
2. **인과관계 조작:** `selectedTag`의 `SharingStarted.Eagerly`를 "메모리 누수 → OOM 크래시"로 몰아감

**결과: 30/100, 재작업 필요.** #1은 즉시 grep으로 잡아냈고, **#2는 예상보다 더 뛰어난 결과**였다 — judge가 `git log`를 뒤져서 실제 커밋(`13229d0`, "selectedTag Eagerly 복원")을 찾아내, 이게 실수가 아니라 **"파생 StateFlow의 stale-read 방지를 위한 의도적 설계"**였다는 걸 증명했다.

> 저품질 리뷰를 만든 당사자조차 몰랐던 사실(커밋 이력)을 judge가 찾아냈다 — judge가 "그럴듯한 말로 대충 채점"하는 게 아니라는 실증.

**검증의 검증:** judge가 인용한 커밋(`13229d0`)이 실제로 존재하는지, 내용이 정말 일치하는지 직접 `git show`로 재확인 → 정확히 일치했다. **judge 자신도 근거를 지어내지 않았다는 것까지 확인한 셈.**

070일차, 074일차, 저품질 리뷰 테스트 **3건 모두**에서 체크리스트 A5(대응 테스트 파일 존재 여부) 항목이 결과표에서 **통째로 누락**됐다. 프롬프트에 명시된 절차인데 실행에서 매번 빠지는 게 **우연이 아니라 재현되는 구조적 결함**으로 확인됐다.

## 즉시 보강 — 074일차와 같은 방식으로 원천 차단

`feature-implementer.md`의 "완료 게이트" 패턴을 그대로 가져와 세 곳에 넣었다:

```markdown
# 완료 게이트 (예외 없음)

domain/*.kt 또는 presentation/**/*ViewModel.kt가 리뷰 대상이면,
그 파일 각각에 대해 A5 행이 반드시 존재해야 하고 값이 채워져야 한다.
표에서 A5 행 자체를 생략하거나 빈 칸으로 두는 것은 허용되지 않는다.
```

- **역할 섹션 직후:** 완료 게이트 신설, "N/A 처리도 허용 안 됨"이라고 도피구를 미리 막음
- **실행 절차 마지막 단계:** 출력 직전 자가 점검 추가 — 실패하면 1-1단계(Glob)로 되돌아가게 함
- **Output_Format 표 설명:** "관련 없으면 제외 가능"이라는 기존 문구가 A5를 빠뜨릴 빌미였다는 걸 인지하고, A5만 예외로 명시

### 검증 — 즉시 재리뷰

`HomeViewModel.kt`를 다시 리뷰시켰더니 **A5가 결과표에 정상적으로 포함됨**(`✅ | HomeViewModelTest.kt 존재`). **3전 3패였던 게 보강 후 1전 1승으로 바뀜.**

## ★ 핵심 통찰 — "사후 감시"와 "사전 설계"의 진짜 차이

> 실패가 재발할 수 있는 표면적을 **어디서 없애는가**의 차이다.

| | 070~074일차 (사후 감시) | 080일차 보강 (사전 설계) |
|---|---|---|
| 방식 | 이미 나온 리뷰를 judge가 다시 읽고 재조사 | 출력 직전 자가 점검을 절차에 못박음 |
| 강점 | 근거 조작(074일차 환각)처럼 심각한 문제에 강력 | judge가 매번 잡아줄 필요 없이 결함 발생 확률 자체가 줄어듦 |
| 비용 | 리뷰 1건당 opus 풀 재조사 필요 (비용 2배) | 프롬프트 한 줄 보강으로 끝 |

**"계획에 테스트 지시가 없어서 건너뜀"(074일차)과 "체크리스트에 A5가 있지만 표에 못 옮김"(080일차)은 둘 다 에이전트가 정의된 절차를 알고 있음에도 출력 직전에 슬쩍 빠뜨리는 같은 종류의 실패 모드다** — 그래서 같은 처방(완료 조건을 예외 없이 못박고, 출력 전 자가 점검 강제)이 그대로 통했다.

## LLM-as-judge의 한계 — 정직하게

- **Judge도 틀릴 수 있다:** 이번엔 judge의 모든 주장을 사람이 직접 재검증했고(컴파일 결과, git 커밋) 다행히 다 맞았지만, 이건 "이번엔 운이 좋았다"이지 "judge는 항상 옳다"가 아니다.
- **같은 맹점을 공유할 위험:** 원 리뷰어와 judge 둘 다 같은 체크리스트(A~D)를 기준으로 판단한다. 체크리스트 자체가 놓치는 유형의 결함은 judge도 똑같이 놓칠 수 있다 — "제3자 검증"이라기보다 "같은 잣대로 두 번 재는 것"에 가깝다.
- **비용:** 오늘 3건 채점에 subagent 토큰만 약 29만, 15분 넘게 걸렸다.
- **자기 강화 편향 가능성:** judge 프롬프트가 "리뷰를 믿지 말라"고 강하게 못박혀 있는데, 과잉 교정되면 정확한 리뷰까지 트집 잡을 위험도 있다 (이번엔 징후 없었지만 표본 3건뿐이라 일반화는 이르다).

## 그럼에도 유용한 진짜 이유 — 개별 채점이 아니라 반복 패턴 발견

> LLM-as-judge의 진짜 가치는 **개별 리뷰 하나하나를 잡아내는 것보다, 여러 번 돌려서 나오는 반복 결함을 찾아 원천을 고치는 데 있다.**

오늘의 흐름이 이걸 그대로 보여준다:

```
review-judge 설계
    ↓
070/074일차 실전 리뷰 2건 + 조작된 저품질 리뷰 1건 재검증
    ↓
3건 전부에서 같은 결함(A5 누락) 반복 확인
    ↓
그 패턴을 근거로 원 에이전트(kotlin-architecture-reviewer) 프롬프트 자체를 보강
    ↓
즉시 재검증으로 확인
```

**judge는 "한 번 쓰고 버리는 채점기"가 아니라, 반복 실행에서 나온 공통 패턴을 원 에이전트를 고치는 데 쓰는 피드백 루프**였다.

```

     → "판단을 검증하는 것"도 결국 같은 "사전 설계" 원칙으로 귀결됨
```

## 오늘 배운 것 — 한 줄 정리

1. AI가 "정정했다"고 한 결론도 **근거 자체가 부정확할 수 있다** — 같은 결론에 도달했어도 재검증이 필요하다.
2. LLM은 코드를 인용할 때 **구조를 통째로 뒤집는 순수 환각**을 만들어낼 수 있다 — 반드시 원본과 직접 대조해야 한다.
3. Judge가 사람도 몰랐던 사실(git 커밋 이력)을 찾아내는 건, **"확인 가능한 근거"를 요구하도록 설계했기 때문**이지 우연이 아니다.
4. 여러 번 재현되는 결함은 **judge로 매번 잡기보다, 원인을 프롬프트 자체에 못박아 원천 차단**하는 게 낫다.
5. LLM-as-judge의 진짜 가치는 **개별 판정이 아니라 반복 실행에서 드러나는 패턴을 찾는 것**이다.
6. Judge도 같은 모델 계열이라 **원 리뷰어와 같은 맹점을 공유할 위험**이 있다는 걸 항상 염두에 둬야 한다.
