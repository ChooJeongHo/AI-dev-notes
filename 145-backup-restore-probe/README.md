# 145 - 141일차 `/code-review` 지적 F1·F2를 에뮬레이터의 진짜 Room 메모리 DB에서 임시 테스트 1개(N=3, 2메서드)로 실행했더니 같은 백업을 2번 가져오면 시청 기록 행이 3→6으로 늘고, 복원 1회 뒤 장르 행은 0(평소 저장 경로 대조는 6)이었다(양성 대조 통과, 예측 5개 중 4개 성립, 작업 12분 39초, 앱 코드 변경 0, DEVLOG PR #208)

**141일차에 `/code-review`가 낸 지적 5건 중 "코드로 직접 확인할 수 있다"고 남겨 둔 두 건을 실행해서 확인했다.** F2는 "같은 백업을 두 번 가져오면 시청 기록이 중복된다", F1은 "복원이 장르 행(`watch_history_genre`)을 만들지 않는다"는 지적이다. 기존 `BackupRepositoryImplTest`는 `withTransaction`까지 모킹해서 행 수를 볼 수 없고 JVM Room 테스트 기반도 없어서, 연결된 기기가 없는 상태에서 읽기 전용 에뮬레이터(API 36)를 띄워 임시 계측 테스트 1개를 `connectedDebugAndroidTest` 클래스 필터로 1회 돌렸다(앱 소스·기존 테스트는 수정하지 않고 임시 파일은 실행 뒤 삭제). 측정 항목·재현 기준·예측 5개는 실행 전에 해시로 고정했고, 평소 저장 경로로 같은 기록을 저장하는 양성 대조로 하네스를 검증했다. 결과는 T1(F2) `watch_history` 행 3→6, T2(F1) 복원 1회 뒤 `watch_history_genre` 행 0·`getGenreCounts()` 빈 목록, 양성 대조 3행·장르 6행이며, 고정 기준을 적용하면 둘 다 "재현됨"이다. 이것은 **지적이 서술한 동작이 실행에서 관찰됐다는 뜻이지 결함 여부 판정이 아니다**(141일차 판정은 건드리지 않았다). 한 번의 에뮬레이터 실행이고 N=3 가공 데이터라는 한계가 있다. 예측은 5개 중 4개 성립(P5 시간만 불성립)이고, 시간 예측이 빗나간 직접 이유는 측정하지 않았다. 작업은 12분 39초(143·144일차 중 최단)지만 결정 화면 1의 49분 16초(질문 뒤 사용자가 돌아오기까지의 시간이 대부분) 때문에 총 100분 1초가 걸렸다. 저장소 변경은 DEVLOG 한 절(+9/−0, PR #208 병합 `d8bcbd4a`)뿐이다.

## 무엇을 했나

JVM 기반(Robolectric, `room-testing`)은 없고 `adb` 기기는 0대라, 에뮬레이터 + Gradle connected 테스트(방법 A)를 골랐다. 테스트 소스(sha256 `fb0a759f…`)와 예측·재현 기준(`prediction145.json`)을 고정했다.

1. **(정정) N=3을 N=30으로 잘못 읽었다.** 단계 0 검토에서 "예측과 맞지 않는다"며 확인 요청을 붙였다. 실제로는 N=3이 맞았고 영향은 지시 한 줄이 늘어난 것뿐이다.

4. **(정정) 지시서의 규칙 충돌을 내가 만들었다.** "삭제는 리터럴 경로만"과 "화면·파일에 계정명 금지"가 충돌하게 쓴 것이고, 단계 2 검토에서 삭제 줄 노출 허용으로 정리했다.
5. **(공개) 추천이 바뀐 곳이 있고 선택은 모두 내 추천을 따랐다.** 144일차에는 최종 `times.tsv` 복사를 안 하는 쪽을 추천했지만 이번엔 승인 화면에 항목으로 올라와 복사를 추천했다.

## 오늘 배운 것

- **AI 리뷰 지적의 동작 서술을 실행으로 확인할 수 있었다(관찰).** "같은 백업을 두 번 가져오면 행이 늘어난다"(3→6)와 "복원은 장르 행을 만들지 않는다"(0, 평소 경로는 6)가 실행 결과와 일치했다. 다만 이 일치는 결함 판정이 아니고 N=3 한 번의 실행이다.
- **양성 대조가 있어서 0을 해석할 수 있었다.** 대조 장르 행이 6이라서 "복원 1회 후 장르 행 0"이 하네스 문제가 아님을 알았다(대조가 0이었다면 T2는 해석하지 않기로 했다).
- **사전 고정한 재현 기준이 판정 문장을 대신했다.** "재현됨"이라는 말은 고정 기준을 적용한 출력이고, 결함 여부는 따로 둘 수 있었다.
- **코드를 읽고 세운 예측은 맞히기 쉽다.** 95~98% 예측 4개가 모두 적중했고, 정보는 "코드 읽기와 실행이 맞는다"는 것뿐이다. 반면 시간 예측은 환경(에뮬레이터 부팅, 빌드 캐시) 가정이라 빗나갔고, 그 이유를 측정하지 않았으면 "측정하지 않았다"로 적는 것이 맞았다.
- **근거 없이 옮긴 설명을 지시에 넣으면 기록에 남을 뻔한다.** 내가 옮긴 "빌드 캐시"를 DEVLOG에 넣지 않고 정정한 처리가 맞았다. 설명을 옮기기 전에 출처를 확인해야 한다.
- 총 시간의 대부분(74.5%)이 결정 화면 대기였고, 그중 화면 1의 49분이 가장 컸다. 작업·백그라운드를 줄여도 대기가 길면 총 시간은 줄지 않는다는 142~144일차 패턴이 그대로 반복됐다.
