# 073 - Stop Hook — "끝내기 전에 전체 점검" + 훅 3부작 완성

**테스트 없이 세션을 끝내려 하면 자동으로 막는 Stop Hook을 만들다가, "서브에이전트가 만든 파일은 메인 세션이 못 본다"는 더 근본적인 구조를 발견했다**

---

## 목적

053(PostToolUse) → 054(PreToolUse) → 071(PreToolUse+Subagent)에 이어, **훅 3부작의 마지막 조각인 Stop Hook**을 완성한다.
072일차 파이프라인에 "테스트 없이 작업을 끝내지 못하게" 하는 완료 조건을 강제로 걸어본다.

---

## 작업 1 — Stop Hook 설계

### 만든 파일 2개

| 파일 | 역할 |
|---|---|
| `.claude/hooks/lib/check_test_pairing.py` | 세션 transcript(JSONL)를 훑어서 판정하는 핵심 로직 |
| `.claude/hooks/stop-test-coverage-guard.sh` | bash 래퍼 — 판정 결과에 따라 exit 2로 차단 |

### 판정 로직 (100% 결정론적)

```
이번 세션 transcript에서:
  domain/*.kt 또는 presentation/**/*ViewModel.kt (src/main 한정)을
  Edit/Write/MultiEdit 한 적이 있는데,
  대응하는 테스트 파일(app/src/test/.../XxxTest.kt)이
  같은 세션에서 한 번도 Edit/Write/MultiEdit 되지 않았다면
  → 차단
```

> "테스트를 잘 짰는지"는 판단하지 않는다 — 오직 "같은 세션에서 테스트 파일이 건드려졌는가"라는 **사실 여부**만 transcript에서 기계적으로 확인한다. LLM 판단이 전혀 개입하지 않는다.

### 설계 재사용 — `is_target()` 함수 공유

071일차에 만든 `reconstruct_edit.py`의 `is_target()`(domain/ViewModel 판정 기준)을 그대로 import해서 재사용했다. **"domain 또는 ViewModel인가"를 판정하는 기준이 훅마다 따로 존재하면 서로 어긋날 위험**이 있기 때문에, 판정 로직 하나를 공유 모듈로 뺀 것.

## 작업 2 — 왜 이번엔 "차단"이 맞는가 (071일차와의 대조)

| | 071일차 (PreToolUse) | 073일차 (Stop, 오늘) |
|---|---|---|
| 판단 주체 | opus 모델이 코드를 읽고 판단 | Python 스크립트가 transcript를 grep하듯 확인 |
| 판단 성격 | **의견** (오탐 가능) | **사실 확인** (오탐 불가능) |
| 설계 | `permissionDecision: allow` + 정보 제공 | `exit 2` **차단** |

071일차에서 세운 원칙("결정론적 규칙만 차단, AI 판단은 정보 제공")을 그대로 적용하면 결론이 나온다: **"테스트 파일이 같은 세션에서 건드려졌는가"는 grep 수준의 사실 확인이라 오판 가능성이 0**이므로, 차단해도 안전하다.

### 무한 루프 방지 장치

```python
if stop_hook_active:  # 이미 한 번 이 훅에 막혔다가 재개한 상태
    pass  # 다시 막지 않고 통과
```

한 번은 강제로 멈춰서 고칠 기회를 주되, **영원히 막히지 않도록** 두 번째 시도부터는 통과시킨다.

## 작업 3 — 실전 테스트에서 발견한 더 중요한 한계

### 테스트 자체는 성공

`GetTrailerWatchStatusUseCase.kt`의 주석만 테스트 없이 살짝 수정 → 실제 세션 transcript로 훅을 직접 실행 → **정확히 감지, exit 2로 차단됨.**

### 그런데 서브에이전트가 만든 파일은 안 잡혔다

072일차에 `feature-implementer` 서브에이전트가 만든 `MarkTrailerWatchedUseCase.kt`, `DetailViewModel.kt` 같은 파일은 **이 훅이 전혀 감지하지 못했다.**

**원인:** `Agent` 도구로 위임한 작업의 Edit/Write는 **서브에이전트 자신의 별도 transcript에만 기록**되고, 메인 세션 transcript에는 "Agent를 호출했다"는 사실만 남는다.

```
메인 세션 transcript: "Agent(feature-implementer) 호출함" ← 이것만 보임
서브에이전트 자신의 transcript: 실제 Edit/Write 기록 ← 메인은 여기 접근 불가
```

→ 이 훅은 **"메인 루프가 직접 수정한 파일"만 감지**하고, **"구현자 서브에이전트에게 위임해서 만든 파일"은 놓친다.** CLAUDE.md에 알려진 제약으로 문서화.

## ★ 070~073을 관통하는 하나의 원인 — "에이전트 경계 = 상태 경계"

이번 시리즈에서 세 번 다른 모습으로 나타난 제약이 사실 같은 원인이었다.

| 일차 | 증상 | 근본 원인 |
|---|---|---|
| 070 | 새 Subagent가 세션 중간에 이름으로 안 불림 | Agent 레지스트리가 **세션 시작 시 고정** |
| 072 | 072일차와 동일 (반복 확인) | 위와 동일 |
| **073** | **서브에이전트의 Edit이 메인 transcript에 안 남음** | **transcript도 에이전트별로 분리** |

> **핵심 통찰:** Claude Code에서 "에이전트"라는 단위는 단순히 역할 분담이 아니라, **레지스트리·transcript 같은 상태(state)까지 서로 분리된 경계**다. 오케스트레이터(메인 세션)가 보는 세계와 서브에이전트가 보는 세계는 처음부터 나뉘어 있다.

## 작업 4 — PreToolUse / PostToolUse / Stop 3종 비교

| | PreToolUse | PostToolUse | Stop |
|---|---|---|---|
| **시점** | 도구 실행 **직전** | 도구 실행 **직후** | 메인 에이전트가 응답을 **끝내려는 순간** |
| **받는 정보** | `tool_input`만 (아직 미적용) | `tool_input` + `tool_result` (실제 결과) | 세션 `transcript_path` 전체 |
| **이 시리즈의 실례** | `pre-edit-architecture-review.sh` (071) | `.kt` 수정 시 Detekt 자동 실행 (053) | `stop-test-coverage-guard.sh` (073, 오늘) |
| **잘 맞는 판단 유형** | "이 변경을 적용하기 전에 미리 검토/차단해야 하나" | "방금 한 일이 부작용을 남겼나, 후속 조치가 필요한가" | "전체 세션을 놓고 봤을 때 완료 조건을 채웠나" |
| **차단 적합도** | 결정론적일 때만 차단(054), 판단이면 정보 제공(071) | 이미 실행이 끝나서 개입 불가 — 정보만 되먹임 | 결정론적이면 차단에 매우 적합 (exit 2 재시도 강제) |
| **한 줄 비유** | "하기 전에 조언" | "하고 나서 되짚기" | "끝내기 전에 전체 점검" |

## 070 → 071 → 072 → 073 시리즈 전체 흐름

```
070: 단일 Subagent 설계 (역할 하나, 권한으로 강제)
    ↓
071: 그 Subagent를 PreToolUse에 연결 (자동 사전검토)
     + "결정론적 차단 vs 확률적 정보 제공" 원칙 확립
    ↓
072: 여러 Subagent를 체이닝 (설계자→구현자→검증자)
     + "쪼개면 느릴 것"이라는 직관이 실측으로 뒤집힘
    ↓
073: Stop Hook으로 완료 조건 강제 (071 원칙을 다른 훅 타입에 재적용)
     + "에이전트 경계 = 상태 경계"라는 070/072/073 공통 원인 발견
```

## 오늘 배운 것 — 한 줄 정리

1. `Stop` 훅은 **세션 transcript 전체**를 볼 수 있어서, "이번 세션에서 뭘 했는지 종합 판단"에 적합하다.
2. "파일이 세션 중 건드려졌는가"처럼 **grep 수준의 사실 확인은 차단해도 안전**하다 — 071일차 원칙이 다른 훅 타입에도 그대로 적용됨을 확인.
3. **무한 루프 방지**는 `stop_hook_active` 플래그로 "한 번만 강제, 재시도부터는 통과"로 설계한다.
4. 판정 로직이 여러 훅에서 겹치면 **공유 모듈로 빼서 기준을 하나로 통일**해야 한다.
5. **서브에이전트가 만든 변경은 메인 세션의 transcript/레지스트리에서 보이지 않는다** — 이건 버그가 아니라 Claude Code의 "에이전트 경계 = 상태 경계"라는 근본 설계다.
6. PreToolUse="하기 전 조언", PostToolUse="하고 나서 되짚기", Stop="끝내기 전 전체 점검"으로 역할이 명확히 나뉜다.
