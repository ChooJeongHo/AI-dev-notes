## 목적

사용자의 요청은 두 가지였다. 첫째, 하루가 다 가는 것 같으니 짧게 걸리는 실험을 하고 싶다. 둘째, 처음 시작했을 때처럼 아직 안 써 본 새 기능이나 신규 기능을 써 보고 싶다. 그래서 두 가지를 함께 다뤘다.

1. **어떤 기능이 저장소에 없는지 확인했다**: 저장소 표(001~128)를 읽었고, `/goal`·`/code-review`·`/ultrareview`·Claude Security 플러그인·Routines·agent view·`/fork`·플러그인과 `claude plugin eval`·`/design`·Artifacts·CLI의 computer use가 한 번도 나오지 않았다(읽은 범위는 001~128이고 129~135는 확인하지 못했다. 136~140은 이 대화의 기록으로 확인했고 새 기능은 쓰지 않았다).
2. **예전 실험과 같은 틀로 다시 붙이면 짧고 의미가 분명하다고 판단했다**: 새 기능 + 이미 있는 기준선(003 리뷰 스킬, 010 PR 자동 리뷰)을 같은 틀로 붙이면 설계 단계가 줄고 "예전 방식보다 나은가"가 결과가 된다는 생각이었다. **이 판단은 절반만 맞았다.** 003·010에는 진짜 버그·오탐 판정과 비용·시간 기록이 없어 비교할 수 있는 값이 지적 수뿐이었다(단계 0에서 확인, 내 쪽 정정 1).
3. **세 가지 후보 중 `/code-review`로 정했다**: 단계가 "실행 → 판정 → 기록" 셋뿐이라 하루 안에 끝날 수 있고, 판정 틀(결과를 사람이 분류)을 재사용할 수 있고, 새 기능이라 호출 방법·출력 형식·비용·시간을 처음 재 볼 수 있기 때문이다(나머지 후보는 `/goal`, `claude plugin eval`).

**알고 싶었던 것**
- `/code-review`는 어떻게 호출하고, 무엇을 대상으로 하고, 어떤 형식으로 보고하는가(문서 확인).
- 병합된 PR 하나에서 몇 건의 지적을 하고, 시간과 비용은 얼마인가.
- 지적이 사람의 판정(A~D)으로 어떻게 나뉘는가.
- 예측(지적 3~8건, A 0~1건, 2~10분)이 맞는가.

**하지 않은 것**: 앱 코드 수정, `--fix`·`--comment` 사용, 클라우드 `ultra` 리뷰, 반복 실행, 여러 PR 비교, 지적 사항의 실제 수정. 대상 1개·판정자 1명·1회 실행이라 결과는 "이 기능이 정확하다/부정확하다"가 아니라 "이 기능의 사용법과 한 번의 출력"이다.

## 개념 정리 (나중에 다시 볼 것)

**1. `/code-review` 쓰는 법**
- 세션 안에서 `/code-review` 또는 별칭 `/review`, 비대화형으로는 `claude -p "/code-review ..."`. `-p`나 Agent SDK에서는 응답에 결과가 들어 있다.
- 대상은 PR 번호, 브랜치, 경로, 리비전 범위로 지정한다. 강도(`low`~`max`)를 쓰면 이후에도 마지막에 입력한 강도를 재사용한다.
- `--fix`(적용)·`--comment`(GitHub 인라인)는 이번에 쓰지 않았다. 출력은 text/JSON이고 호스트에 따라 `ReportFindings`(파일·줄·요약·`correctness` 같은 범주, 최대 32건)로 받을 수도 있다. 모델이 매긴 심각도 필드는 문서에 없다.
- 터미널 세션에서는 백그라운드 서브에이전트로 돌고 `-p`에서는 포그라운드다. 사용량은 요금제(또는 API)로 잡힌다. `ultra`(클라우드)는 별도 기능이다. 프로젝트의 `CLAUDE.md`를 따르고 `REVIEW.md`는 아니다.

**2. 스쿼시 병합된 PR을 리뷰하는 법**: 스쿼시 병합은 PR 전체가 커밋 하나다. 그래서 `<병합커밋>^..<병합커밋>` 범위가 곧 PR 전체이고, 체크아웃·리셋·스태시 없이 읽기만으로 대상을 고정할 수 있다. 같은 이유로 병합 뒤 로컬 브랜치는 `git branch -d`가 "not fully merged"로 실패하고 `-D`가 필요하다(브랜치 커밋이 `main` 계보에 없다). 안전 확인은 "브랜치 트리 == `main` 트리"로 한다.

**3. JSON으로 비용·토큰 재기**: `--output-format json`의 최상위 `usage`·`num_turns`는 0이고(`local_command=code_review`) 실제 값은 `modelUsage`와 `total_cost_usd`에 있다. 읽을 위치를 모르면 0을 사실로 오해한다.

**4. 읽기 전용 허용 목록**: `--allowedTools`에 읽기 명령(`git show·diff·log·rev-parse·cat-file·ls-tree`, `Read·Grep·Glob`)만 열고 `--disallowedTools "Edit,Write,NotebookEdit"`로 막는다. `git status`는 인덱스를 갱신하므로 뺐다.

**5. A~D 구조와 "확신 없음 칸 없음" 문제**: 라벨은 A 진짜 버그, B 타당하지만 버그 아님, C 오탐, D 판단 불가다. 판정자가 확신이 없을 때 갈 곳이 D뿐인데 D는 "코드 읽기만으로 확정 불가 + 사유"라서 B로 들어가기 쉽다. 그러면 B가 "맞는데 결함은 아니다"와 "잘 모르겠다"를 섞어 담고 A 비율이 가려진다. 라벨 기준에는 "PR이 새로 만든 결함인지"도 없다.

**6. 작은 표본의 구간**: n=5에서 95% Clopper-Pearson은 k=0이 0~52.2%, 1이 0.5~71.6%, 2가 5.3~85.3%, 3이 14.7~94.7%, 4가 28.4~99.5%, 5가 47.8~100%다. 5건으로는 어떤 비율도 좁힐 수 없다.

**7. 예측 보정**: 확신을 "낮음"으로 적은 P2는 맞았지만 해석이 모호하고, "매우 낮음"으로 적은 P3은 27초 대 2~10분으로 크게 빗나갔다. 사전 고정(해시)은 사후 합리화를 막는 장치다.

**8. zsh와 bash의 차이**: zsh는 따옴표 없는 변수를 단어로 쪼개지 않고, `$MC:a`는 수식어로 읽는다. macOS `grep -E`는 `\b`를 지원하지 않는다. 검색이 0건이면 같은 방식으로 알려진 값을 찾는 양성 대조를 먼저 본다.

**9. 컨텍스트 한도**: 보고가 길어지면 79%, 83%에서 `/compact` 요구가 나온다. 결과를 파일에 남겨 두면 압축 뒤에도 이어갈 수 있다.

**10. 구독 대 API 과금**: JSON의 `total_cost_usd`는 API 단가 환산값이다. 구독 한도에서 얼마나 소모됐는지는 이 세션에서 확인하지 못했다.
