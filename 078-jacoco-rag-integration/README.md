# 078 - "원리적으로 답 못한다"를 실제로 풀다 — RAG에 JaCoCo 커버리지 통합

**076/077일차에 두 번이나 "이 질문은 이 도구가 원리적으로 답할 수 없다"고 정직하게 인정했던 질문을, 코퍼스 자체를 확장해서 실제로 풀어냈다**

---

## 목적

076일차 Q3("테스트 커버리지가 낮은 Repository가 어디야?")는 RAG가 "이 데이터로는 답할 수 없다"고 정직하게 한계를 인정한 사례였다. 077일차(Voyage로 교체)에서도 같은 한계가 그대로였다.

078일차는 이 한계의 **진짜 원인**(임베딩 품질이 아니라 애초에 커버리지 데이터가 인덱스에 없었던 것)을 짚고, **코퍼스 자체를 확장**해서 실제로 풀어본다.

## JaCoCo 커버리지 청크 통합

### 새 청크 타입 추가

```kotlin
enum class ChunkType {
    CLASS,
    FUNCTION,
    FILE_OVERVIEW,
    /** JaCoCo 커버리지 리포트에서 파생된 파일당 라인 커버리지 요약 - 소스 코드가 아닌 메트릭 데이터 */
    COVERAGE_METRIC,
}
```

### 파이프라인

```
./gradlew jacocoTestReport
    ↓
jacocoTestReport.xml 파싱 (JacocoCoverageParser)
    ↓
파일당 "FavoriteRepositoryImpl.kt 라인 커버리지 32%, 미커버 라인 14개"
같은 자연어 문장으로 합성
    ↓
COVERAGE_METRIC 타입 청크로 만들어서 같은 CodeChunk 테이블에 소스 청크와 함께 저장
```

### 스코프 일관성 유지

```kotlin
/** indexedPaths 스코프 밖의 파일에 대한 커버리지 청크는 만들지 않는다
 *  (소스 스코프와 항상 일치시킴) */
```

소스 코드가 인덱싱 안 된 파일의 커버리지 청크만 붕 떠 있으면 안 되므로, **같은 경로 필터를 소스와 메트릭 양쪽에 동일하게 적용**했다.

## 설계 변화 — "코드 검색"에서 "코드+메트릭 통합 검색"으로

### 1. 청크 타입의 성격이 바뀌었다

기존 `CLASS`/`FUNCTION`/`FILE_OVERVIEW`는 전부 "소스 코드를 그대로 잘라낸 것"이었다. `COVERAGE_METRIC`은 소스가 아니라 **소스에 대한 메타데이터(빌드 산출물)를 자연어 문장으로 합성한 것**이다. 청크 생성 로직이 "파일을 파싱"에서 "이종 데이터를 텍스트로 정규화"로 한 단계 넓어졌다.

### 2. 같은 벡터 공간에 이종 문서가 공존한다 — 경쟁 관계 발생

코드 청크와 커버리지 청크가 같은 테이블·같은 벡터 공간에 있다 보니, 검색 시 서로 경쟁한다. 이번엔 "커버리지" 질문에서 `COVERAGE_METRIC`이 코드 청크를 압도적으로 밀어낸 게 잘된 사례였지만, **반대로 코드 질문에 커버리지 청크가 섞여 나올 위험**도 생겼다 (이번엔 안 나왔지만 스코프가 넓어지면 가능).

> 다음 개선 지점: `chunkType` 필터를 검색 파라미터로 노출.

### 3. 데이터 신선도(freshness) 문제가 새로 생겼다

소스 코드 청크는 파일이 안 바뀌면 영원히 유효하지만, **커버리지 청크는 테스트를 새로 돌릴 때마다 stale해진다.** 지금은 인덱싱 시점에 JaCoCo XML을 1회성으로 읽는 구조라, "최신 커버리지"를 보장하려면 `jacocoTestReport` → `ragIndex` **순서 의존성**이 암묵적으로 생겼다 — 코드 청크에는 없던 제약이다.

### 4. 스코프 필터링을 소스·메트릭 양쪽에 동일하게 적용해야 한다

`-Ppaths`로 샘플링할 때 커버리지 청크도 같은 경로 프리픽스로 걸러야, 소스와 메트릭이 "같은 파일 집합"을 가리킨다는 일관성이 안 깨진다.

### 5. ★ 가장 중요한 일반화 — "코퍼스 밖의 사실은 절대 모른다"의 해법은 임베딩이 아니라 확장

> 076/077에서 "원리적으로 답 불가"였던 이유는 "RAG는 인덱싱된 코퍼스 밖의 사실은 절대 모른다"는 근본 제약이었다. 그 해법은 **더 똑똑한 임베딩이 아니라 코퍼스 자체를 확장하는 것**이었다.

이건 일반화 가능한 패턴이다:
- "어떤 화면이 제일 느려?" → Baseline Profile/성능 프로파일 데이터를 같은 방식으로 청크화
- "어떤 의존성이 오래됐어?" → Dependabot/버전 카탈로그 데이터를 같은 방식으로 청크화

## 오늘 배운 것 — 한 줄 정리

1. RAG가 "모른다"고 답한다면, 먼저 확인할 건 **임베딩 품질이 아니라 "그 정보가 애초에 인덱스에 있는가"**다.
2. 코사인 유사도는 코퍼스 크기가 바뀌어도 **기존 청크의 점수 자체는 변하지 않는다** — 새 후보가 추가될 뿐이다.
3. 서로 다른 종류의 데이터(코드 vs 메트릭)를 같은 벡터 공간에 넣으면 **검색 경쟁**이 생긴다 — 타입 필터가 필요해질 수 있다.
4. 빌드 산출물(JaCoCo 등)을 인덱싱하면 **데이터 신선도 문제**가 새로 생긴다 — 소스 코드에는 없던 "순서 의존성"이다.
5. 스코프를 샘플링할 때는 **연관된 모든 데이터 종류에 동일한 필터**를 적용해야 일관성이 깨지지 않는다.
6. "코퍼스를 확장하면 새로운 질문에 답할 수 있다"는 패턴은 **일반화 가능하다** — 성능 데이터, 의존성 데이터 등 다른 메트릭에도 같은 방식을 적용할 수 있다.
