# 082 - N+1 TMDB 검색 문제 해결 — "우연히 통과한 테스트"를 발견하다

**081일차에서 "범위 밖"으로 미뤄뒀던 문제를 해결했는데, 그 과정에서 기존 테스트 9개가 실제로는 검증하지 않으면서 "우연히" 통과하고 있었다는 걸 발견했다**

---

## 목적

081일차 KOFIC 연동에서 "TOP 10마다 TMDB 검색 1회씩 = N+1 문제"를 명시적으로 범위 밖에 남겨뒀다. 082일차는 그 미뤄둔 문제를 실제로 해결한다 — 070~074 시리즈의 "설계 → 한계 인정 → 다음날 해소" 패턴과 같은 완결 구조.

---

## 작업 1 — 핵심 설계: "캐시를 한 번만 읽어서 메모리에서 매칭"

### 잘못된 접근을 피한 것이 핵심

N+1을 해결하는 방법이 "TOP N개마다 캐시 쿼리"라고 생각하기 쉬운데, 이러면 **네트워크 호출이 DB 쿼리로 바뀔 뿐 여전히 N번 호출**이라 근본 해결이 아니다.

```kotlin
// 핵심 아이디어: 캐시 전체를 한 번만 읽어서 메모리에 올려두고, 그 안에서 매칭
// → 순위 범위를 넓혀도(TOP 10 → TOP 50) 로컬 DB 쿼리 횟수는 항상 1회로 고정
@Query("SELECT * FROM cached_movies WHERE category IN (:categories)")
suspend fun getAllByCategories(categories: List<String>): List<CachedMovieEntity>
```

```kotlin
suspend operator fun invoke(targetDate: String? = null): List<BoxOfficeMovie> = coroutineScope {
    val boxOfficeList = ...
    val cachedMovies = getCachedMoviesSnapshot()  // 딱 1번만 호출

    boxOfficeList
        .map { boxOffice -> async { BoxOfficeMovie(boxOffice, findMatch(boxOffice.movieName, cachedMovies)) } }
        .map { it.await() }
}

private suspend fun findMatch(movieName: String, cachedMovies: List<Movie>): Movie? =
    cachedMovies.firstOrNull { titleMatches(it.title, movieName) } ?: findMatchFromNetwork(movieName)
```

**로컬에서 못 찾을 때만 네트워크로 폴백** — 캐시 히트면 네트워크 호출 자체가 발생하지 않는다.

## 예상 밖 발견 — "우연히 통과한 테스트"

새 코드를 테스트하려고 기존 테스트를 돌렸는데, **기존 9개 테스트가 새 `getCachedMoviesSnapshot()` 메서드를 스텁(mock 설정)하지 않았는데도 그냥 통과했다.**

### 원인 규명

```
새 메서드 호출을 suspendRunCatching { }으로 감쌌음
    ↓
MockK가 스텁 안 된 메서드 호출 시 예외를 던짐
    ↓
그 예외를 suspendRunCatching이 "캐시 조회 실패"로 해석
    ↓
조용히 emptyList()로 폴백
    ↓
결과적으로 "캐시 미스 → 네트워크 폴백" 경로를 타면서 우연히 통과
```

> **이건 회귀는 아니지만 의도치 않은 우연이다.** 실제로 무엇을 테스트하는지 명시적으로 드러나지 않으면, 나중에 누군가 이 캐치 로직을 건드렸을 때 테스트가 **"의도한 대로" 깨지는 게 아니라 "우연히" 깨지게 된다.**

**조치:** 기존 테스트에 명시적 스텁(`coEvery { getCachedMoviesSnapshot() } returns emptyList()`)을 추가해서, "캐시가 비어있어서 네트워크로 간다"는 경로가 **의도된 것으로 명확히 드러나게** 했다.

> **일반화된 교훈:** 테스트가 통과한다고 해서 "그 테스트가 의도한 걸 검증했다"고 확신하면 안 된다. 예외 처리 코드(`try-catch`, `runCatching` 등)가 있는 곳에서는 **"실패해서 폴백된 것"과 "성공해서 그 값이 나온 것"을 구분**해야 한다.

## 작업 2 — 새로운 테스트 케이스 6개

| 테스트 | 검증 내용 |
|---|---|
| 캐시 히트 시 네트워크 검색 0회 | `coVerify(exactly = 0) { searchMoviesOnce(any()) }` |
| 제목 정규화 매칭 (공백/구두점) | "탑건: 매버릭" ↔ "탑건:매버릭" 매칭 확인 |
| 캐시 미스 → 네트워크 폴백 | 캐시에 없으면 정확히 1회 네트워크 검색 |
| **캐시 스냅샷은 항상 1회만 조회** | 리스트 크기(10개)와 무관하게 `getCachedMoviesSnapshot()` 정확히 1회 |
| 부분 히트 (일부는 캐시, 일부는 네트워크) | 같은 실행 안에서 섞여도 각각 올바르게 처리 |
| 캐시 조회 자체가 실패해도 네트워크로 폴백 | 안전망이 이중으로 작동 |

## 작업 3 — 성능 실측 (Before vs After)

OkHttp의 호스트당 동시 연결 5개 제한을 흉내낸 시뮬레이션 기준:

| TOP N | Before (캐시 없음) | After (캐시 80% hit) |
|---|---|---|
| 10 | 335ms / 네트워크 10회 | **167ms / 2회** |
| 30 | 958ms / 30회 | **314ms / 6회** |
| 50 | 1601ms / 50회 | **323ms / 10회** |

**TOP 50 기준 Before는 5배 느려지는데(335ms→1601ms), After는 거의 그대로(167ms→323ms)** — N+1이 실제로 해소됐다는 걸 수치로 확인.

## 작업 4 — 실기기 검증, 이번엔 로그캣으로

081일차에서 "컴파일/테스트 통과만 믿지 말고 직접 화면으로 확인"이라는 교훈을 얻었는데, 오늘은 **화면 렌더링뿐 아니라 실제 네트워크 호출 횟수까지 로그캣으로 직접 확인**했다.

```bash
adb logcat -c
adb shell am force-stop com.choo.moviefinder
adb shell am start -n com.choo.moviefinder/.MainActivity
# ... KOFIC API 호출 로그 확인
```

**결과:** 실제 KOFIC TOP 10 중 **네트워크 검색은 5건만 발생**(나머지 5건은 로컬 캐시 히트), 경고/에러 없음 — **코드가 실제로 프로덕션에서 캐시 우선 경로를 타는 것까지 확인**했다.

> **081일차와의 차이:** 081은 "화면이 정상적으로 보이는가"를 스크린샷으로 확인했고, 082는 "내부적으로 의도한 최적화가 실제로 작동하는가"를 로그로 확인했다 — 실기기 검증도 목적에 따라 다른 방법이 필요하다.

## 작업 5 — 리스크를 정직하게 짚기

| 리스크 | 실제 영향 |
|---|---|
| 캐시 신선도 (1시간마다 갱신) | 방금 개봉한 영화는 캐시에 없어서 자동으로 네트워크 폴백 — 정확도 저하 없음, 그 항목만 최적화 혜택 못 받음 |
| 캐시 커버리지 (now_playing+popular만) | trending/upcoming 전용 영화는 항상 네트워크 — **기존과 동일, 회귀 아님** |
| 오탐 가능성 | 기존과 동일한 제목 문자열 매칭 — **새로 만든 리스크 아님**, 원래 있던 것 |
| 약간 오래된 부가정보 | 캐시된 평점/줄거리가 최대 1시간 전 스냅샷일 수 있음 |
| 캐시 테이블 크기 | 스크롤을 많이 한 경우 스냅샷 로드 비용 증가 가능(실사용에선 미미할 것으로 예상) |

> **패턴 발견:** 여러 리스크 중 상당수가 "새로 만든 문제가 아니라 원래 있던 리스크"라는 걸 명시적으로 구분했다 — 개선 작업이 새로운 위험을 얼마나 추가했는지를 정확히 짚는 게 정직한 정리다.

## 오늘 배운 것 — 한 줄 정리

1. N+1 문제 해결의 핵심은 "쿼리를 줄이는 것"이 아니라 **"한 번만 읽어서 메모리에서 처리하는 것"**이다.
2. **테스트가 통과한다고 해서 의도한 걸 검증했다는 보장은 없다** — 예외 처리 코드가 있으면 "실패해서 폴백" vs "성공해서 나온 값"을 구분해야 한다.
3. Mock 프레임워크에서 스텁 안 된 메서드의 예외가 **다른 안전장치(runCatching 등)에 삼켜지면 테스트가 우연히 통과할 수 있다** — 명시적 스텁이 필요한 이유.
4. 성능 개선은 "느낌"이 아니라 **Before/After 수치로 증명**해야 설득력이 있다.
5. 실기기 검증은 화면(UI)뿐 아니라 **로그(내부 동작)까지 확인**해야 완전하다.
6. 리스크를 정리할 때는 **"새로 생긴 리스크"와 "원래 있던 리스크"를 구분**해서 정직하게 밝히는 게 좋은 문서화다.
