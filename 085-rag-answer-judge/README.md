# 085 - LLM-as-judge를 RAG에 적용 — "겉모습은 재사용됐지만 알맹이는 절반만 재사용됐다"

**080일차 judge 패턴을 RAG 답변 검증에 적용했더니, 검증하는 사람(Claude) 자신이 저지른 실수를 judge가 실제로 잡아냈다 — 그리고 079일차의 함정(유사도≠랭킹)을 정확히 재현한 오답도 정확히 40점(감점 상한)으로 잡아냈다**

---

## 목적

080일차의 `review-judge`(코드 리뷰 검증)가 **다른 도메인(RAG 답변 검증)에도 재사용 가능한 범용 패턴이었는지** 실증한다. 083일차에서 KOFIC 설계의 재사용성을 실증했던 것과 같은 정신 — "재사용 가능하게 설계했다"는 주장은 실제로 다른 곳에 적용해봐야 검증된다.

---

## 작업 1 — rag-answer-judge 설계

`.claude/agents/rag-answer-judge.md` — (질문, 검색된 청크, 생성된 답변) 세트를 받아 독립적으로 재조사하는 감사관.

### 080일차와 다른, 새로 추가한 핵심 기준

> 079일차에서 발견한 문제(유사도 1위가 실제 랭킹 1위와 다를 수 있음)처럼, "수치 비교/랭킹"이 필요한 질문에 RAG가 검색 결과만으로 부정확한 확답을 했는지 특히 확인

이 기준은 `review-judge`엔 아예 없던 개념이다 — 코드 리뷰에는 "랭킹을 착각하는" 유형의 실패가 없기 때문이다.

## 작업 2 — 실전 재검증 (076~079일차 로그를 못 찾아서 라이브로 재실행)

076~079일차의 실제 실행 로그는 git 이력에서 못 찾았다. **지어낸 과거 기록으로 채우지 않고, 정직하게 오늘 라이브로 다시 실행**하는 쪽을 택했다.

### 전체 재인덱싱에서 예상 밖 발견

```
./gradlew :tools:codebase-rag:ragIndex
    ↓
54분 소요, Voyage API 149회 호출, 15만 토큰 소모
    ↓
예상: 로컬 해싱 임베딩(무료)이 쓰일 줄 알았음
실제: voyage-code-3(실제 시맨틱 임베딩)가 사용됨
```

셸 환경변수 체크로는 API 키가 없어 보였는데, `ProjectConfig`가 **`local.properties`에서 직접 키를 읽는 구조**였다 — 077일차에 설계해둔 폴백 메커니즘이 조용히 잘 작동하고 있었다는 뜻이기도 하다.

## Q1 — "TMDB 인증은 어떻게 되어 있어?" — 검증자 자신의 실수를 judge가 잡다

**68/100, "재검색·재생성 필요."**

> 답변을 쓰던 Claude가 검색된 청크 5개 중 3개가 `COVERAGE_METRIC`(코드 없이 커버리지 %만 담긴 청크)인 걸 보고도, **직접 소스 파일을 따로 Read해서 알고 있던 내용을 마치 "검색된 컨텍스트에서 읽은 것"처럼 답변에 섞어 넣었다.**

judge는 이걸 정확히 짚어냈다 — "컨텍스트에 없는 내용은 추측하지 말라"는 시스템 프롬프트 규칙 위반. 게다가 진짜 정답에 가까운 청크(`NetworkModule.kt`의 API 키 인터셉터)는 top-5에 아예 안 들어와서 답변에서 통째로 빠졌고, 엔드포인트 개수도 4개로 잘못 셌다(실제 5개).

> **의미:** 이건 RAG 시스템의 결함이 아니라 **검증자 스스로 저지른 방법론 위반**이었다. judge가 검증 대상뿐 아니라 검증자 자신의 실수까지 잡아냈다는 게, judge가 설계대로 정확히 작동한다는 강력한 증거다.

## Q2 — "어떤 화면이 제일 느려?" — 079일차 함정을 정면으로 통과

**97/100, "신뢰 가능."**

이번엔 청크 수치만으로 정직하게 답변을 작성했다. judge가 특별히 확인한 것: 검색 유사도 2위였던 `FavoriteFragment`를, 답변이 실제 성능 수치 기준으로는 4위(가장 빠른 축)로 **올바르게 재배치**했는지 — 정확히 재배치되어 있었다.

> **079일차와의 연결:** 079일차에서 "유사도 1위 ≠ 실제 랭킹 1위"라는 근본 한계를 발견했는데, 오늘은 그 함정을 실제로 피해간 좋은 답변 사례를 확보했다.

---

## Q3 — 의도적 오답 테스트: 유사도=랭킹 착각을 일부러 재현

**정확히 40/100 — 감점 상한선에 걸림.**

"관련도 순위를 보면 ... 두 번째로 나타나므로"라는 문장으로, **유사도 순위를 실제 성능 순위인 것처럼 혼동**하는 답변을 의도적으로 만들었다. judge가 이 문장 자체를 답변의 자백으로 지목하며 정확히 잡아냈다.

**judge의 정교한 구분이 인상적인 지점:** "검색 자체는 완벽했다(재현율 100%)"와 "문제는 생성 단계에만 있다"를 명확히 나눠서 판정했다 — 검색과 생성 중 **어디가 잘못됐는지까지 구분**하는 진단이었다.

| 케이스 | 점수 | 판정 |
|---|---|---|
| Q1: TMDB 인증 (검증자가 컨텍스트 밖 지식을 섞음) | 68/100 | 재검색·재생성 필요 |
| Q2: 어떤 화면이 제일 느려 (정직하게 청크만으로 작성) | 97/100 | 신뢰 가능 |
| Q3: 어떤 화면이 제일 느려 (의도적 오답 — 유사도=랭킹 착각) | 40/100 | 재생성만 필요 (검색은 정상) |

## 작업 4 — 정직한 재사용성 평가

### 그대로 재사용된 것 (스캐폴딩)

- "산출물을 의심하고 원본을 직접 재검증한다"는 감사관 철학
- 4개 기준 × 25점 = 100점 채점 구조
- **감점 상한 규칙** — 이번 오답 테스트에서 정확히 40점이 나온 게, 이 규칙이 그대로 작동한 증거
- Output_Format 표 형태, "신뢰 가능/재작업 필요" 이분 판정 구조

### 새로 설계해야 했던 것

| 항목 | 왜 review-judge로는 안 풀렸나 |
|---|---|
| 랭킹/수치비교 정확성(기준 3) | review-judge엔 대응하는 개념 자체가 없음 — 이번 테스트에서 실제로 가장 크게 작동한 기준 |
| 청크 타입별 지식 (CLASS/COVERAGE_METRIC/PERFORMANCE_METRIC) | review-judge는 파일 전체를 읽으면 되니 "이 청크엔 애초에 소스코드가 없다"는 구분 자체가 필요 없었음 |
| 주어진 입력 밖에서 정답 소싱 | RAG는 정답 소스가 청크 하나가 아니라, 원본 파일이나 외부 데이터(JSON 등)까지 직접 찾아가 재계산해야 하는 경우가 있음 |

**결론:** 겉모습(포맷, 채점 골격, cap 규칙)은 거의 그대로 재사용됐지만, **"무엇을 검증하는가"의 알맹이는 RAG 시스템 내부(청크 형식, 임베딩 제공자, 외부 데이터 소스)를 새로 조사해서 설계해야 했다.** 재사용은 절반의 이야기였고, 나머지 절반은 새 도메인 조사였다.

## 오늘 배운 것 — 한 줄 정리

1. Judge 패턴을 다른 도메인에 옮길 때 **"채점 구조(포맷)"와 "무엇을 검증할지(도메인 지식)"는 분리해서 재사용성을 평가**해야 한다.
2. 좋은 judge는 **검증 대상뿐 아니라 검증자 자신의 실수**도 잡아낼 수 있다 — 이번엔 실제로 그랬다.
3. "검색은 완벽했지만 생성이 틀렸다"처럼, **문제가 파이프라인의 어느 단계에 있는지까지 구분**하는 게 좋은 진단이다.
4. 과거 로그를 못 찾았을 때 **지어내지 않고 정직하게 라이브로 재실행**하는 게 맞는 선택이었다.
5. Judge의 **재현성(같은 입력 → 같은 점수)을 실제로 재검증**해야 회귀 테스트로 신뢰할 수 있다 — 한 번 맞았다고 항상 맞는 게 아니다.
6. 환경변수만으로 설정을 확인하면 놓치는 게 있다 — `local.properties` 같은 다른 설정 경로도 실제로 확인해야 한다.
