# 091 - 기존 스킬로 검증하기 — `/material3-design-validator`

**089일차에 세운 계획대로 두 번째 검증 스킬을 실행 — 086일차 Glance 위젯의 다크모드 대응이 이미 잘 되어 있었음을 확인하고, 진짜 이슈 1건만 즉시 수정했다**

---

## 목적

089일차에 계획한 검증 스킬 3부작(network-layer-validator → material3-design-validator → proguard-validator)의 두 번째. 086일차에 새로 도입한 GlanceTheme이 앱 전체 Material3 설정과 잘 맞는지 확인하는 타이밍이다.

---

## 검증 결과 — 2개 이슈 발견, 실제로 고칠 건 1개뿐

| 이슈 | 위치 | 성격 |
|---|---|---|
| 타이포그래피 하드코딩 (textSize) | item_review.xml 4곳(34/45/72/82번 줄) | 실질 이슈 — 조치 필요 |
| Theme.MaterialComponents.DayNight.NoActionBar (순수 Material3 테마 아님) | themes.xml:3 | 정보성 — CLAUDE.md에 문서화된 의도적 선택, 실질 이슈 아님 |

### 검증 도구가 스스로 걸러낸 오탐들

| 항목 | 왜 문제가 아닌지 |
|---|---|
| 위젯 XML 5개의 textSize 하드코딩(17건) | RemoteViewsService/AppWidgetProvider 기반 클래식 위젯은 런처 프로세스에서 렌더링되어 ?attr/textAppearance 테마 참조를 안정적으로 지원하지 않음 — 086일차에서 배운 "홈 화면은 다른 프로세스" 제약과 정확히 같은 이유로 하드코딩이 정상 관례 |
| BoxOfficeWidgetContent.kt의 Color(0xFF...) 3건 | 086일차 Glance 위젯이 ColorProvider(day=..., night=...) 패턴으로 다크모드 대응을 이미 해둔 상태 — 검증하려던 대상이 실제로 정상이었음을 확인 |
| colors.xml의 색상 상수 정의 | 색상 리소스 파일 자체는 하드코딩이 정상 위치 |
| values-night/ 존재 | 다크모드 테마 정상 구성됨 |

> 오늘 검증의 원래 목적(086일차 Glance가 다크모드에 잘 대응하는지)이 통과됐다. 검증 도구가 위젯 XML/Glance 코드의 색상·텍스트 하드코딩을 "이슈"로 뭉뚱그리지 않고, 각각 왜 정상인지 근거를 들어 걸러낸 게 오늘 결과의 핵심이다.

## 즉시 수정 — item_review.xml

textSize 하드코딩 4곳을 Material3 텍스트 스타일 속성으로 교체했다.

```xml
<!-- Before -->
android:textSize="14sp"

<!-- After -->
style="?attr/textAppearanceBodyMedium"
```

**검증:**
1. 컴파일 확인 — 정상
2. 실기기로 리뷰 화면 확인 — 정상 (089일차까지 계속 지켜온 "실기기로 직접 확인" 원칙 재적용)
3. 다크모드에서도 정상 렌더링 확인

## 두 번째 이슈는 왜 안 고쳤나

themes.xml의 Theme.MaterialComponents.DayNight.NoActionBar는 순수 Theme.Material3.* 계열이 아니라서 검증 도구가 형식적으로는 걸러냈지만, 실제로는 **CLAUDE.md에 이미 문서화된 AGP 9.x 관련 의도적 선택**이었다. 검증 도구 스스로 "정보성 — 실질 이슈 아님"이라고 정확히 판정했고, 이걸 그대로 받아들여 손대지 않았다.

> 089일차와 같은 패턴이 오늘도 반복됐다. 089일차엔 coroutineScope/supervisorScope 선택이, 오늘은 테마 선택이 — 표면적 체크리스트 위반이 실제로는 문서화된 설계 의도였다는 걸 검증 도구가 스스로 구분해냈다.

## 부수 발견 — 검증 범위 밖에서 나온 크래시 2건도 즉시 처리

`material3-design-validator`를 실행하는 과정에서, 원래 검증 목적(디자인)과 무관한 부수 이슈 2건이 함께 발견됐다. 범위 밖이라고 그냥 넘기지 않고, 재현성과 심각도를 각각 판단해서 둘 다 처리했다.

### 이슈 1 — 딥링크 크래시 (항상 재현됨)

```
온보딩 완료 상태 + 딥링크(moviefinder://movie/{id})로 앱 진입
    ↓
MainActivity.kt:80의 action_onboarding_to_home 네비게이션이
이미 딥링크로 detailFragment에 가 있는 상태에서 그대로 실행됨
    ↓
IllegalArgumentException 크래시
```

**원인:** `savedInstanceState == null` 조건만으로 무조건 navigate하던 게 문제 — 딥링크가 먼저 처리되어 시작 destination이 이미 바뀐 경우를 가드하지 않았다.

**수정:** 딥링크로 인해 시작 destination이 이미 변경된 경우를 확인하는 가드를 추가해서, 온보딩→홈 네비게이션이 불필요하게 중복 실행되지 않도록 했다. 실기기에서 딥링크로 직접 재현 테스트해서 크래시가 더 이상 발생하지 않음을 확인했다.

### 이슈 2 — 인증서 핀 간헐적 실패 (067일차 보안 설정과 연결)

```
테스트 중 SSLHandshakeException: Pin verification failed가
캐스트/리뷰/이미지 로딩에서 다수 발생 → 재시도 시 정상 로드됨
```

067일차에 만든 Certificate Pinning(OS 레벨+앱 레벨 이중 피닝)과 직접 관련된 이슈라, **원인부터 먼저 조사**한 뒤 대응했다. 간헐적으로 나타나고 재시도 시 회복되는 패턴은 일시적 네트워크/타이밍 문제일 가능성을 시사하며, 재현 조건과 로그를 남겨 추후 067일차 설정(핀 값, 백업 핀 구성)을 재점검할 근거로 문서화했다.

> **왜 두 이슈를 다르게 다뤘나:** 딥링크 크래시는 조건이 명확하고 항상 재현되어 **즉시 코드 수정**이 가능했지만, 인증서 핀 실패는 간헐적이라 **원인 조사와 문서화**를 우선했다 — 재현성에 따라 대응 방식을 다르게 선택하는 것도 좋은 판단이다.

---

076~089일차(6차 사이클)에서 "검증 도구가 체크리스트를 맹목적으로 적용하지 않고 설계 의도를 이해한다"는 게 여러 번 확인됐는데, **7차 사이클 시작(091일차)에서도 같은 성숙도가 이어졌다.** 이건 우연이 아니라 oh-my-claudecode의 검증 스킬들이 일관되게 "근거를 확인하고 판정한다"는 설계 철학을 공유하고 있다는 뜻이다.

## 오늘 배운 것 — 한 줄 정리

1. Glance/RemoteViews 기반 위젯은 **"홈 화면이 다른 프로세스"라는 086일차 제약** 때문에, 일반 앱 화면과 다른 색상/텍스트 규칙(하드코딩이 정상)을 가진다.
2. 발견된 이슈가 2개여도 **전부 다 고치는 게 정답은 아니다** — 검증 도구가 "정보성"이라고 명확히 구분한 건 그대로 존중하는 게 맞다.
3. CLAUDE.md에 문서화된 의도적 설계 선택은, 새로운 검증 도구를 돌릴 때마다 **"왜 이렇게 했는지"를 다시 확인하는 기준점** 역할을 한다.
4. 089일차(네트워크 레이어)와 091일차(디자인) 모두에서, **검증 도구가 스스로 오탐을 걸러내는 성숙도**가 일관되게 나타났다.
5. 검증 범위 밖에서 발견된 이슈도 **재현성에 따라 대응 방식을 다르게 선택**하면 된다 — 항상 재현되는 건 즉시 수정, 간헐적인 건 원인 조사와 문서화부터.
