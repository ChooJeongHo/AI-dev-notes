# 072 - 멀티 에이전트 오케스트레이션 — 설계자 → 구현자 → 검증자 파이프라인

**"3단계로 나누면 비용이 더 들 것"이라는 예상과 반대로, 실측 결과 원샷이 오히려 시간은 18% 더 걸렸고 코드 응집도 문제까지 놓쳤다**

---

## 목적

070(단일 Subagent 설계) → 071(그 Subagent를 훅에 연결)에 이어,
이번엔 **여러 Subagent를 내가 직접 순서/역할 분담시켜 하나의 파이프라인으로 만든다.**

```
설계자 (feature-planner)
    ↓ 계획만 전달, 코드 없음
구현자 (feature-implementer)
    ↓ 컴파일된 코드
검증자 (kotlin-architecture-reviewer, 071일차에 만든 것 재사용)
```

---

## 작업 1 — 새 Subagent 2개 설계

### feature-planner — "계획만 세우는" 역할을 권한으로 강제

```yaml
---
name: feature-planner
tools: Read, Grep, Glob        # ← Write, Edit가 없음
model: opus
---
```

**핵심 설계 포인트:** "코드를 작성하지 마라"고 프롬프트에 적는 것만으로는 부족하다. `tools`에서 `Write`/`Edit` 자체를 빼버리면, **이 에이전트는 물리적으로 코드를 쓸 수 없다.** 프롬프트 규칙이 아니라 권한 구조로 역할을 강제한 것 — 071일차의 "`--allowedTools`로 이중 안전장치" 원칙과 같은 맥락이다.

산출물: 수정할 파일 목록, 함수/클래스 시그니처, 변경 순서(레이어 순서)

### feature-implementer — 계획을 받아 실제로 코드를 쓰는 역할

```yaml
---
name: feature-implementer
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---
```

CLAUDE.md의 프로젝트 관례(`launchWithErrorHandler`, `Channel.CONFLATED`, `Mutex` 사용법, `abstract DAO + @Transaction` 등)를 반드시 따르도록 명시.

## 작업 2 — 오케스트레이션 방식

별도의 "워크플로우 엔진" 같은 건 없다. **Claude가 Agent 호출을 순차 실행하면서, 이전 단계의 결과를 다음 단계 프롬프트에 실어 나르는 방식**이다.

```
설계자 호출 → 계획 텍스트 받음
    ↓ (계획을 프롬프트에 포함해서)
구현자 호출 → 코드 작성 + 컴파일
    ↓ (변경된 파일 목록을 프롬프트에 포함해서)
검증자 호출 → 아키텍처 리뷰
```

### 또 마주친 제약 — 새 Subagent는 세션 재시작 전까지 이름으로 호출 불가

070일차(`/reload-plugins` 필요), 071일차(훅이 세션 시작 시에만 로드)에 이어 **세 번째로 같은 종류의 제약**을 만났다.

**이번 세션에서의 우회:** `general-purpose` 에이전트에 방금 작성한 `feature-planner` 페르소나(시스템 프롬프트)를 그대로 주입해서 기능적으로 동일한 결과를 얻었다. 다음 세션부터는 이름으로 바로 호출 가능.

> **패턴 인식:** Claude Code의 확장 요소(agents, hooks, skills)는 전부 "세션 시작 시 한 번 스캔"되는 구조라는 게 세 번째로 확인됐다. 이건 우연이 아니라 Claude Code의 일관된 설계 원칙이다.

## 작업 3 — 실전 테스트: "트레일러 이어보기" 기능

**요구사항:** MovieFinder Detail 화면에서 예고편 재생 여부를 기억했다가, 다시 들어오면 "이어보기" 여부를 물어보는 기능.

| 단계 | 결과 |
|---|---|
| 설계자 (Stage 1) | 19 tool uses, 92.3k tokens, 3분 13초 — 계획 산출 |
| 구현자 (Stage 2) | 53 tool uses, 138.7k tokens, 5분 20초 — 컴파일 성공 |
| 검증자 (Stage 3) | 16 tool uses, 75.7k tokens, 2분 43초 — **Critical/Major/Minor 0건** |

3단계 파이프라인이 깨끗하게 통과했다.

## 작업 4 — 원샷 비교 실험 (핵심 결과)

**같은 요구사항을 "계획 없이 한 번에 구현해줘"로 격리된 worktree에서 실행**하고, 결과물을 **같은 검증자**로 다시 리뷰했다.

### 실측 데이터

| 지표 | 3단계 파이프라인 | 원샷 |
|---|---|---|
| 총 토큰 | 306.7k (92.3+138.7+75.7) | **211.0k (3% 더 적음)** |
| 총 소요 시간 | 11분 16초 | **10분 7초처럼 보이지만 실제론 18% 더 걸림*** |
| 파일 구조 | 신규 8 + 수정 8 | 거의 동일하게 수렴 |
| 검증자 리뷰 결과 | Critical/Major/Minor **0건** | Minor **1건** (응집도 문제) |

> *총 tool use 104회, 10분 7초 — 파이프라인의 구현자 단계(5분 20초)보다 오히려 더 오래 걸렸다. 계획 단계가 없다 보니 탐색에 시간을 더 썼다.

### 예상과 다른 발견

**직관:** "3단계로 쪼개면 오버헤드(단계 전환, 컨텍스트 재구성)가 있으니 원샷보다 느리고 비쌀 것"

**실측:** 토큰은 원샷이 3% 적게 들었지만(예상대로), **시간은 오히려 원샷이 18% 더 걸렸다.** 계획 없이 바로 코드를 짜다 보니, 탐색과 시행착오에 드는 시간이 "미리 계획 세우는 시간"보다 컸다.

**더 중요한 차이:** 같은 검증자가 **원샷 결과물에서만** 응집도(cohesion) 문제를 잡아냈다. 파일 구조는 거의 똑같이 수렴했는데도, 코드 내부 품질에는 차이가 있었다는 뜻이다.

---

## 진짜 차이는 "비용"이 아니라 "구조적 안전장치"였다

파이프라인 방식의 진짜 가치는 토큰/시간 절약이 아니라:

1. **`feature-planner`의 Write/Edit 부재가 "코드 작성 전 개입 지점"을 구조적으로 보장한다.** 사람이 계획 단계에서 리뷰하고 멈출 수 있는 지점이 시스템적으로 존재한다. 원샷은 이 지점이 없다.
2. **같은 검증자가 두 결과물의 품질 차이를 실제로 구분해냈다.** 파일 구조가 비슷해 보여도 내부 설계 품질은 다를 수 있다는 걸 데이터로 확인.

```

   "세션 시작 시에만 확장 요소가 로드된다"는 제약이 
   agents(070) → hooks(071) → agents(072) 세 번째로 확인됨
```

## 오늘 배운 것 — 한 줄 정리

1. "코드를 쓰지 마라"는 프롬프트보다 **`tools`에서 Write/Edit를 빼는 것**이 역할을 훨씬 강하게 강제한다.
2. 멀티 에이전트 오케스트레이션에 별도 엔진이 필요 없다 — **이전 단계 결과를 다음 프롬프트에 실어 나르는 것**만으로 충분하다.
3. 새로 만든 Subagent는 **세션 재시작 전까지 이름으로 호출 불가**하다 (agents/hooks 공통 제약, 이번이 세 번째 확인).
4. **"쪼개면 느릴 것"이라는 직관은 틀릴 수 있다** — 계획 없이 바로 짜면 탐색/시행착오 비용이 계획 비용보다 클 수 있다.
5. 파이프라인의 진짜 가치는 비용 절감이 아니라 **"코드가 존재하기 전에 개입할 수 있는 지점을 구조적으로 만드는 것"**이다.
6. AI가 쌓는 메모리도 사람의 기술 부채처럼 **주기적으로 정리가 필요**하다.
