# 121 - 디버그 로그 API 키 노출 수정 — 인터셉터 순서를 바꿔도 키는 응답 줄로 샌다

**디버그 로그에 API 키와 session_id가 그대로 찍히던 문제를 마스킹으로 막았다. 로깅 인터셉터를 키 주입보다 앞에 두는 방법은 해법이 아니었다 — 응답 줄이 최종 URL을 다시 찍어서 키가 노출됐다**

---

## 목적

116일차에서 "디버그 빌드의 로깅 인터셉터가 KMRB serviceKey를 쿼리스트링 그대로 로그에 남긴다"는 걸 발견하고 범위 밖으로 남겨뒀다. 실제로 그때 세션 출력에 키 앞부분 일부가 찍힌 적도 있어서, 알려진 한계로 두지 않고 막기로 했다.

---

## 작업 1 — 조사: 세 클라이언트의 노출 양상이 달랐다

| 클라이언트 | 노출 위치 |
|---|---|
| KMRB, KOFIC | 요청 줄과 응답 줄 모두 |
| TMDB v3 | 응답 줄에서만 |
| TMDB v4 | 이미 안전 (헤더 마스킹으로 처리되어 있었음) |

release 빌드는 로깅 자체가 꺼져 있어서 노출 대상이 아니다. 116일차 확인 때 본 APK가 9/20 빌드라 최신 커밋 기준은 아니었다. 이번 프롬프트에서 그 상태가 유지되는지 다시 봐달라고 요청했지만, 받은 요약에는 그 재확인 결과가 따로 적혀 있지 않다. 그래서 release 쪽은 "116일차에 확인한 상태 그대로로 보이지만 이번에 새로 확인한 결과는 기록이 없다"고 적어둔다.

---

## 작업 2 — 설계: 이름 4개를 상수로 공유

- 디버그 `addDebugLogging()`에 `redactQueryParams(...)`를 추가해서 네 호출 지점을 한 곳에서 해결한다.
- 마스킹 대상은 `api_key`, `key`, `serviceKey`, `session_id` 네 개다. 이 이름들을 상수로 두고, 키를 주입하는 인터셉터와 마스킹 목록이 같은 상수를 쓰게 해서 이름이 서로 어긋날 수 없게 했다.
- 테스트는 합성 클라이언트가 아니라 실제 클라이언트 빌더를 가짜 키로 만들어 로컬 서버에 호출하고, 로그를 캡처해서 검증하는 방식을 택했다. 이를 위해 `NetworkModule`에 `internal build*(apiKey)` 헬퍼를 뽑았다.

`session_id`까지 포함한 이유는 TMDB 세션 ID가 109일차 OAuth로 받은 로그인 세션 값이라, 로그에 남으면 API 키만큼 민감하기 때문이다.

## 작업 3~4 — 구현과 테스트

소스 6개를 변경했고 새 테스트 7개를 추가했다. 유닛 테스트는 948개 통과(기존 941 + 신규 7), 실패 0, skipped 0이었다.

제약을 일부러 깨뜨린 변이 5종은 모두 해당 테스트가 실패했다. 세부 목록은 받은 요약에 없어서 여기에 적지 않는다. 설계 단계에서 계획한 건 이름 제거, 호출 제거, 주입 쪽 이름 변경 세 가지였다.

---

## 알게 된 사실

### 1. 로깅 인터셉터의 순서 변경은 해법이 아니다

로깅 인터셉터를 키 주입보다 앞에 둬도, 응답 줄이 최종 URL을 찍어서 키가 노출된다. 순서를 바꾸면 요청 줄만 가려질 뿐이다.

이 응답 줄 노출은 별도 실험으로 재현했다. 가짜 시크릿에 로컬 서버를 쓴 OkHttp 5.0.5 실험이었고, 실제 키는 쓰지 않았다.

### 2. 리뷰가 추가 누수를 찾아냈다

리뷰에서 `DebugEventListener`가 `session_id`를 찍는 누수가 따로 나왔다. 실패하는 테스트로 먼저 재현한 뒤 고쳤다.

## 작업 5 — 실기기 검증 (SM-S926N)

키 값이 화면에 다시 찍히지 않도록, 줄 내용을 보지 않고 `logcat`에서 개수만 셌다.

| 항목 | 결과 |
|---|---|
| 마스킹된 줄 | TMDB 10 / KOFIC 2 / KMRB 4 |
| 마스킹 안 된 비밀 파라미터 | 0줄 |
| 실제 키 값이 포함된 줄 | 0줄 |
| 크래시 | 없음 |

마스킹된 줄이 1 이상이어야 한다는 조건을 같이 걸었다. 0줄만 보면 마스킹이 된 건지 로깅이 꺼진 건지 구분이 안 되기 때문이다.

수정 전 기기 측정은 생략했다. 호출이 두 배가 되기 때문이고, 수정 전 증거는 JVM 테스트의 red 단계로 대신했다.

## 남은 것과 한계

- 머지 후 `main` CI는 확인하지 못했다. 머지 직후라 진행 중이었고, 결과는 모른다.
- release 변형에서는 새 테스트를 건너뛴다. release는 로깅이 없어서 검증할 로그가 없고, 디버그 변형(CI, pre-push)에서는 전부 실행된다.
- 기기 첫 실행은 증거로 쓰지 않았다. 처음 `monkey`로 띄운 콜드 스타트는 OkHttp 로그가 0줄이었고, 원인은 조사하지 않았다.
- 범위 밖: `DebugHealthCheck`와 인기 영화 위젯은 `"api_key"` 리터럴을 쓰지만 로깅이 없어서 현재 노출은 없다. KMRB 장애 중 등급 칩 선택 시 연쇄 호출 문제도 기존 그대로다.

## 120일차 포트폴리오의 미해결 항목 하나가 닫혔다

120일차 "남은 과제"에 있던 "디버그 빌드에서 KMRB serviceKey가 로그에 남음"이 이번에 해소됐다. 해소 범위가 KMRB만이 아니라 KOFIC, TMDB v3, 그리고 `session_id`까지 넓어졌다는 점이 처음 기록보다 큰 결과다.

---

## 오늘 배운 것 — 한 줄 정리

1. 로깅 인터셉터를 키 주입 앞에 둬도 응답 줄이 최종 URL을 찍어서 키가 샌다 — 순서는 해법이 아니고 마스킹이 해법이다.
2. 마스킹이 맞는지 검증하려면 "마스킹 안 된 줄 0"과 "마스킹된 줄 1 이상"을 같이 봐야 한다. 0만 보면 로깅이 꺼진 것과 구분되지 않는다.
3. 마스킹 이름과 키 주입 이름이 따로 있으면 어긋난다 — 같은 상수를 공유하면 어긋날 수 없다.
4. 합성 클라이언트로 정책만 검증하는 테스트는 실제 조립이 바뀌어도 못 잡는다 — 실제 클라이언트 빌더를 통과시키는 테스트가 맞다.
5. 보안 검증 중에는 검증 과정에서 키가 다시 화면에 찍히지 않게 줄 내용 대신 개수만 센다.
6. 리뷰가 두 번째 누수(`session_id`)를 찾았다 — 작은 수정이라도 리뷰는 빼지 않는다.
