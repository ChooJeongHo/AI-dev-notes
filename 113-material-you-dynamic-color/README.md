# 113 - Material You 동적 색상 — "M3 없이도 적용 가능"은 맞았지만, 편의 메서드가 그 전제를 못 지켰다

**"M3 마이그레이션 없이도 동적 색상을 쓸 수 있다"는 명제 자체는 맞았다 — 다만 라이브러리의 편의 메서드(인자 없는 applyToActivitiesIfAvailable)가 Theme.MaterialComponents 같은 비-M3 테마를 처리 못 하는 사각지대였다**

---

## 목적

MovieFinder에 Material You 동적 색상(사용자 배경화면 색상에 맞춰 앱 테마가 자동으로 바뀌는 Android 12+ 기능)을 추가한다.

---

## 선행 정리 — 프롬프트에 담긴 근거 없는 전제 처리

작업 시작 전, Claude Code가 프롬프트에 담긴 "091/098/112일차에서 이런 결론을 냈다"는 언급을 git 로그와 메모리 전체에서 검색했는데, 실제 기록과 일치하지 않았다. 091일차 실제 기록은 인증서 핀 로테이션 조사였고, "Theme.MaterialComponents 확인"이나 "Material3 마이그레이션 대상 아님" 결론은 git 이력이나 메모리 어디에도 없었다.

처리 방향: 출처 불명확한 과거 언급은 빼고, 순수하게 지금 코드 상태를 직접 확인한 사실만 근거로 진행하기로 했다.

---

## 작업 1 — 조사

Theme.MovieFinder는 Theme.MaterialComponents.DayNight.NoActionBar 기반, 색상은 전부 하드코딩. material 라이브러리 1.14.0으로 DynamicColors API 요구사항(1.6.0+)을 충족하고, minSdk 24에서도 API 31 미만은 자동 no-op이라 안전하다는 걸 확인했다.

---

## 작업 2 — 구현: 편의 메서드 한 줄로 시작했다가 버그 2개 발견

처음엔 DynamicColors.applyToActivitiesIfAvailable(this) 한 줄로 시작했지만, 실기기 검증 중 실제 버그 2개를 찾아 고쳤다.

### 버그 1 — 인자 없이 호출하면 조용히 아무것도 안 함

Theme.MaterialComponents 계열엔 없는 attr(dynamicColorThemeOverlay)를 찾다가, 찾지 못해도 에러 없이 조용히 아무 동작도 안 했다.

수정: 오버레이 스타일을 명시적으로 지정해서 해결.

### 버그 2 — Application.onCreate()에서 적용하면 AppCompatActivity가 덮어써버림

Application.onCreate()(Activity 생성 전)에서 적용하면, AppCompatActivity의 super.onCreate()가 베이스 테마를 재적용하면서 덮어써버렸다.

수정: 적용 시점을 MainActivity.onCreate()의 super.onCreate() 이후로 옮겨서 해결. 최종 코드는 MainActivity.kt에 있다.

---

## 작업 3 — 테스트

MainActivityDynamicColorTest.kt 계측 테스트 2개 추가 (API 게이팅 확인 + 앱 정상 기동 확인). 유닛 테스트 856개 전부 통과.

---

## 작업 4 — 실기기 검증

### 1. 하드코딩 색상이 동적 색상 적용을 방해하는가

아니요, 방해하지 않았다. 버그를 고치고 나니 정상 적용됨을 Pixel 에뮬레이터에서 벽지 변경 + 스크린샷으로 직접 확인했다.

### 2. 실기기에서만 드러난 문제

삼성 실기기(SM-S926N)는 OS 자체가 벽지에서 색 팔레트를 아예 안 만들어준다 — 이건 코드와 무관한 기기 제약으로, 미해결로 남겼다.

부수적으로, SearchFragment/OnboardingFragment의 Compose 화면 2곳은 dynamicColorScheme() 미배선이라 여전히 M3 기본 보라색으로 남는다 — 이건 별도 작업이 필요한 부분으로 남겨뒀다.

---

## 작업 5 — 정리

"M3 마이그레이션 없이도 동적 색상 적용 가능"은 맞다. 다만 편의 메서드(인자 없는 호출)는 그 전제를 실제로 충족 못 시키는 라이브러리 쪽 사각지대였다는 게 이번 핵심 발견이다.

명제 자체는 옳았지만, 그 명제를 구현하는 표준 API(편의 메서드)가 비-M3 테마를 암묵적으로 가정하고 있었다는 게 실기기 검증으로만 드러났다.

## 오늘 배운 것 — 한 줄 정리

1. "이론적으로 가능하다"는 명제와 "표준 API로 바로 된다"는 건 다른 문제다 — 편의 메서드가 암묵적으로 특정 조건(M3 테마)을 가정하고 있을 수 있다.
2. 라이브러리 함수가 조건 불충족 시 에러 없이 조용히 no-op하면, 이건 컴파일·테스트로 절대 못 잡고 실제로 화면을 보고 확인해야만 드러난다.
3. Application.onCreate()와 Activity.onCreate()는 테마 적용 시점에서 실행 순서가 중요하다 — 너무 일찍 적용하면 나중에 덮어써질 수 있다.
4. 실기기 검증은 기기 제조사별 OS 차이(삼성의 벽지 팔레트 미생성)까지 드러낼 수 있다 — 이건 코드로 해결 불가능한 영역이라 정직하게 "미해결"로 남기는 게 맞다.
5. 프롬프트에 넣은 "과거 결론"이 실제 기록과 다를 수 있다 — 작업 시작 전에 근거를 검색해서 확인하는 습관이 잘못된 전제로 작업이 흘러가는 걸 막아준다.
