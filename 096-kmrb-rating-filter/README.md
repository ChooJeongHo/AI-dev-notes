# 096 - KMRB 관람등급 필터 — 082일차 N+1 해법이 이번엔 그대로 재사용되지 않았다

**082일차의 "캐시 우선 조회"는 TMDB 데이터가 이미 로컬에 캐싱되어 있었기 때문에 가능했던 방식이었다 — KMRB 등급은 애초에 로컬 캐시가 없어서, 같은 원칙을 다른 방식으로 다시 구현해야 했다**

---

## 목적

095일차에서 KMRB 관람등급을 상세 화면에 "보여주기"만 했는데, 096일차는 검색 결과에서 등급별로 "걸러보기"까지 가능하게 만든다.

---

## 작업 1 — 082일차 N+1 해법이 그대로는 안 통했다

082일차에서 KOFIC 박스오피스 N+1 문제를 풀 때, 핵심은 "TMDB 캐시 테이블을 한 번만 읽어서 메모리에서 매칭"하는 것이었다. 이게 가능했던 이유는 홈 화면을 둘러보며 now_playing/popular 캐시가 이미 Room에 쌓여있었기 때문이다.

KMRB 등급은 사정이 다르다:

| | 082일차 (KOFIC × TMDB) | 096일차 (검색 결과 × KMRB) |
|---|---|---|
| 매칭 대상 데이터 | TMDB — 앱을 쓰다 보면 자연히 캐싱됨 | KMRB — 어떤 캐시도 미리 존재하지 않음 |
| "캐시를 한 번 읽어서 매칭" 전략 | 그대로 통함 | 애초에 읽을 캐시가 없어서 통하지 않음 |

**결론:** "캐시 우선 조회"라는 패턴(스캐폴딩)은 유효했지만, 그 패턴이 전제하는 "이미 채워진 캐시"라는 조건 자체가 이번엔 성립하지 않았다 — 083/085/087일차에서 반복된 "재사용은 스캐폴딩까지지 도메인 조건까지는 아니다"라는 결론이 여기서도 반복됐다.

---

## 작업 1 (계속) — 새로 설계한 접근

캐시가 없으니 처음부터 만드는 대신, 검색 결과 조회 시점에 KMRB 등급을 함께 조회해서 자체 캐시 테이블에 쌓아가는 방식을 택했다. 한 번 조회된 영화는 두 번째부터 로컬에서 즉시 매칭되므로, 시간이 지날수록 082일차와 같은 효과(캐시 히트율 상승)를 자연스럽게 얻게 된다.

```
검색 결과 title 목록
    ↓
로컬 KMRB 등급 캐시에서 먼저 조회 (히트하면 네트워크 스킵)
    ↓
캐시 미스인 것만 KMRB API로 조회 후 캐시에 적재
```

095일차의 GetKoreanRatingUseCase(단건 조회)는 상세 화면 전용으로 그대로 남겨두고, 검색 결과처럼 여러 건을 동시에 다루는 경로는 별도 UseCase로 분리했다 — 하나의 UseCase가 "단건"과 "다건 배치"라는 서로 다른 성능 특성을 다 떠안지 않도록 한 설계 판단이다.

---

## 작업 2 — UI: 관람등급 필터 칩

SearchFragment에 전체/전체관람가/12세/15세/청소년관람불가 칩을 추가했다. 칩 선택 시 이미 로드된 검색 결과를 등급 기준으로 필터링해서 보여준다.

---

## 작업 3~4 — 테스트 및 실기기 검증

새 배치 조회 UseCase와 캐시 로직에 대한 유닛 테스트를 작성하고, 실기기에서 필터 칩을 선택했을 때 실제로 결과가 걸러지는지 확인했다.

---

## 작업 5 — 082일차 패턴 재사용성 정리

| 구성요소 | 재사용 여부 |
|---|---|
| "캐시를 한 번 읽어서 메모리에서 매칭"이라는 사고방식 | 재사용됨 — 설계의 뼈대로 그대로 가져옴 |
| 실제 캐시 테이블(이미 채워져 있다는 전제) | 재사용 불가 — KMRB 전용 캐시를 새로 만들어야 했음 |
| 캐시 히트/미스 분기 로직 구조 | 재사용됨 |

**정직한 결론:** 082일차의 진짜 자산은 "캐시 테이블 자체"가 아니라 "캐시를 다루는 사고방식"이었다. 데이터 소스가 바뀌면 캐시 자체는 새로 만들어야 하지만, 그 캐시를 "어떻게 효율적으로 조회할 것인가"에 대한 설계 원칙은 그대로 옮겨왔다.

```

    ↓

```

## 오늘 배운 것 — 한 줄 정리

1. 이전에 만든 최적화 패턴을 재사용할 때는 "패턴 자체"와 "그 패턴이 성립하기 위한 전제 조건"을 구분해서 봐야 한다.
2. 캐시 우선 조회는 캐시가 이미 채워져 있을 때만 효과가 있다 — 캐시가 비어있는 새로운 데이터 소스에는 같은 코드를 복붙할 수 없다.
3. 단건 조회용 UseCase와 다건 배치 조회용 UseCase는 성능 특성이 달라서 분리하는 게 맞는 설계다.
4. 083/085/087일차에서 반복된 "재사용의 두 층위(스캐폴딩 vs 도메인 조건)"라는 원칙이 096일차에서도 다시 확인됐다.
