# 115 - TMDB 언어 연동 — 승인 게이트가 조용한 파손을 막고, 68초 실측이 롤백을 결정했다

**앱 언어를 English로 바꿔도 영화 제목/줄거리가 한국어로 남는 112일차의 한계를 풀려다 보니, 같은 title을 재사용하는 숨은 기능 두 곳(박스오피스 매칭, KMRB 등급 조회)이 한국어 제목에 의존하고 있었다 — 조사→승인 게이트가 이 얽힘을 구현 전에 잡아냈고, 실기기에서 잰 68초가 검색 화면의 롤백을 결정했다**

---

## 목적

112일차에서 미뤄둔 TMDB 언어 연동을 처리한다. 앱 UI는 영어로 바뀌는데 영화 제목/줄거리는 한국어로 남는 불일치를 해소하는 게 목표였다.

---

## 배경 — 그냥 고치면 끝나는 문제가 아니었다

- **기존 한계:** 앱 언어를 English로 바꿔도 TMDB API의 `language` 파라미터가 `ko-KR`로 고정되어 있었다.
- **얽힘:** 같은 `title` 값을 재사용하는 두 개의 숨은 기능이 한국어 제목에 의존하고 있어서, 단순 수정하면 다른 기능이 깨질 위험이 있었다. 이 얽힘을 미리 찾아내는 게 이번 실험의 핵심이었다.

---

## 진행 방식 — 6단계 게이트 워크플로우

"조사 → 설계(승인) → 구현 → 테스트 → 실기기 검증 → 정리" 6단계를 처음부터 명시하고, 각 단계 사이에 사람이 개입해 방향을 확정하는 구조로 진행했다. AI가 혼자 끝까지 밀어붙이지 않고, 설계 단계에서 반드시 멈춰 승인을 받는 게 특징이다.

---

## 1단계 — 조사

| 항목 | 발견 |
|---|---|
| language 파라미터 | 인터셉터가 아니라 **Retrofit 메서드 15개 각각의 기본값**으로 박혀 있었음 |
| 한국어 title 의존 지점 | 2곳 — ① 박스오피스 매칭(KOFIC 영화명 ↔ TMDB title 정확 매칭), ② KMRB 등급 조회 |
| KMRB 호출부 | 상세 화면 + 검색 화면 필터, **총 2개 호출부** (요청서에 없던 호출부를 추가로 발견) |

**결정적 발견:** 홈 화면의 Room 캐시(`cached_movies`)가 **박스오피스 매칭의 로컬 캐시 스냅샷과 동일한 테이블**이었다. 이걸 그냥 언어별로 바꾸면 082일차의 매칭 최적화가 깨질 수 있는 구조적 얽힘이었다.

---

## 2단계 — 설계: 조건부 승인

조사 결과를 근거로 두 가지 갈림길(검색 결과 언어, 홈 목록 언어)을 제시받았고, 아래 조건을 붙여 "앱 언어 따름" 쪽으로 승인했다.

> 박스오피스 매칭의 TMDB 폴백은 ko-KR 유지, 언어 변경 시 홈 캐시 무효화, 위젯도 검증, 너무 느리면 롤백

이후 대화 중 조건을 추가로 정제했다 (예: "한국어 제목 추가 조회는 등급 필터가 켜졌을 때만 하고, 캐시해서 N+1 재발 방지"). AI가 설계를 일방적으로 확정한 게 아니라, 매 조건마다 구현 가능성과 트레이드오프를 설명하며 합의해 나갔다.

---

## 3단계 — 구현

- `AppLanguageProvider` 신설 — 앱 언어를 TMDB 언어 코드로 변환. 분기 로직은 순수 함수로 분리해 테스트 가능하게 했다 (114일차 `MovieFinderTheme` 리팩터링과 같은 패턴 재사용).
- 상세/배우/트렌딩/discover/개봉예정/홈 목록에 앱 언어 반영
- 박스오피스 네트워크 폴백은 **명시적으로 ko-KR 고정**
- 언어 변경 이벤트에 훅을 걸어 **홈 캐시 즉시 무효화**
- KMRB 매칭용 한국어 제목을 `movieId` 기준으로 **별도 Room 캐시**에 저장하는 신규 경로 추가

구현 도중 PreToolUse 훅(`kotlin-architecture-reviewer`)이 실시간으로 개입했다. `getKoreanTitle` 메서드를 처음엔 잘못된 인터페이스(`MovieQueryRepository`)에 넣었다가, 리뷰 피드백을 받고 `MovieDetailRepository`로 옮겼다.

---

## 4단계 — 테스트

- 새 유닛 테스트 다수 작성
- 시그니처 변경으로 깨진 기존 테스트(약 10개 파일)를 전부 추적해 수정
- **최종 894개 테스트 전부 통과, Detekt 0건**

---

## 5단계 — 실기기 검증 (가장 많은 시간이 든 단계)

예상 못 한 디버깅이 여러 번 발생했다.

### 1. UI 조작 실수 연발

adb 좌표 탭이 계속 빗나가서 다른 앱이 열리거나 엉뚱한 필터가 걸리는 일이 반복됐다. `uiautomator dump`로 정확한 좌표를 뽑는 방식으로 전환해 안정화했다.

### 2. 거짓 양성 — "캐시 무효화 실패"로 오판할 뻔함

언어를 English로 바꾼 직후 홈 화면 캡처에서 영화 제목이 여전히 한국어로 보여 "캐시 무효화가 실패했다"고 오판할 뻔했다. 실제로는 화면에 보인 게 **박스오피스(KOFIC 데이터, 원래도 한국어가 맞음) 섹션**이었고, DB를 직접 열어보니 실제 영화 목록 캐시는 정상적으로 영어로 갱신돼 있었다. **스크린샷만으로 판단하지 않고 DB/로그까지 내려가서 확인**한 덕분에 오판을 피했다.

### 3. SQLite WAL 함정

`getKoreanTitle` 캐시가 DB에 안 보여서 "캐시 기록이 안 된다"고 다시 오판할 뻔했다. 원인은 Room이 WAL(Write-Ahead Log) 모드라, 커밋된 데이터가 `-wal` 파일에만 있었던 것이다. 메인 DB 파일만 pull하면 최신 데이터가 안 보인다. `-wal`/`-shm` 파일을 함께 pull하고 나서야 정상 확인됐다.

### 4. 진짜 성능 문제 — 68초

검색 화면에서 KMRB 등급 필터를 처음 켰을 때(캐시 없음, 60개 항목) 로그 타임스탬프 기준 **약 68초**가 걸렸다. **유닛 테스트로는 절대 못 잡는, 실기기에서만 드러나는 문제**였다.

### 5. 위젯 검증

실기기 홈 런처에 위젯이 이미 배치돼 있어서, 새로고침 버튼으로 `BoxOfficeWidgetWorker`를 직접 트리거했다. 로그로 정확한 언어 파라미터 사용과 매칭 성공을 확인했다.

**양쪽 언어에서 매칭 정확도를 명시적으로 재확인했다:**

| 앱 언어 | 위젯 표시 | 로그 확인 |
|---|---|---|
| 한국어 | 1위 암살자(들) 260,544명 | `language=ko-KR` 고정 TMDB 검색 → 매칭 성공 |
| 영어 | #1 암살자(들) 260,544 admissions | `language=ko-KR` 고정 TMDB 검색 → 매칭 성공 |

앱 UI 언어가 바뀌어도 박스오피스 매칭 정확도 자체는 전혀 흔들리지 않았다. 영어 모드에서도 영화명(암살자(들))이 한국어로 남는 건 박스오피스 데이터가 KOFIC 원본이기 때문이며, 의도한 동작이다.

### 6. 위젯의 "stale snapshot" 특성 — 새로 확인한 알려진 한계

언어를 English로 바꾼 직후 위젯을 보면 **여전히 이전(한국어) 상태 그대로** 보였고, 새로고침 버튼을 눌러야 비로소 갱신됐다.

이건 버그가 아니다. Glance 위젯의 설계 원칙 때문에 생기는 정상 동작이다 — `provideGlance()`는 저장된 스냅샷만 그리고 직접 I/O를 하지 않으며, 갱신은 `BoxOfficeWidgetWorker`가 전담한다. 다만 **"언어를 바꿨는데 위젯만 안 바뀐 것처럼 보이는 사용자 체감 순간"이 실제로 존재한다**는 걸 실기기에서 처음 확인했다.

자동 갱신 주기가 6시간이라, 언어를 바꾼 직후엔 **최대 6시간 동안 위젯이 이전 언어로 남아있을 수 있다.** 이번 작업 범위 밖이라 고치지 않았지만, 알려진 한계로 기록할 가치가 있다.

---

## 6단계 — 정리: 68초 실측이 롤백을 결정했다

68초라는 실측 근거를 가지고, 사전에 위임해둔 "느리면 롤백" 조건에 따라 **검색 화면만 한국어 고정으로 되돌렸다.** 상세 화면은 영화당 1회 조회라 그대로 유지했다. CLAUDE.md에 최종 상태와 트레이드오프, 롤백 사유를 실측 수치와 함께 문서화했다.

### 최종 상태

| 대상 | 언어 |
|---|---|
| 상세 / 배우 / 트렌딩 / discover / 개봉예정 / 홈 목록 | 앱 언어를 따름 |
| 박스오피스 네트워크 폴백 | ko-KR 고정 |
| 검색 목록 (KMRB 필터 대상) | **한국어 고정 (롤백)** |
| KMRB 매칭용 한국어 제목 | `movieId`별 Room 캐시 (상세 화면 경로에서 유지) |
| 위젯 | 언어 전환 직후엔 이전 스냅샷 유지 (새로고침 또는 다음 주기 갱신 후 반영, 알려진 한계) |

### 112일차 한계는 해소됐나 — 부분 해소

대부분의 화면은 앱 언어를 따르게 됐지만, **검색 목록은 한국어로 남았다.** 즉 영어 모드에서 검색 목록은 한국어, 상세는 영어라는 화면 간 불일치가 새로 생겼다. 불일치가 완전히 사라진 게 아니라 **범위가 검색 화면 하나로 좁혀진 것**이다.

## 재사용 가능한 실기기 자동화 팁 — 앱 언어를 UI 없이 전환하기

이번 세션 초반엔 UI 탭 좌표가 계속 어긋나 시간을 많이 썼다. 아래 명령으로 앱 UI를 조작하지 않고도 특정 앱의 언어를 즉시 전환/복구할 수 있다.

```bash
adb shell cmd locale set-app-locales <패키지> --user 0 --locales <코드>
```

이 명령을 처음부터 알았다면 언어 전환/복구 검증은 훨씬 빨랐을 것이다. 다음에 비슷한 언어 전환 검증을 할 때 재사용할 수 있다.

---

## 이 실험에서 눈여겨볼 점

- **설계 단계에서 멈추는 게 실제로 작동했다.** 처음 제안한 방향(단순 언어 전환)이 그대로 갔다면 박스오피스/KMRB가 조용히 깨졌을 것이다. 조사→승인 게이트가 그걸 막았다.
- **실기기 검증이 유닛 테스트로 못 잡는 것을 잡았다.** 68초 성능 문제, WAL 캐시 확인 문제, 스크린샷만으론 안 보이는 것들.
- **AI가 자기 판단을 의심하고 더 파고든 순간이 여러 번 있었다.** 박스오피스 섹션과 실제 캐시의 구분, WAL 파일 재확인 — 섣부른 결론 대신 로그/DB 원본까지 내려가서 검증했다.
- **사람과 AI의 역할 분담:** 방향 결정(언제 롤백할지, 어떤 트레이드오프를 감수할지)은 사람이, 실측·구현·회귀 추적은 AI가 맡았다.

## 111~115를 관통하는 패턴 — "롤백 조건을 미리 정해두면 실측이 결정해준다"

112일차는 "고치려다 만든 회귀를 되돌렸다"였고, 115일차는 **되돌릴 조건을 착수 전에 합의해둔 덕분에, 실측 수치(68초) 하나로 롤백이 즉시 결정**됐다. 결정을 사후에 고민하는 게 아니라 사전에 위임해둔 기준에 실측값을 대입하는 방식이라 판단이 빨랐다.

---

## 오늘 배운 것 — 한 줄 정리

1. 같은 값(`title`)을 재사용하는 숨은 기능이 있으면, 한 곳을 고치는 것이 다른 곳을 조용히 깨뜨릴 수 있다 — **구현 전 조사와 승인 게이트**가 그걸 막는다.
2. 작업 착수 전에 "이 수치를 넘으면 롤백한다"는 **롤백 조건을 미리 합의**해두면, 실측 결과가 나왔을 때 망설임 없이 결정할 수 있다.
3. 화면에 보이는 것만으로 "실패"를 판단하지 말고 **DB/로그 원본까지 내려가서 확인**해야 한다 — 박스오피스 섹션은 원래 한국어가 맞았다.
4. Room이 WAL 모드일 땐 메인 DB 파일만 pull하면 최신 데이터가 안 보인다 — `-wal`/`-shm`도 함께 가져와야 한다.
5. 성능 문제는 유닛 테스트에 안 잡히고 **실기기에서 로그 타임스탬프로 실측**해야 드러난다 — 이번엔 60개 항목에 68초였다.
6. "부분 롤백"도 정당한 결과다 — 다만 그로 인해 **새로 생긴 불일치(검색 목록 한국어, 상세 영어)를 정직하게 기록**해야 한다.
7. 위젯은 저장된 스냅샷을 그리는 구조라, 앱 언어를 바꿔도 **다음 갱신 전까지 이전 언어가 남는다** — 버그가 아니라 설계의 결과지만, 사용자 체감 한계로 기록해야 한다.
8. `adb shell cmd locale set-app-locales`로 앱 언어를 UI 없이 전환할 수 있다 — 좌표 탭이 어긋날 때 시간 낭비를 줄여준다.
