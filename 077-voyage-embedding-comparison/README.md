# 077 - 로컬 해싱 임베딩 vs 실제 Voyage AI 임베딩 — "1줄 교체" 설계가 실제로 검증되다

**076일차에 "인터페이스로 추상화해뒀으니 나중에 교체 가능"이라고 설계한 걸 실제로 검증 — Q2에서 의미 기반 검색과 문자열 매칭의 차이가 극적으로 드러났다**

---

## 목적

076일차에서 `EmbeddingProvider` 인터페이스로 추상화해두고 "나중에 실제 API로 1줄 교체 가능"이라고 했는데, **실제로 그게 되는지 검증 안 하고 끝났었다.** 077일차는 이 약속을 실제로 지켜서, 로컬 해싱 임베딩과 실제 Voyage AI 임베딩(`voyage-code-3`)의 검색 품질을 같은 3개 질문으로 직접 비교한다.

---

## 설계 변경 — 인터페이스에 `embedDocuments`/`embedQuery` 분리 추가

```kotlin
interface EmbeddingProvider {
    val dimension: Int
    val name: String

    /** 인덱싱 시점: 코드 청크(문서) 임베딩 */
    fun embedDocuments(texts: List<String>): List<FloatArray>

    /** 질의 시점: 사용자 질문 임베딩 */
    fun embedQuery(text: String): FloatArray
}
```

**왜 나눴나:** Voyage 같은 실제 임베딩 모델은 검색 품질을 위해 **문서용/질의용 프롬프트를 다르게 붙이는 비대칭(`input_type`) 임베딩**을 지원한다. 076일차의 단일 `embed()` 함수로는 이 차이를 표현할 수 없어서, 인터페이스 자체를 확장해야 했다.

---

## 실전에서 만난 두 개의 API 제약

### 1. 무료(결제수단 미등록) 계정의 이중 제한

| 제한 종류 | 값 |
|---|---|
| RPM (분당 요청) | 3회 |
| TPM (분당 토큰) | 10,000 |

처음 배치 크기(100청크/호출, 약 2~3만 토큰)로 시도했더니 **TPM 자체를 한 번에 초과**해서 실패했다. 실측(90줄 코드 청크 ≈ 813 토큰) 기준으로 **배치 크기를 10청크로 낮춰서** 최악의 경우에도 8~9천 토큰 선을 넘지 않게 조정했다.

```kotlin
// 결제수단 미등록 계정은 10K TPM 한도가 있음
private val batchSize: Int = 10  // 100 → 10으로 축소

companion object {
    // 결제수단 미등록 계정 기본 한도가 3 RPM이라 
    // 20초/회 미만으로는 안전하지 않음 - 여유를 둬 21초로 고정
    private const val MIN_CALL_INTERVAL_MS = 21_000L
}
```

### 2. 전체 인덱싱은 40분 — 샘플링으로 전환

전체 1,224개 청크를 이 제한 그대로 돌리면 **40분 가까이** 걸린다는 게 계산으로 나왔다. 오늘 목적(3개 질문 검색 품질 비교)엔 전체가 필요 없어서, **3개 질문과 관련된 디렉토리만 선별 인덱싱**하는 옵션을 Gradle task에 추가했다.

```bash
./gradlew :tools:codebase-rag:ragIndex -Ppaths="domain/repository,data/repository,..."
```

> **투명성 원칙:** "전체 코퍼스가 아니라 샘플"이라는 걸 결과에 명시하고 비교하기로 했다 — 조건을 숨기고 비교하면 잘못된 결론을 낼 위험이 있다.

## Before/After 비교 — 3가지 질문

### Q1. "영화 즐겨찾기 추가는 어떤 파일들을 거쳐서 처리돼?"

| | 로컬 해싱 (076) | Voyage (077) |
|---|---|---|
| 1위 | FavoriteRepository.kt (0.213) | FavoriteRepository.kt (0.579) |
| 2위 | FavoriteMovieDao.kt (0.208) | **TmdbAuthRepository.kt (0.561) ← 오답** |
| 3위 | SettingsFragment.kt (0.193) ← 노이즈 | FavoriteRepositoryImpl.kt (0.553) |

유사도 점수 자체는 Voyage가 훨씬 높지만(0.54~0.58 vs 0.18~0.21), 이 질문에서는 **Repository/Impl 파일들의 문체·구조가 서로 비슷해서 코사인 거리가 뭉치는 부작용**도 함께 확인됐다 — Voyage가 항상 더 낫다는 단순한 결론은 아니라는 뜻.

### Q2. "TMDB API 인증은 어떻게 되어 있어?" — 가장 극적인 차이

| | 로컬 해싱 (076) | Voyage (077) |
|---|---|---|
| 1위 | TmdbAuthApiService.kt (0.307) | TmdbAuthApiService.kt (0.673) |
| 2위 | TmdbV3SessionApiService.kt (0.288) | TmdbAuthRepository.kt (0.634) |
| 4위 | **HomeFragment.kt (0.256) ← 노이즈** | TmdbAuthRepositoryImpl.kt (0.621) |
| 5위 | **TrendingPagingSource.kt (0.233) ← 노이즈** | TmdbAuthApiService.kt (0.603) |

로컬 해싱은 4·5위가 완전히 무관한 파일이었는데, **Voyage는 top5 전부가 실제 TMDB 인증 관련 파일**이고 유사도도 0.60~0.67로 일관되게 높다.

> **핵심 발견:** "인증"이라는 단어가 코드에 그대로 없어도("토큰 발급/교환/세션" 같은 표현으로만 있어도) **의미를 이해해서 찾아냈다.** 이게 로컬 해싱(문자열/조사 매칭 의존)과 실제 임베딩(의미 기반)의 본질적 차이다.

### Q3. "테스트 커버리지가 낮은 Repository가 어디야?" — 둘 다 원천적으로 못 푼다, 그런데 흥미로운 차이가 있다

두 방식 다 "Repository"라는 단어에만 끌려 나온 결과였고, 실제 커버리지 데이터는 코드 텍스트 어디에도 없어서 **원천적으로 답할 수 없는 질문**이라는 결론은 동일했다.

**그런데 점수 패턴에 흥미로운 차이가 있었다:**

| | 관련 질문(Q1,Q2) 점수대 | 무관 질문(Q3) 점수대 | 신뢰도 신호로 쓸 수 있나 |
|---|---|---|---|
| 로컬 해싱 | 0.18~0.31 | 0.30~0.38 | ❌ **Q3 점수가 오히려 Q1보다 높음** |
| Voyage | 0.54~0.67 | 0.35~0.38 | ✅ 뚜렷한 간격 — "이 질문엔 자신 없다"는 신호가 점수 자체에 나타남 |

076일차 Q3에서 배운 "정직하게 모른다고 답하기"의 다음 단계 발견이다 — **Voyage는 점수 자체가 암묵적으로 확신도를 표현**하지만, 로컬 해싱은 그렇지 않다.

## 트레이드오프 정리

| | 로컬 해싱 (TF hashing) | Voyage (voyage-code-3) |
|---|---|---|
| 검색 품질 | 식별자 문자열 중복에만 반응 | 의미 기반 — 표현 차이를 넘어 매칭 |
| 질의 속도 | 0ms (즉시) | 300ms~21초 (API 왕복 + rate limit) |
| 전체 인덱싱 속도 | 1,224청크 52ms | 이 계정 등급 기준 ~40분 (결제수단 등록 시 대폭 단축) |
| 비용 | $0 | $0.18/1M 토큰, 계정당 첫 2억 토큰 무료 |
| 오프라인 사용 | ✅ 가능 | ❌ 매번 네트워크 필요 |
| API 키 의존성 | 없음 | 필수 — 키 유출/만료가 곧 도구 장애 |
| 신뢰도 신호 | 없음 (Q3에서 확인) | 점수 간격이 확신도를 어느 정도 표현 |

**결론:** 076일차의 설계(`EmbeddingProviderFactory`가 키 유무로 자동 전환)가 맞는 방향이었다 — 로컬 해싱은 "항상 되는 안전망", Voyage는 "품질이 중요할 때 켜는 옵션"으로 계층화하는 게 076에서 076으로 이어지는 자연스러운 결론.

## 076 → 077 발전 요약

```
076: EmbeddingProvider 인터페이스로 추상화, 로컬 해싱으로 파이프라인 전체 검증
     → "나중에 1줄 교체 가능"이라는 설계만 하고 검증은 안 함
        ↓
077: 실제로 Voyage로 교체해서 검증
     → 인터페이스 확장 필요(embedDocuments/embedQuery 비대칭)했지만 
       핵심 구조(Room 저장, 코사인 검색)는 그대로 재사용됨
     → 실제 API 제약(rate limit)을 만나 샘플링 전략으로 대응
     → Q2에서 의미 기반 검색의 실질적 가치를 수치로 확인
```

## 오늘 배운 것 — 한 줄 정리

1. "나중에 교체 가능하게 설계했다"는 **실제로 교체해봐야 검증된다** — 076일차 설계는 부분 수정(비대칭 임베딩 지원)이 필요했지만 핵심 구조는 유지됐다.
2. 무료 API 티어는 **RPM과 TPM 두 종류의 제한을 동시에** 걸 수 있다 — 배치 크기는 실측(토큰 수 확인)으로 정해야 한다.
3. 전체 데이터가 아니라 **샘플로 비교할 때는 그 사실을 결과에 명시**해야 한다 — 조건을 숨긴 비교는 오해를 낳는다.
4. 의미 기반 임베딩의 가치는 **어휘가 정확히 안 겹치는 질문**(Q2: "인증" ↔ "토큰 발급/세션")에서 가장 뚜렷하게 드러난다.
5. **검색 점수의 절대값뿐 아니라 "관련 질문과 무관한 질문 사이의 점수 간격"도 신뢰도 신호**로 쓸 수 있다 — 로컬 해싱은 이 신호가 없었다.
6. API 키처럼 민감한 값은 **로그/diff 출력에도 그대로 찍힐 수 있다** — 터미널 로그를 복사해서 공유할 때는 항상 한 번 더 확인해야 한다.
