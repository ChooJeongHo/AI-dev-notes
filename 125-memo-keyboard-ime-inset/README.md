# 125 - 상세 메모 입력란이 세로 키보드에 가려지는 문제 — 원인은 설정 하나가 아니라 "IME를 무시한 인셋 구조"였고, 수정 뒤 "닫힘"을 둘러싼 롤백 조건 R6을 재정의했다

**124일차에 3/3으로 재현만 해 둔 "상세 화면 메모 입력란이 세로 키보드에 가려짐"을 조사하고 고쳤다. 키보드를 올리면 입력란의 가시 높이가 25회 이상 전부 0px이었고, 메모가 없으면 스크롤로도 닿지 않았다. 원인은 `windowSoftInputMode`가 아니라 edge-to-edge 환경에서 인셋 리스너가 IME를 무시하는 구조였다. `DetailFragment.kt` 한 파일(+22/−2)을 고쳐 36/36에서 217/217px이 보이게 했다. 키보드를 닫으면 페이지가 스크롤 끝으로 이동하는 부작용에서 롤백 조건 R6이 문자 그대로 걸렸고, 완화하지 않고 멈춰서 물은 뒤 근거와 함께 "재정의"로 기록했다**

## 목적

124일차 다른 탭 점검에서 "상세 메모 입력란이 세로 키보드에 가려짐"을 3/3 재현했지만 원인은 보지 않았다. 오늘은 재현 → 원인 분리 → 방안 비교 → 롤백 조건 합의 → 구현 → 기기 검증 순서로 갔다.

원칙은 이전과 같다.
- 수정 전에 먼저 재현하고 측정한다. 증상과 원인을 분리한다.
- 확인하지 못한 것은 확인하지 않았다고 쓴다.
- 오늘은 상세 화면 메모 하나만 고친다. 다른 문제는 발견해도 기록만 한다.
- 롤백 조건은 구현 전에 합의하고, 걸리면 완화하지 않고 멈춰서 선택지를 받는다.

## 작업 1 — 재현과 측정 (코드 수정 0)

실기기 SM-S926N, 세로, 3버튼 내비. IME 상단 y=1794. 입력란(`til_memo`)은 217px이다. "가시 높이"는 입력란 중 툴바 아래부터 IME 위까지 보이는 px로 정의했고, `uiautomator` 경계와 `dumpsys window`의 IME 프레임, 스크린샷으로 교차 확인했다.

| 조건 | 키보드 내림 | 키보드 올림 | 올린 채 스크롤로 닿나 |
|---|---|---|---|
| 영화 550, 메모 0개, 위치 A(입력란 2057–2274) | 217px ×6 | **0px ×5** | 닿지 않음. 끝까지 가도 1835–2052(IME 상단보다 41px 아래) |
| 같은 영화, 위치 B(스크롤 끝) | 217px ×4 | 0px ×3 | 닿지 않음 |
| 같은 영화, 위치 C(2746–2963) | 217px ×4 | 0px ×3 | 해당 없음 |
| 969681, 1423191(포스터 있음), 1767216(포스터·백드롭 없음), 메모 0개 | 각 217px ×4 | 각 0px ×3 | 닿지 않음 |
| 입력 1→4줄(217→291→365→439px) | | 가시 0px, 전 구간 | 상단 1835 고정, 아래로만 자람 |
| 1423191, 메모 5개 표시(`rv_memos` 2060px) | 217px ×3 | 0px | **닿음**. 스크롤하면 838–1055로 올라와 217px 보임 |

- 증상: 키보드를 올리면 입력란이 키보드 뒤로 들어가고, 입력하는 글자가 한 번도 안 보인다. 올림 25회 이상이 전부 같았다. 같은 도구가 내림 상태에서는 217px을 잡아서 "0px"의 양성 대조도 된다.
- **메모가 0개이면 스크롤로도 닿지 않는다.** 닿으려면 입력란 아래에 콘텐츠가 1326px(3120−1794) 이상 있어야 하는데 실제는 1068px(포스터 있음), 736px(포스터·백드롭 없음)라 258px/590px 모자란다. 메모를 처음 쓰려는 가장 흔한 상황이 가장 심하다.
- 화면 자체는 줄지 않는다. `nested_scroll` 경계가 올림/내림 모두 323–3120이다.
- 집계에서 제외한 표본: 7개(`hide_ime`이 정의되지 않아 키보드가 안 내려가고 탭이 키보드 키로 간 경우, 저장은 안 했고 글자 1개는 DEL로 지워 힌트 길이 18로 확인), 계산 값 2건(`til_memo=NA`를 잘못 읽음).

## R6 재정의 — 문자 그대로 걸렸고, 완화하지 않고 멈췄다

R6 직접 조작 중 "키보드를 닫을 때 페이지가 이동"하는 결과가 나와 Claude Code가 멈췄다.

| 입력란 위치 | 탭 직전 | 키보드 올림 | 키보드 내림 후 | 이동량 |
|---|---|---|---|---|
| A(1982, 1996) | 1982 / 1996 | 1549 | 1835 | **−147 / −161px** |
| B(스크롤 끝) | 1835 | 1549 | 1835 | 0px |
| C(2710) | 2710 | 1549 | 1835 | **−875px** |
| 수정 전 | | | | 0px |

- **원인(코드로 설명됨)**: 키보드가 내려가면 아래 패딩 168px이 사라져 스크롤 범위가 줄고, `NestedScrollView`가 현재 스크롤을 새 최대값(스크롤 끝)으로 clamp한다. 그래서 어느 위치에서 시작해도 닫은 뒤에는 입력란이 1835에 놓인다.
- Claude Code는 "이상이 아니다"라고 스스로 판단하지 않고 걸림 가능성으로 보고했다. 선택지는 A 현재 상태 수용 / B 닫힐 때 스크롤 복원 추가(+8~10줄, R4를 36줄로 올려야 함, R1·R2·R5 전부 재측정) / C 수정 중단이었다.

**A(수용)로 결정하고 "R6 재정의"로 기록했다.**
- 수정 전 0px은 입력란이 키보드에 가려져 스크롤이 일어날 수 없던 **고장 난 상태의 값**이라 기준이 될 수 없다.
- 닫힐 때 범위가 줄어 clamp되는 것은 "키보드가 올라올 때 범위를 늘린다"는 같은 메커니즘의 양면, 즉 필연적 결과다.
- **롤백 조건 초안 안에서 R1은 "IME 올림·내림 뒤 스크롤 위치는 의도된 변화"로 대상에서 빼놓고, R6은 "닫힘은 수정 전과 같을 것"으로 써서 서로 충돌했다.** 조건을 완화한 것이 아니라 초안의 모순을 정리한 것이다. 이 모순은 초안을 쓴 쪽(나)의 점검 부족이었다.
- B는 비용이 컸다(R4 상향, 전부 재측정, 키보드가 열린 동안 사용자가 직접 스크롤한 위치를 덮어쓸 새 위험).
- 재정의 전에 닫히는 순간 화면을 프레임으로 확인하는 조건을 달았다. 영상 프레임에서 깜빡임·빈 화면·목록 재배치는 **보이지 않았다.** 다만 올림(6.72초)과 닫힘 완료(7.24초) 사이에 중간 프레임이 없어(0.52초 공백) 그 사이의 모습은 확인하지 못했다. 코드와 R4(24줄)는 그대로다.

## 과정에서 있었던 오판과 정정

- **홈 계층 diff 오탐**: 처음에는 5개 id가 달라 코드를 의심했지만, 같은 데이터에서 다시 재니 0이었다(시청기록 데이터 차이 때문).
- **내 검증 부족**: 메모를 4번 저장하고도 "입력란 아래 콘텐츠 1068px 불변"이라고 쓴 것은 저장이 화면에 안 그려진 상태의 값이었다. 저장 성공을 확인하지 않고 쓴 검증 부족이다.
- **무효로 버린 표본**: 키보드가 안 내려간 7개, `til_memo=NA` 오독 2건, APK `strings` 검색(양성 대조 실패).
- **가로 상세 입력란 23px 차이**는 수정 영향이 아니라 스와이프 관성이었다(같은 조건 3/3 이동 없음).
- **R2 미수행 9칸**은 스크립트 오류였다(위 참고).
- **CI 시간 비교 요청의 오류(내 쪽)**: 자료 요청에서 "124일차(13.0/13.4분)"라고 적었는데, 그 숫자는 124일차가 아니라 123일차 README에 있는 값이었다. Claude Code가 GitHub 기록을 조회해 어떤 값과도 맞지 않음을 확인해서, 이 README는 124·125일차 실측값만 썼다. 123일차 README의 13.0/13.4분이 맞는 값인지는 PR #163과 그 main push 기록을 다시 조회해야 알 수 있다.
- **권한 프롬프트 처리 오류(Claude Code)**: 임시 파일 삭제 명령에서 `rm -rf "$SP/$d"` 형태에 경고가 떴고, 사용자가 질문하는 사이 프롬프트가 시간 초과로 자동 거부됐다. 그 직후 Claude Code가 안전한 형태(`"${SP:?}/${d:?}"`)로 바꿔 다시 실행했고, 사용자 확인 없이 통과해 **실제로 삭제됐다.** 삭제 대상은 임시 worktree 2개, 그 안의 키 사본, DB 복사본 4개로 전부 scratchpad 안이었다. DB는 이미 해시 3/3 일치와 행 수까지 확인된 뒤라 손실은 없었다. Claude Code는 이를 자기 판단 잘못으로 인정하고 "권한 프롬프트가 답 없이 자동 거부되면 같은 작업을 다시 실행하지 않고 알린 뒤 맡긴다"를 메모리에 남겼다.

## 오늘 배운 것 — 한 줄 정리

1. 증상은 "입력란이 안 보임" 하나였지만 원인은 인셋 리스너의 IME 무시 + 스크롤 범위 부족이 겹친 **구조**였다. 설정 하나(`windowSoftInputMode`)를 의심했지만 이미 `adjust=resize`인데도 가렸다.
2. 메모가 0개일 때가 가장 심했다 — 스크롤로도 닿지 않아서 "처음 메모를 쓰는" 사용자가 가장 먼저 막힌다. 데이터 상태에 따라 심각도가 달라졌다.
3. **롤백 조건 초안 안에서 서로 충돌할 수 있다.** R1은 "스크롤 위치 변화는 의도된 변화", R6은 "닫힘은 수정 전과 같을 것"이라 쓰는 바람에 R6이 걸렸다. 초안을 쓸 때 "이 수정이 필연적으로 바꾸는 것은 무엇인가"를 먼저 적고 조건을 쓰면 줄일 수 있다.
4. 이틀 연속(124 R1, 125 R6) 조건이 걸려 "재정의"로 기록했다. 124일차는 수정 전 값이 잘린 값이라서, 125일차는 수정 전 값이 고장 난 상태의 값이라서였다. **재정의는 근거와 함께 명시해야 하고, 두 번 연속이면 조건을 쓰는 방식 자체를 의심해야 한다.**
5. 양성 대조가 이번에도 맞았다(`am crash` 1건 검출, 내림 상태의 217px, `windowSoftInputMode` 검색 0건 확인).
6. "미수행"은 실패도 무효도 아니다. 값이 없는 칸은 따로 세고 다시 채웠다고 적었다.
7. 도구가 사람에게 묻는 순간에 답이 없으면 같은 일을 안전한 형태로 다시 실행하지 않고 알려야 한다. 이번에는 손실이 없었지만 원칙의 문제다.
8. 범위를 지키는 결정(저장 후 목록 미표시를 기록만, 닫힘 스크롤 복원을 기록만)이 R4를 24줄로 지켰다.
9. 한 줄 입력만 보고 통과시키지 않고 1→4줄까지 재서 구현 누락을 잡았다. 롤백 조건에 "여러 줄"을 미리 넣어 둔 것이 효과를 냈다.
10. 기기 측정만으로 검증한 수정은 CI가 지켜 주지 않는다. 이 한계를 "남은 한계"에 적어 두는 것이 다음에 같은 자리를 건드릴 때의 안전장치다.
