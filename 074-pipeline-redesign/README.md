# 074 - 사후 감시에서 사전 설계로 — 073의 한계를 파이프라인 재설계로 해소

**"문제를 막을 것인가, 안 생기게 설계할 것인가"는 양자택일이 아니었다 — 재설계 후에도 검증자가 체크 항목 하나를 실제로 빼먹으면서, 결정론적 백스톱이 왜 여전히 필요한지가 실측으로 증명됐다**

---

## 목적

073일차는 "서브에이전트가 만든 파일은 Stop Hook이 못 본다"는 한계를 **문서화만 하고 끝났다.**
074일차는 이 문제를 사후 감시(Stop Hook)로 더 정교하게 잡으려 하지 않고, **애초에 구현자 에이전트 정의 자체를 고쳐서 문제가 생길 여지를 없앤다.**

---

## 작업 1 — feature-implementer에 "완료 게이트" 못박기

### 핵심 추가 규칙

```markdown
# 필수 조건 (완료 게이트 — 예외 없음)

domain/*.kt 또는 presentation/**/*ViewModel.kt 파일을 신규 생성하거나 
수정했다면, 대응하는 테스트 파일을 반드시 같은 실행 안에서 함께 작성해야 
합니다. 이 조건을 채우지 못했으면 "구현 완료"로 보고할 수 없습니다.

- 계획에 테스트 지시가 없어도 예외 없이 적용됩니다. 
  (feature-planner의 계획서가 테스트를 언급 안 한 건 면책 사유가 아님)
```

> **왜 "계획에 없어도 예외 없음"을 명시했나?** 실제로 과거에 "계획에 테스트 지시가 없다"는 이유로 신규 UseCase 2개의 테스트를 건너뛴 적이 있었고, 그 결과 기존 테스트 파일의 생성자 호출이 컴파일조차 안 되는 사고가 CI에서야 발견된 적이 있었다. 이 규칙은 그 재발 방지책이다.

### 검증 순서를 3단계로 확장 (핵심 변경)

```bash
# Before: 메인 컴파일만 확인
./gradlew :app:compileDebugKotlin

# After: 3단계 순서대로 전부 확인
./gradlew :app:compileDebugKotlin           # ① 메인 소스 컴파일
./gradlew :app:compileDebugUnitTestKotlin   # ② 테스트 소스 컴파일 ← 새로 추가
./gradlew :app:testDebugUnitTest            # ③ 실제 테스트 실행
```

**왜 ②가 중요한가:** 메인 소스가 컴파일된다고 테스트 소스도 컴파일되는 게 아니다. 신규 생성자 파라미터를 **기존** 테스트가 못 받는 경우가 정확히 이 케이스다. 073일차의 사고 원인이 바로 "①만 확인하고 ②를 확인 안 해서 CI에서야 발견"된 것이었다.

## 예상 밖 발견 — "사전 설계"도 100% 보장은 아니었다

검증자 리포트: **Critical/Major/Minor 0건.**

그런데 확인해보니 **A5 항목이 체크리스트 표에서 빠져 있었다** — 새로 추가하라고 지시했는데도, 이번 실행에서는 아예 언급이 없었다.

Claude가 직접 파일 존재를 확인해보니 실제로는 테스트가 다 있어서 결과적으로 문제는 없었지만:

> **"확장한 체크리스트를 검증자가 매번 성실히 수행한다"는 보장은 없다는 걸 실측으로 확인했다.**

이건 정확히 071일차에서 확립한 원칙("LLM 판단은 확률적, 완전한 신뢰 불가")이 **074의 사전 설계 접근에도 그대로 적용된다**는 증거다.

## 073 vs 074 — 비교

| | 073: Stop Hook (사후 감시) | 074: 에이전트 재설계 (사전 예방) |
|---|---|---|
| 개입 시점 | 세션이 끝나려는 순간 (이미 다 끝난 뒤) | 코드가 작성되는 바로 그 실행 안 |
| 신뢰성 | **100% 결정론적** (파일 존재 grep) — 절대 안 빼먹음 | LLM이 지시를 따르는지에 달림 — 이번엔 지켰지만 검증자의 A5 누락에서 보듯 100% 보장 아님 |
| 커버리지 | 서브에이전트가 만든 파일은 못 봄 (transcript 분리) — **치명적 사각지대** | 서브에이전트 자신의 정의이므로 사각지대 없음 — 어떤 경로로 코드가 만들어지든 적용됨 |
| 실패 시 경험 | 세션 종료 거부, 재작업 강제 — 사후적이고 거친 개입 | 애초에 문제가 생기지 않음 — 마찰 없음 |

## 결론 — 양자택일이 아니라 계층 방어(Defense in Depth)

**074가 073보다 근본적으로 낫다** — 073의 치명적 결함(서브에이전트 사각지대)을 애초에 만들지 않기 때문이다.

**하지만 074만으로는 부족하다** — LLM이 지시를 따르는 건 확률적이다(검증자가 A5를 빼먹은 것처럼). 결정론적 백스톱(073)을 없애도 되는 게 아니라, **역할을 좁혀서 유지**해야 한다.

```
정상 경로 (파이프라인을 거쳐 코드가 만들어짐)
    → 074(에이전트 정의 자체의 규칙)가 1차 방어선

예외 경로 (파이프라인 안 거치고 domain/ViewModel을 직접 고침)
    → 073(Stop Hook)이 최후 안전망으로 남음
```

> 067일차 네트워크 보안 강화에서 이미 나왔던 개념("이중 피닝 전략 — OS 레벨 + 앱 레벨")과 같은 원리다. **한 레이어가 뚫려도 다음 레이어가 막는다.**

## 070 → 074, 5일간의 "AI 설계" 시리즈 요약

```
070: 단일 Subagent 설계 (역할 하나, 권한으로 강제) → 오탐 발견
071: 오탐 방지 규칙 내장 + Hook 연동 → "차단 vs 정보 제공" 원칙 확립
072: 멀티 에이전트 파이프라인 → "쪼개면 느릴 것"이라는 직관이 뒤집힘
073: Stop Hook 완성 → "에이전트 경계 = 상태 경계"라는 공통 원인 발견
074: 073의 한계를 재설계로 해소 → "사전 설계도 완벽하지 않다" 재확인
     → 결론: 양자택일이 아니라 계층 방어
```

## 오늘 배운 것 — 한 줄 정리

1. 사후 감시(Stop Hook)의 근본 한계는 **정교하게 만들어도 안 고쳐진다** — 애초에 그 정보 자체(서브에이전트의 변경사항)에 접근할 수 없기 때문이다.
2. 진짜 해법은 "감시를 더 잘하기"가 아니라, **책임을 애초에 올바른 위치(에이전트 정의 자체)로 옮기는 것**이다.
3. `compileDebugKotlin` 성공 ≠ `compileDebugUnitTestKotlin` 성공 — **테스트 소스 컴파일은 별도로 반드시 확인**해야 한다.
4. "계획에 없었다"는 하위 단계의 면책 사유가 되지 않는다 — **각 역할은 자기 책임 범위를 스스로 지켜야 한다.**
5. **사전 설계(074)도 100% 신뢰할 수 없다** — LLM 기반 검증자는 지시받은 체크 항목을 빼먹을 수 있다(A5 누락 사례).
6. 최종 결론: **결정론적 백스톱과 AI 기반 1차 방어선은 경쟁 관계가 아니라 계층 관계다** — 둘 다 필요하되 역할을 좁혀서 공존시킨다.
