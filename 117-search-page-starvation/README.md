# 117 - 검색 페이지 기아 재조사 — 하루 안에 진단이 두 번 뒤집히고, 코드 대신 정직한 정지 상태로 마무리했다

**116일차의 "페이지 기아" 진단을 "로딩 중을 빈 상태로 오판하는 것"이라고 고쳤다가, 재검증에서 KMRB API 429가 끼어들었고, 그 잡음을 걷어내자 기아가 "조건부로 실재"한다는 세 번째 결론에 도달했다 — 코드를 커밋하지 않고 실패 테스트 상태 그대로 정지하기로 했다**

---

## 목적

116일차에서 발견한 검색 필터 페이지 기아 버그("통과 0건이면 다음 페이지가 안 불려 검색 결과 없음이 잘못 표시된다")를 수정한다.

---

## 1차 결론 — "기아가 아니라 오판"

JVM 테스트로 재현을 시도했더니 "다음 페이지가 안 불린다"는 116일차 관측이 재현되지 않았다. 대신 다른 현상이 나타났다.

- 필터로 첫 페이지가 0건이 된 순간부터 refresh=NotLoading, items=0이 된다. 이때 append=Loading인데도 UI는 "검색 결과 없음"을 띄운다.
- 이 상태가 통과 항목이 처음 나타날 때까지, 또는 마지막 페이지까지 계속된다.
- 실기기에서는 페이지당 필터가 약 10초 걸려서, "dragon"+12세 이상은 결과를 찾는 동안 내내 "없음"으로 보이다가 어느 순간 목록이 나타나는 셈이었다.

결론: 진짜 버그는 페이지 기아가 아니라 로딩이 끝나지 않았는데 빈 상태를 확정 표시하는 것이다.

이 진단을 근거로, 승인받은 좁은 범위(1번: UI 판정만 수정)로 handleLoadStates가 itemCount == 0 && append.endOfPaginationReached일 때만 "검색 결과 없음"을 띄우도록 고쳤다.

## 2차 결론 — 재검증에서 결론이 다시 뒤집혔다

1차 결론을 실기기로 재확인하려는 과정에서 예상 밖의 잡음이 끼어들었다.

### KMRB 429 — 측정 자체가 API 한도를 소진시켰다

zombie+전체관람가를 측정하자 KMRB 요청 40건이 1.2초 안에 전부 HTTP 429 Too Many Requests로 실패했다. 오늘 측정으로 KMRB 호출이 약 600건 이상 쌓이면서 공공 API 한도를 소진한 것으로 보였다. 한도가 정확히 얼마인지는 확인되지 않았고, 이 상태에서는 앱의 다른 KMRB 기능(상세 등급, 박스오피스 배지, 필터)도 실패할 수 있었다.

### shimmer 정지 관측

429 이후 몇 분이 지나도 화면은 shimmer에 멈춰 있었고 TMDB 3페이지 요청이 없었다. 실패한 제목이 서로 다른 40개였다는 건, 필터 적용 시점에 이미 2페이지가 로드되어 있었다는 뜻이었다.

### JVM에서 진짜 페이지 기아를 재현했다 — 조건부로

필터 적용 전에 2페이지가 이미 로드되어 있고, 두 페이지 모두 통째로 걸러지면 Paging이 이어 로드를 멈췄다(30초 타임아웃). 1페이지만 로드된 경우에는 정상으로 이어 로드됐다 — 지난번(1차) 재현 시도가 놓친 이유가 바로 이거였다.

정정: "페이지 기아는 없다, 오진이다"는 1페이지만 로드된 경우에만 맞았다. 116일차 관측이 실제 기아였을 수 있다. 1차에서 적용한 UI 수정은 이 경우를 "가짜 검색 결과 없음"에서 "무한 shimmer"로 바꿔놓았을 뿐이었다 — 사용자에게는 더 나쁠 수 있다.

## 작업 6 — 116일차 "근본 해결은 범위 밖"의 해소 정도

| 116일차 항목 | 상태 |
|---|---|
| 통과 0건인데 "검색 결과 없음"이 잘못 표시됨 | 부분 해소. 1페이지 로드 조건은 해소, 2페이지 선로드 조건은 오히려 무한 shimmer로 악화 |
| 다음 페이지가 안 불림 (페이지 기아) | 조건부로 실재로 재분류, 미해소 |
| initialLoadSize=60이 무의미(loadSize 무시) | 확인만 했고 미수정 |
| 연쇄에 상한 없음(knight+15+ 138초, night+전체관람가 94초) | 미해소. 콜드에서 긴 shimmer가 진행 표시 없이 남음(약 86초) |
| 필터를 PagingSource로 이동(근본 리팩터) | 미착수 |
| 문서/메모리 서술 | 두 번 정정. 코드 주석 1건은 훅 오류로 미정정 |

### 대안 실험 (미적용)

필터를 cachedIn 앞으로 옮기고 등급 변경 시 재검색하는 구조는 같은 2페이지 시나리오를 JVM에서 통과했다(fetched [1,2 → 1,2,3,4,5]). 다만 이건 적용하지 않았고, 등급 변경 시 목록이 맨 위로 초기화되고 TMDB 재조회가 생기는 대가가 있다(HTTP 캐시가 대부분 흡수하긴 함).

## 과정에서 생긴 문제 — 숨기지 않고 기록

1. 카카오톡 화면 텍스트 출력. 측정 중 카카오톡이 포그라운드로 올라온 걸 모르고 UI 덤프를 읽다가 메시지 텍스트를 출력했다. 카카오톡에 입력은 보내지 않았고, 덤프 파일은 삭제했으며, 측정 스크립트는 이제 화면을 읽기 전에 포커스를 확인한다.
2. KMRB 429. 로그로 확인된 것만 451건이고, 기준선 측정분은 캡처 실패로 집계하지 못했다. 일일 쿼터인지 순간 제한인지, 지금도 막혀 있는지는 확인하지 못했다.
3. 성급한 정정. 1페이지 로드 조건만 본 결과로 "기아는 없다"를 CLAUDE.md와 메모리에 적었다가 같은 날 다시 고쳤다.
4. 측정 스크립트 결함. kill $!이 adb logcat을 남겨서 수동으로 정리했다. 기준선의 요청 로그 캡처도 실패했다.
5. 훅 오류. 앞서 적은 대로 3회 연속 거부됐다. 우회하지 않았다.

## 현재 상태와 결정 대기

- 미커밋 변경: SearchResultsPane.kt(신규), SearchFragment.kt(수정), 테스트 3개 파일, CLAUDE.md(정정). 재현 테스트가 실패 상태라 지금 push하면 pre-push 훅이 실패한다.
- 결정: KMRB 한도 초기화 후 재개하기로 했다 — 지금은 멈추고, 잘못된 결론 위에 코드를 더 쌓지 않는다.
- 재개 시 정할 것: (A) 필터를 cachedIn 앞으로 이동 vs (B) PagingSource 레벨 필터(상한 포함). UI 수정만 두는 안은 2페이지 선로드 케이스에서 무한 shimmer라 단독으로는 부족하다.
- 재개 지점은 메모리 project_search_empty_state_false_positive.md에 기록해뒀다.

## 핵심 통찰

회귀 테스트가 실제 결함을 놓친 이유는 시나리오에 "이미 2페이지가 로드된 상태"가 없었기 때문이다. 통과하는 테스트가 곧 안전하다는 뜻은 아니다. 사용자가 실제로 밟는 순서(스크롤 → 칩 선택)를 재현하는지가 더 중요했다.

116일차 메모리의 "실제로 재현됨"은 증상(결과 없음 화면)만 근거였고 원인은 검증된 적이 없었다. 증상과 원인을 분리해서 기록해야 다음 세션이 존재하지 않는 원인을 고치지 않는다.

## 오늘 배운 것 — 한 줄 정리

1. 외부 API(KMRB)를 측정 도구로 반복 호출하면, 측정 행위 자체가 실제 서비스의 API 한도를 소진시켜서 다른 기능까지 실패시킬 수 있다.
2. 회귀 재현이 실패해도 원인을 바로 "없다"로 결론짓지 말고, 재현 시나리오 자체가 실제 사용자 경로를 제대로 흉내 냈는지 먼저 의심해야 한다.
3. 부분적인 수정이 한 조건에서는 개선이지만 다른 조건에서는 악화일 수 있다 — "가짜 없음"을 없앴다고 끝이 아니라, 그 대신 생긴 "무한 로딩"도 같은 무게로 평가해야 한다.
4. 잘못된 결론이 문서/메모리에 이미 적혀 있었다면, 정정한 사실도 같은 자리에 명확히 남겨야 다음 세션이 틀린 기록을 그대로 믿지 않는다.
5. 결론이 흔들리는 상태에서는 코드를 커밋하지 않고 정지하는 것도 정당한 결정이다 — 확실하지 않은 위에 다음 작업을 쌓지 않는 게 맞다.
6. 증상(화면에 뭐가 보이는가)과 원인(왜 그런가)은 기록할 때 분리해야 한다 — 증상만 적어두면 다음 세션이 존재하지 않는 원인을 고치려 들 수 있다.
