# 131 - `image.tmdb.org` 인증서 핀은 "11/10 만료 대비"가 아니라 이미 10/14부터 깨져 있었고, 핀을 CA 쪽(루트+중간 5개)으로 재구성해 화면 판정 성공률 4.7~11.8% → 100%, 핀 검증 실패 줄 약 120~300/회 → 0이 됐다

## 목적

127일차에 폰의 회색 포스터가 "`image.tmdb.org` 인증서 핀 불일치"로 보여 후속 후보 1순위로 기록했고, 핀 만료일(2026-11-10)이 다가오고 있었다. 오늘은 만료 전에 핀을 안전하게 갱신하는 작업으로 시작했는데, 첫 조사에서 문제의 성격이 바뀌었다.

원칙은 이전과 같다.
- **읽기 → 재현 → 방안 비교 → 롤백 조건 합의 → 구현 → 기기 검증** 순서를 지킨다. 수정 APK를 설치하기 전에 기준선을 먼저 측정한다.
- 숫자·날짜 기준이나 롤백 조건이 걸리면 해석하지 않고 멈추고 묻는다. 재정의는 이유를 적고 승인을 받는다.
- 기기 설정(`wm density`, 회전 잠금 등)은 바꾸지 않고 마지막에 한 번 더 읽는다. 온보딩 플래그는 직접 수정하지 않는다.
- 요청 URL·키는 출력하지 않고, 핀 값은 앞 8자와 길이만 적는다.
- 저장소 변경은 변경 내용을 보여 주고 push·PR·merge 승인을 따로 받는다.

## 작업 2 — 만료 후 동작과 증상 정리

### 문서·실측으로 확인한 것
- NSC `pin-set`은 체인에 핀된 공개키가 하나 이상 있어야 유효하다. **`expiration`이 지나면 그날부터 핀 검사가 비활성화된다(fail-open, 시스템 CA 신뢰는 유지).** 문서도 만료를 두면 공격자가 우회할 수 있다고 경고한다.
- OkHttp `CertificatePinner`에는 만료 기능이 없다. 해당 호스트에 핀이 있으면 체인에 하나 이상 있어야 한다.
- 실측 b(에뮬레이터 API 37, 디버그): 틀린 핀 + **과거** 만료 → 성공률 100%, 핀 검증 실패 줄 0. 만료 후 핀 검사가 꺼짐을 실제로 확인했다.
- 실측 a: 같은 틀린 핀 + **미래** 만료 → 실패 검출. **디버그 빌드도 OS 층 핀은 적용된다**(`debug-overrides`는 user CA로 서명된 체인에만 핀을 면제). 기존 주석 "디버그 빌드에서 피닝 비활성화"는 OkHttp 앱 층에만 맞는 말이었다.
- 실측 c: NSC는 수정본이고 OkHttp 핀만 틀린 릴리스 → 이미지 실패. **NSC만 고치면 릴리스가 안 고쳐진다**는 근거다.

### 그래서 11/10은 증상을 바꾼다
11/10 이후에는 OS 층의 핀 검사가 꺼지지만 앱 층에는 만료가 없어서, **디버그 빌드는 풀리고 릴리스는 계속 실패하는 함정**이 생긴다. 그래서 문서만 고치는 변경(원안 R1)으로는 부족했다.

### 포스터 회색 증상과의 관계
- DEVLOG.md:47의 "폰도 일부 포스터 회색(핀 추정)"이 증거와 맞다. 127일차 폰 기준선에서 핀 실패가 2,866줄이었다.
- CLAUDE.md:315 "폰은 YR2라 정상"은 정정이 반영되지 않은 낡은 문장이었다(127일차에 근거가 약하다고 내가 정정한 부분이 이번 실측으로 확인됐다). CLAUDE.md의 "중간 인증서는 경로마다 다름"도 오늘 증거로는 지지되지 않았다(미국 러너와 한국 엣지 8곳이 같은 체인을 주고, 10/12 → 10/19 시간 순서로 설명된다). 다만 10/16 즈음 일부 엣지에 옛 인증서가 남았을 가능성은 배제하지 못했다.
