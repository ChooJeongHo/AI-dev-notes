# 094 - 인증서 핀 간헐적 실패 — 원인 재현 없이 코드로 확인 가능한 만큼 개선

**"재현될 때까지 기다린다"는 접근을 버리고, 코드 검토만으로 확인 가능한 것을 확인하고 안전장치를 추가하는 방식으로 확실하게 마무리했다**

---

## 목적

091일차에서 미해결로 남겨둔 인증서 핀 간헐적 실패 이슈. 재현을 기다리는 접근은 도돌이표가 될 위험이 커서, "원인 100% 규명"이 아니라 "코드로 확인 가능한 것 확인 + 안전장치 추가"로 목표를 낮춰서 재현 여부와 무관하게 오늘 확실히 끝나도록 진행했다.

---

## 확인한 것

| 항목 | 결과 |
|---|---|
| 핀 값 위치 | NetworkModule.kt의 CertificatePinner.Builder에서 확인 |
| 백업 핀 존재 여부 | 1개만 등록되어 있었음 — 인증서 로테이션 시 검증 실패 위험 |
| 실패 시 동작 | SSLHandshakeException → IOException으로 처리되어 DomainException.NetworkError로 변환됨, 재시도 없이 즉시 실패 |

---

## 즉시 개선한 것

1. 백업 핀 추가 — 기존 리프 인증서 핀 외에 상위(중간 CA) 인증서 핀을 백업으로 등록해서, TMDB가 인증서를 교체해도 한쪽 핀이 살아있도록 이중화
2. SSL 핸드셰이크 실패 전용 재시도 — 인증서 검증 관련 예외에 한해 1~2회 짧은 재시도를 추가해, 일시적 네트워크/타이밍 문제로 인한 실패를 흡수

---

## 정직한 결론

간헐적 실패의 정확한 원인은 재현 전까지는 특정할 수 없다. 이건 오늘 못 밝힌 게 아니라, 애초에 코드 검토만으로는 알 수 없는 성질의 문제다.

대신 067일차의 "이중 피닝(OS+앱 레벨)" 원칙을 오늘은 "핀 자체의 이중화(주 핀+백업 핀)"로 한 단계 더 강화했고, 실패해도 한 번 더 시도하는 안전장치를 추가했다. 원인을 몰라도 재발 시 영향을 줄이는 조치는 확실하게 끝냈다.
