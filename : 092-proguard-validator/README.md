# 092 - 기존 스킬로 검증하기 — `/proguard-validator` (검증 스킬 3부작 완성)

**한 번도 실제 릴리즈 빌드를 배포한 적 없던 MovieFinder를, 배포 전에 미리 R8/ProGuard 규칙을 점검해서 "릴리즈 빌드에서만 터질 크래시"를 사전에 차단했다**

---

## 목적

089일차에 계획한 검증 스킬 3부작(network-layer-validator → material3-design-validator → proguard-validator)의 마지막. 089일차에서 "아직 실제 릴리즈 배포 이력이 없어서 지금 당장 급하지 않다"고 순위를 낮췄던 항목을, 3부작을 마무리하며 점검한다.

---

## 왜 지금이 딱 좋은 타이밍인가

081일차 이후 반복된 패턴 — "컴파일·테스트·detekt는 통과했지만 실기기(또는 특정 빌드 모드)에서만 드러나는 문제" — 가 ProGuard/R8에도 그대로 적용된다. minifyEnabled true인 릴리즈 빌드는 디버그 빌드와 바이트코드 자체가 다르게 난독화·최적화되므로, 디버그 빌드로 아무리 테스트해도 릴리즈 빌드 전용 크래시는 절대 못 잡는다. 066일차에 릴리즈 파이프라인을 만들어뒀지만 아직 실제 배포 전이라, 지금이 이 문제를 무료로(사고 없이) 잡을 수 있는 시점이다.

---

## 검증 결과

### 실질 이슈 — keep 규칙 보강 필요

| 대상 | 문제 | 조치 |
|---|---|---|
| KOFIC/TMDB DTO 클래스 (kotlinx.serialization) | @Serializable 클래스라도 R8이 필드명을 난독화하면 JSON 역직렬화가 릴리즈 빌드에서만 조용히 실패할 수 있음 | 직렬화 대상 클래스에 대한 keep 규칙 보강 |
| Glance 위젯 관련 클래스 (086일차) | GlanceAppWidgetReceiver/GlanceAppWidget 구현체가 리플렉션 기반으로 시스템에서 참조되는데, 난독화 시 클래스명이 바뀌면 위젯이 릴리즈 빌드에서만 깨질 수 있음 | 위젯 클래스 keep 규칙 추가 |

### 정보성 — 이미 기본으로 커버되는 항목

| 대상 | 왜 문제가 아닌지 |
|---|---|
| Room Entity/DAO | KSP 기반 코드 생성이라 R8 난독화 이전 컴파일 타임에 이미 구체 클래스로 확정되어 별도 keep 불필요 |
| Retrofit 인터페이스 | 표준 Android Gradle Plugin 기본 ProGuard 규칙에 이미 Retrofit 관련 keep이 포함되어 있음 |

> 089/091일차와 같은 패턴이 오늘도 나타났다 — 검증 도구가 "R8이 건드리는 모든 것을 다 keep하라"는 식으로 뭉뚱그리지 않고, 어떤 게 기본 규칙으로 이미 안전하고 어떤 게 실제로 빠졌는지를 구분해서 짚었다.

---

## 즉시 수정 — 실제 minifyEnabled 빌드로 검증

089/091일차는 "실기기"로 검증했다면, 092일차는 "릴리즈 빌드 자체"로 검증해야 하는 다른 종류의 확인이 필요했다.

```
proguard-rules.pro에 keep 규칙 추가
    (KOFIC/TMDB 직렬화 클래스, Glance 위젯 클래스)
    ↓
./gradlew assembleRelease (minifyEnabled=true로 실제 난독화 빌드)
    ↓
릴리즈 APK를 실기기에 설치
    ↓
박스오피스 데이터 로딩(KOFIC/TMDB 직렬화 경로) +
홈 화면 위젯 추가(Glance 경로) 정상 동작 확인
```

디버그 빌드로는 이 문제 자체가 재현되지 않기 때문에, 검증도 반드시 릴리즈 빌드로 해야 의미가 있었다.

## 089 → 091 → 092, 검증 스킬 3부작 요약

| | 089 | 091 | 092 |
|---|---|---|---|
| 검증 대상 | 네트워크 레이어 | Material3 디자인 | R8/ProGuard 규칙 |
| 발견한 실질 이슈 | callTimeout 미설정 | textSize 하드코딩 | 직렬화/위젯 keep 규칙 누락 |
| 검증 방법 | 실기기 + 유닛 테스트 | 실기기 + 다크모드 | 릴리즈(minifyEnabled) 빌드 + 실기기 |
| 검증 도구가 걸러낸 오탐 | coroutineScope 선택 | 위젯 하드코딩, 테마 선택 | Room/Retrofit 기본 keep 규칙 |

**세 스킬 모두에서 반복된 패턴:** 체크리스트를 기계적으로 적용하지 않고, "기존에 이미 커버되는 것"과 "실제로 빠진 것"을 구분했다. 076~089일차(6차 사이클)에서 확인된 "AI 검증 도구의 성숙도"가, 직접 만든 도구가 아닌 기존 스킬 3개 모두에서 일관되게 나타났다는 게 이 3부작 전체의 결론이다.

## 081일차와의 연결 — "특정 조건에서만 보이는 문제"의 네 번째 변주

| 일차 | 어떤 조건에서만 보였나 |
|---|---|
| 056/079 | 에뮬레이터 vs 실기기 (성능) |
| 081 | 실기기 (기능 정확성 — 목업으로 재현 안 됨) |
| 092 | 릴리즈(minifyEnabled) 빌드 vs 디버그 빌드 (난독화) |

"이 코드가 실제로 배포될 조건에서 검증했는가"라는 하나의 질문이, 이번엔 "에뮬레이터/실기기"가 아니라 "디버그/릴리즈 빌드"라는 다른 축으로 나타났다. 매번 다른 형태였지만 근본은 같다 — 테스트 환경과 실제 배포 환경의 차이가 클수록, 그 차이 안에서만 드러나는 버그가 있다.

---

## 오늘 배운 것 — 한 줄 정리

1. minifyEnabled 릴리즈 빌드는 디버그 빌드와 바이트코드가 달라서, **디버그 빌드 테스트만으로는 릴리즈 전용 크래시를 절대 못 잡는다.**
2. @Serializable 클래스, 리플렉션 기반으로 참조되는 클래스(위젯 등)는 **R8 난독화 시 특별히 keep 규칙이 필요**하다.
3. Room(KSP)이나 Retrofit처럼 널리 쓰이는 라이브러리는 **AGP 기본 ProGuard 규칙에 이미 커버되는 경우가 많다** — 무조건 다 keep하지 말고 실제로 빠진 것만 추가하면 된다.
4. "실기기냐 아니냐"뿐 아니라 "릴리즈 빌드냐 아니냐"도 **테스트 환경과 실제 배포 환경의 간극**을 만드는 또 다른 축이다.
5. 아직 실제 배포 전인 지금이, 이런 문제를 **사고 없이 무료로 잡을 수 있는 가장 좋은 타이밍**이다.
